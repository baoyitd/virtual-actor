# v0.5.0 最终用户 Review 指南

版本：v0.5.0 | 日期：2026-06-11 | 当前 Formal Status：Self-Tested

## 1. 评审目标

本轮 review 重点不是再做工程自测，而是站在最终用户和产品验收视角确认 5 件事：

1. 角色定义工作台是否比旧版更容易理解、更容易完成。
2. 角色能力侧与资产治理侧是否真正拆开，没有重新混成一个大表单。
3. 使用前说明与调用预览是否真能帮助人在调用前做判断，而不是第二个重编辑页。
4. 测试、发布、外供、正式消费、市场推荐是否构成完整主链路。
5. 当前产品形态是否足以支撑“企业角色资产可沉淀、可复用、可外供”的核心价值。

## 3. 建议顺序

建议分两轮：

1. 快速走查：15 到 20 分钟
2. 完整链路：30 到 45 分钟

如果快速走查已经出现明显 P0/P1 问题，可以先停，不必完整走完第二轮。

## 4. 第一轮：快速走查

### Step 1. 登录后看角色列表

进入角色列表页，重点判断：

1. 你是否能一眼看懂列表在表达什么。
2. 角色卡片上的状态、说明卡状态、测试状态、输出方式是否足够帮助你判断“这个角色现在能不能用”。
3. 列表顶部的入口组织是否自然，是否能理解“新建角色 / 数据资产管理 / 市场”等入口各自作用。

预期：

1. 不需要额外解释就能理解页面主结构。
2. 不会感觉是“字段堆在一起的后台页”。

### Step 2. 打开一条已发布角色详情

从角色列表中选择一条已发布角色，打开详情页，重点判断：

1. 详情页能否清楚表达角色是什么。
2. 角色能力信息、说明卡状态、治理状态是否被合理分层。
3. 从详情页去“使用前说明”“治理与发布”“试用”“正式消费”的入口是否自然。

预期：

1. 详情页是总览，不是大表单。
2. 角色能力、说明、治理、使用入口的关系是清楚的。

### Step 3. 看“使用前说明与调用预览”

打开说明卡页，重点判断：

1. 页面是不是以说明卡为主，而不是第二个重表单页。
2. 你是否能在不调用角色的前提下，判断这个角色适不适合当前任务。
3. “适用场景 / 怎么正确使用 / 你将得到什么 / 为什么可信 / 当前限制”这些信息是否有价值。

预期：

1. 这是面向消费前判断的页面。
2. 编辑只是轻量修订，不是主叙事。

### Step 4. 看“治理与发布”

打开治理页，重点判断：

1. 这里是否明确是治理页面，而不是继续写角色能力。
2. `owner / business_domain / category` 这类字段是否体现资产治理责任，而不是为了填表而填表。
3. 发布前检查是否告诉你“为什么不能发布、去哪补齐”。

预期：

1. 治理责任与角色能力是分开的。
2. 门禁解释清楚，不是黑盒拦截。

### Step 5. 看“外供与追溯”

打开外供页，重点判断：

1. 你是否能理解 `Tool package / Skill package` 是什么。
2. 平台是不是把外供说明、版本绑定、回写要求讲清楚了。
3. 这页是否足以支撑“角色资产可对外复用”的产品感，而不是只有下载文件。

预期：

1. 外供不是裸 API。
2. 回写和追溯不是被省略掉的。

### Step 6. 看“正式消费”

打开使用台，输入一个经营复盘类问题，重点判断：

1. 调用前说明是否有帮助。
2. 返回结果是否像一个“经营复盘顾问”的结果，而不是普通 LLM 瞎答。
3. 结构化结果、状态、边界、来源是否表达清楚。

建议问题：

`请依据当前知识与数据，给出经营复盘结论，并列出主要依据。`

预期：

1. 有明确答案。
2. 有结构化结果。
3. 有 `knowledge + data` 来源。

### Step 7. 看资产市场

打开市场页，重点判断：

1. 市场是否不只是列表目录，而是真能帮助人发现角色。
2. AI 推荐是否比简单分类筛选更有帮助。
3. 无匹配、越界意图、正常匹配这三类情况是否表达合理。

建议问题：

`我需要一个帮管理层做经营复盘和投资前置判断的角色`

预期：

1. 应推荐与“经营复盘 / 管理层判断 / 投资前置分析”语义接近的角色，而不是无关角色。
2. 推荐理由要像在说这个角色为什么适合，不是空话。

## 5. 第二轮：完整链路

如果第一轮通过，再走一遍从零创建。

### Step 1. 新建角色并使用 AI 草案

进入新建角色页：

1. 点击 `生成结构化草案`
2. 看 AI 是否把一段描述落成结构化内容
3. 重点看 `L1-L4` 是否比旧版更容易理解

你要重点判断：

1. `L1-L4` 的组织是否自然。
2. `placeholder` 是否真在帮助填写。
3. 高级项是否被适度折叠，没有一上来压满。

### Step 2. 补角色能力

在工作台中：

1. 绑定知识
2. 选择数据资产
3. 查看 `output_mode / output_type`
4. 保存草稿

你要重点判断：

1. 角色能力侧是否只承接“角色本身的组成”。
2. 治理类内容是否没有混进来。

### Step 3. 去说明卡页确认

进入说明卡页后，判断：

1. 系统生成的内容是否像“可消费说明”。
2. 如果来源变化，`stale -> fresh` 这条链路是否能理解。

### Step 4. 去治理页进入内部试用

在治理页补齐必要治理项后：

1. 进入内部试用
2. 看门禁是否合理

### Step 5. 走 test-consume

在测试台执行一次测试，判断：

1. `test-consume` 和正式消费是否有明确区隔。
2. 测试结果是否对说明卡和治理状态产生合理影响。

### Step 6. 发布并外供

回治理页发布，再去外供页：

1. 生成 `Tool package`
2. 生成 `Skill package`
3. 看版本绑定、包内容和回写要求

### Step 7. 回到正式消费和市场

最后再去：

1. 使用台
2. 市场页

确认从“创建 -> 说明 -> 治理 -> 测试 -> 发布 -> 外供 -> 消费 -> 市场”是否真是一条完整链路。

## 6. 重点验收维度

如果你时间有限，优先看这 6 项：

1. 新工作台是否显著降低了理解成本。
2. 角色能力侧和治理侧是否真正拆开。
3. 说明卡是否有真实消费价值。
4. 发布门禁是否体现资产治理，而不是技术校验。
5. 外供页是否能支撑“角色资产可外部复用”的商业表达。
6. 正式消费与市场推荐是否能体现这个角色不是普通大模型回答。

## 7. 建议记录方式

如果你发现问题，建议每条记录 4 项：

1. 页面或路径
2. 操作步骤
3. 预期结果
4. 实际结果

如果是 UI/UE/UX 问题，额外说明一句：

`为什么这会增加理解成本、操作成本，或者损伤产品价值表达`

如果是功能问题，额外说明一句：

`它会不会阻断主链路`

## 8. 当前已知非阻塞背景

这些不是你这轮 review 的重点：

1. `v0.5.0` 当前是 `Self-Tested`，但不是 `Accepted`
2. 当前唯一 `Accepted` 对外交付基线仍是 `v0.3.0-commercial-trial`
3. `18080` 的 smoke runtime 仍保留给工作方 / 测试方做主链路复现；最终用户 review 只使用 `18120` 的真实集成环境

## 9. 一句话建议

先走第一轮快速走查；如果你在第一轮已经明确感受到“产品结构是对的，只是还有细节问题”，再进入第二轮完整链路。这样效率最高。
