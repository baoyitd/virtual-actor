# DD-13 AI 推荐质量复审结论与整改要求（2026-05-27）

## 1. 复审结论

结论：**不通过**。

本轮 `DD-13 资产市场 AI 推荐入口` 不能按“已闭合”收口，推荐质量问题必须在 `v0.4` 本轮解决，不接受保留为 `v0.4.x` 风险项。

当前实现已完成：

- 资产市场页面入口、场景卡片、推荐输入区、推荐结果态、空态、返回列表。
- 场景卡片按 `output_type` 过滤。
- 明显无意义输入可落到 `matched=false + 运营信号`。

但这还不足以证明“业务意图 -> 已发布角色匹配 + 推荐理由”已成立。当前推荐更接近“关键词命中 `output_type` 后返回同类角色”，而不是“理解业务意图后推荐合适角色资产”。

## 2. 本次复审证据

本次真实运行态和真实浏览器复审观察到：

1. 正向样例 `我需要帮高管做项目投资决策的角色` 可以返回推荐结果。
2. 无意义字符串 `qxkzmt 98231` 可以正确返回无匹配空态。
3. 但输入 `火星殖民地税务筹划和跨星际报关审查` 时，系统仍推荐了 `合规审核角色_v2`。

第 3 点说明当前推荐链路仍存在实质性误判：只要意图里带有“审查/审核/税务/报关”等局部词汇，就可能被路由到某个 `output_type` 并给出看似合理的推荐。这不符合本项目对“企业数字角色资产运营平台”的产品要求，也不符合 `DD-13` 的业务语义。

## 3. 根因判定

根因不是单一 bug，而是推荐设计和实现口径偏弱：

1. `Phase A` 仍是“关键词 -> output_type”映射，语义层级过低。
2. `Phase B` 只按 `output_type` 从已发布角色池中过滤，未对 `business_domain`、`applicable_scenarios`、`bio`、`tags`、边界声明做真实匹配。
3. `Phase C` 的 LLM 只负责“写推荐理由”，不负责“判断该角色是否真的匹配”或“拒绝推荐”。
4. 缺少“推荐池准入”规则，信息不完整的已发布角色也会进入 AI 推荐池，导致推荐依据虚弱。
5. 自动化测试口径偏低，当前只证明“有结果/无结果”，没有拦住“词面沾边但业务不匹配”的假阳性。

## 4. 本轮必须补齐的整改项

### 4.1 推荐语义必须升级，不能继续停留在 output_type 路由

工作方需要把推荐链路从：

```text
intent 关键词 -> output_type -> 同类角色 -> 生成理由
```

升级为至少：

```text
intent 结构化分析 -> 候选角色召回 -> 角色匹配评分/拒判 -> 推荐理由
```

最低要求：

1. 先对用户意图做结构化提取，至少形成：
   - `output_type` 候选
   - `business_domain` / 业务域判断
   - `applicable_scenarios` / 任务场景线索
   - 是否超出企业正常业务语境或当前角色池边界
   - 匹配置信度
2. 再对候选角色做匹配评分，评分至少基于：
   - `output_type`
   - `business_domain`
   - `applicable_scenarios`
   - `bio`
   - `tags`
   - 必要时结合 `knowledge_boundary` / `capability_boundary`
3. 低于阈值时必须返回 `matched=false`，不能因为某个关键词沾边就给出推荐。

### 4.2 LLM 的职责必须从“润色理由”升级为“参与判断是否匹配”

当前 LLM 只负责写 `recommendation_reason`，这不够。

本轮至少需要实现以下两种方式之一：

1. `LLM rerank / judge`：
   - 先用规则或召回拿到候选角色；
   - 再让 LLM 对每个候选角色输出 `match / no_match`、`score`、`reason`；
   - 只有通过阈值的角色才进入推荐结果。

2. `规则评分 + LLM 只解释`：
   - 如果工作方不愿让 LLM 参与最终判定，那么必须先实现足够强的规则评分；
   - 且对“超范围/语义不相干”必须能稳定拒绝；
   - LLM 只在通过规则阈值后补充推荐理由。

无论选哪种方式，都不得继续维持“先按关键词分流，再对所有同类角色统一给理由”的弱方案。

### 4.3 推荐池必须有准入门槛

不是所有 `published` 角色都可以直接进入 AI 推荐池。

本轮需明确并实现：

1. 进入 AI 推荐池的角色至少要具备：
   - `output_type`
   - `business_domain`
   - `applicable_scenarios`
   - 有意义的 `bio` 或等价业务描述
2. 不满足以上条件的角色：
   - 可以继续出现在资产市场普通列表；
   - 但不得参与 AI 推荐；
   - 如有必要，可在管理侧标注“补齐场景信息后方可进入 AI 推荐池”。

否则推荐系统本身没有足够的角色画像可供判断，质量不可能稳定。

### 4.4 legacy / 历史已发布角色的数据补齐策略必须明确

如果现有已发布角色缺少 `applicable_scenarios`、`business_domain` 等字段，工作方需要同步提交：

1. 哪些字段缺失会阻止其进入 AI 推荐池；
2. 历史角色如何补填；
3. 未补填时对资产市场列表和 AI 推荐各自的影响；
4. 是否需要迁移脚本、默认值策略或一次性回填脚本。

这不是可选说明，而是本轮推荐质量整改的组成部分。

### 4.5 推荐理由必须“有依据”，不能只是泛化话术

当前推荐理由中存在大量模板化表达，例如：

```text
基于您的业务意图和角色XX输出类型匹配推荐
```

这类文案不能作为推荐成立的证据。

本轮要求：

1. 推荐理由必须明确引用角色的实际匹配依据，例如：
   - 适用场景
   - 业务域
   - 知识边界
   - 输出类型为何匹配
2. 如果角色缺少这些依据，就不应进入推荐结果。

## 5. 自动化测试必须同步升级

当前 `V29-V34` 只能证明基础通路，不足以证明推荐质量。工作方本轮必须补齐新的验收测试，至少覆盖以下类型：

1. 正向匹配：
   - 投资决策意图 -> 只返回决策支持相关角色。
2. 明确无匹配：
   - `qxkzmt 98231` -> `matched=false`。
3. 词面沾边但语义不匹配：
   - `火星殖民地税务筹划和跨星际报关审查` -> 必须 `matched=false`。
4. 域不匹配：
   - 例如投资审查意图，不得推荐一个仅适用于其他业务域的角色。
5. 角色画像缺失：
   - 缺少 `applicable_scenarios` 或 `business_domain` 的已发布角色，不得进入 AI 推荐结果。
6. 推荐理由质量：
   - 不允许仅返回通用模板话术；
   - 需要断言理由中包含角色真实匹配信息或结构化依据。

如果工作方采用 LLM judge / rerank，还必须补齐：

7. LLM 失败回退策略：
   - 在 LLM 不可用时，系统仍能保守拒绝，而不是放宽推荐。

## 6. 浏览器/人工验证口径

工作方复提审前，至少要补齐以下真实验证证据：

1. 正向推荐浏览器录证：
   - 输入高管投资决策意图，出现合理推荐。
2. 反向拒绝浏览器录证：
   - 输入 `火星殖民地税务筹划和跨星际报关审查`，出现“未找到匹配的已发布角色”空态。
3. 返回列表复位验证：
   - 从推荐结果返回列表后，筛选状态和结果态都已正确清空。

## 7. 本轮复提审要求

工作方下次提审时，必须同时回传以下内容：

1. 推荐方案如何升级的设计说明：
   - 结构化意图分析
   - 候选召回
   - 匹配评分 / 拒判
   - 推荐理由生成
2. 推荐池准入规则和历史数据补齐策略。
3. 新增/修改的自动化测试清单与结果。

## 8. 对工作方的明确口径

本次不是“再做一点体验优化”，而是“推荐能力尚未达到 v0.4 的验收下限”。

请按以下原则整改：

1. 不得把该问题降级为“推荐质量后续优化”。
2. 不得只改文案或只调关键词表。
3. 不得只用新增 few-shot / prompt 润色替代匹配逻辑升级。
4. 必须同时解决：
   - 匹配判定逻辑
   - 推荐池准入
   - 历史角色画像不足
   - 自动化测试口径偏弱

整改完成后，再按“本轮已闭合”重新提审。

## 9. 关于 LLM 调用方式的审核建议（非强制）

以下是审核方给出的**建议方案**，用于帮助工作方评估实现路径，但**不是强制指定方案**。工作方应回到问题本质，自行评估是否采纳，并在提审时说明取舍理由。

建议优先考虑：

```text
推荐池准入过滤
-> 非 LLM 候选召回
-> 单次 LLM judge / rerank
-> 阈值过滤 / 保守拒绝
```

含义是：

1. 先把不满足推荐池准入条件的角色排除；
2. 用非 LLM 方式先召回少量候选角色；
3. 只做 **1 次 LLM 调用**，同时输出：
   - `intent_summary`
   - `is_out_of_scope`
   - 候选角色的 `match / no_match`
   - `score`
   - `reason`
4. 分数不足时直接拒绝推荐。

给出该建议的原因：

1. 当前根因不是“缺少一次意图分析调用”，而是“缺少真正的匹配判定和拒判能力”。
2. 两次同步 LLM 调用（Phase A + Phase C）会拉高时延和复杂度，但未必显著提升本轮问题的闭合质量。
3. “非 LLM 召回 + 单次 LLM judge”更利于：
   - 控制响应时延
   - 控制 prompt 长度
   - 控制候选规模
   - 测试稳定复现
   - LLM 失败时保守拒绝

但这只是建议，不是裁决。工作方可以选择其他方案，例如：

- 两次 LLM 调用（独立意图分析 + 候选 judge）
- 更强的规则评分 + LLM 仅解释
- 其他能够实质解决“误判推荐”问题的方案

前提是：

1. 必须真正解决“词面沾边即误推角色”的根因；
2. 必须满足本文件第 4 节和第 5 节的整改要求；
3. 必须在复提审时说明：
   - 为什么选择该方案
   - 为什么它能更好解决当前问题
   - 性能、稳定性、测试和回退策略如何控制
