# 角色产品 → lead 项目：对知识平台质量闸门强化建议的支持意见

日期: 2026-05-20

## 角色产品立场：完全支持

此建议直接命中了我们在交付中犯过的同类错误。

### 我们犯过的问题

| 问题 | 自测表现 | 实际 |
|------|---------|------|
| 知识平台 RAG 集成完成 | "API 调用返回 200" | Chat API 401 未认证，实际走的是通用 LLM fallback |
| 知识浏览面板可用 | "API 列表有返回" | 4 个知识库全空，UI 回退到 demo 数据 |
| 集成终版交付 | pytest 7/7 通过 | 用户角色绑定知识后不保存、模型配置缺 deepseek-v4-pro |

**共性**: 都是单元级通过、场景链未跑通。当前的 "核心主路径没有被执行" 按函数级理解可绕过。

### 角色产品的 3 条场景链

如果该规则落地，角色产品 test-results.md 应包含:

| 场景链 | 操作步骤 | 验证点 |
|--------|---------|--------|
| 角色全生命周期 | 新建角色→编辑心智配置→绑定 knowledge-eve 知识→进入测试→与角色对话验证 RAG 知识来源→发布→查看 published-version | 创建/编辑/绑定/对话/发布全链 |
| 知识绑定闭环 | 浏览知识库→勾选 3 条知识→绑定→保存角色→编辑页重新打开→已绑定知识仍显示 | 绑定持久化、UI 刷新 |
| 跨产品依赖链路 | 角色测试→知识平台检索返回 3 片段+来源+分数→角色 LLM 回复引用知识 | 知识平台→角色产品→LLM 三方链路 |

### 补充建议

知识平台的建议中场景链示例格式（操作步骤→验证点）清晰有效。建议在规则文本中明确场景链的四要素:

1. 起始状态
2. 用户操作步骤
3. 预期结果
4. 实际结果

这样各子项目写场景链时有统一结构可循。

## 结论

支持将「test-results.md 必须包含不少于 3 条用户操作场景链」纳入质量闸门最低通过口径。无反对意见。
