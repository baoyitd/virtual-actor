# 角色产品 → 知识平台 接口需求与缺口评估

> 版本：v1.0 | 日期：2026-06-17
> 发起方：角色产品（Virtual Actor）
> 接收方：知识平台（Knowledge Workbench）
> 目的：从接口消费方角度，梳理角色产品对知识平台的接口需求、当前对接现状与缺口，请知识平台确认现状理解是否准确，并对缺口项提出满足方案
> 前置文档：`role-to-knowledge-integration-proposal.md`（v0.3，2026-05-14，双边闭环）、`handoff-public-contract-interface.zh-CN.md`（2026-06-16，知识平台发起）

---

## 一、梳理方法

本评估从角色产品的**用户场景与项目目标**出发推导接口需求，不从当前代码实现推导。

角色产品的项目目标：帮助企业创建、管理、运营可被调用的数字角色资产，角色基于专属知识、按自身立场给出**可靠结论**。

"可靠结论"的关键支撑：角色必须能区分知识的权威层级——引用 P1 制度级依据与 P3 参考级材料，在回答中的权重和表述应有差异。当前角色产品无法做到这一点。

---

## 二、接口需求（按用户场景推导）

### 场景1：角色创建/编辑——浏览与绑定知识

**用户场景**：角色创建者在定义角色时，需要选择将哪些知识对象绑定到角色，形成角色的专属知识范围。

**用户价值**：创建者不应只看到"文件列表+标题"，而应能看到每篇知识的权威层级（P1 制度级 / P2 操作指南 / P3 参考资料）、文档角色（总纲/细则/案例）、适用与不适用范围——这样才能做出有价值的绑定决策，而不是盲目绑定或仅凭标题猜测。

**需要知识平台提供的接口能力**：

| 需求项 | 说明 |
|--------|------|
| 知识库列表 | 列出可挂载的知识库/集合，返回 id 和名称 |
| 知识对象清单 | 列出指定知识库下的所有知识对象，每条返回：knowledge_object_id、title、tier（权威层级）、doc_role（文档角色）、evidence_type（证据类型）、canonical（是否正式依据）、use_for / not_for（适用/不适用范围）、summary、tags、type |

### 场景2：角色消费——知识检索支撑角色回答

**用户场景**：角色被消费方调用时，需要从已绑定的知识范围中检索相关片段，注入角色自身的 LLM prompt，由角色 LLM 合成回答。角色产品始终自行合成回答，不会委托知识平台代为合成——因为回答必须体现角色的立场、观点和决策风格，而非仅展示知识事实。

**用户价值**：角色的回答应区分引用的权威程度——P1 制度级依据应标注为正式依据，P3 参考级材料应标注为辅助参考。消费方看到"本结论基于3篇P1制度级依据和2篇P3参考材料"比看到"基于5篇来源不明的文档"更有决策支撑力。

**需要知识平台提供的接口能力**：

| 需求项 | 说明 |
|--------|------|
| RAG 检索 | 输入 query + 知识范围，返回相关内容片段，每条包含：chunk 内容、来源文档 reference、权威层级 tier、相关性 score |
| 问题路由（潜在改进，非硬性缺口） | 输入问题，输出路由结果（问题类型、适用权威层级、边界模式）。角色产品当前用关键词匹配做边界检查，知识平台的路由能力可提升精确度，但当前方案可工作 |

### 场景3：角色发布——知识版本快照

**用户场景**：角色发布时，需要记录当前知识平台的版本标识，用于追溯"发布时角色绑定的知识是什么版本"。

**用户价值**：保障已发布角色的知识追溯性——消费方或审计方可回查角色发布时刻的知识基底版本。

**需要知识平台提供的接口能力**：

| 需求项 | 说明 |
|--------|------|
| 版本标识 | 返回当前知识库的版本标识（如 commit_hash 或 version_id），不可变，用于角色发布时快照记录 |

### 场景4：角色健康检查

**用户场景**：角色消费前，系统需要确认知识平台可达且认证有效。

**用户价值**：避免在知识平台不可达时给出无知识支撑的虚假回答，保障消费结果的可靠性。

**需要知识平台提供的接口能力**：

| 需求项 | 说明 |
|--------|------|
| 健康状态 | 返回知识平台可达性与认证状态 |

### 场景5：说明卡——知识范围结构化描述

**用户场景**：角色发布前需补充说明卡，其中包含角色知识覆盖范围的结构化描述，供消费方在调用前了解角色的知识支撑水平。

**用户价值**：消费方看到"本角色绑定了3篇P1制度级依据、5篇P2操作指南、2篇P3参考资料，覆盖新品上市评估和渠道管理领域"比看到"绑定了10篇文档"更有调用决策支撑力。

**需要知识平台提供的接口能力**：与场景1相同——知识对象的结构化元数据，用于生成说明卡中的知识范围描述。

## 三、当前对接现状

### 前序约定基线

角色产品与知识平台的接口约定基于 `role-to-knowledge-integration-proposal.md`（v0.3，2026-05-14），定义了4项接口契约：

| 原约定接口 | 原约定端点（Open WebUI） | 原约定语义 |
|------------|------------------------|-----------|
| 接口1：知识对象列表查询 | `GET /api/v1/knowledge/` + `GET /api/v1/knowledge/{kb_id}/files` | 列出知识库和知识对象，返回 id、title、type、tags、summary |
| 接口2：知识内容获取 | `GET /api/v1/knowledge/{kb_id}/files/{file_id}/content` | 获取知识全文（Markdown），MVP 后置 |
| 接口3：知识检索（RAG） | `POST /api/chat/completions`（约定）→ 实际运行态 `POST /api/v1/retrieval/query/collection` | 基于知识范围检索相关片段 |
| 接口4：知识版本标识 | `GET /api/v1/version` | 返回 commit_hash 作为版本标识 |

原约定文档明确记载：**"首期联调直接对接 Open WebUI API（localhost:3000），待 Phase 6 Dify 就绪后可选迁移"**（§5.3）。角色产品代码当前全部对接 Open WebUI 端点。

### 角色产品实际调用

| 场景 | 实际调用接口 | 实际端点 |
|------|-------------|---------|
| 场景1：浏览绑定 | `list_knowledge_bases()` + `list_files()` | `GET /api/v1/knowledge/` + `GET /api/v1/knowledge/{kb_id}/files`（Open WebUI） |
| 场景2：知识检索 | `retrieve()` | `POST /api/v1/retrieval/query/collection`（Open WebUI） |
| 场景3：版本快照 | `get_version()` | `GET /api/v1/version`（Open WebUI） |
| 场景4：健康检查 | `health()` | `GET /api/v1/knowledge/`（Open WebUI，需认证） |
| 场景5：说明卡 | 同场景1 | 同场景1 |

### 知识平台新文档提到的接口

知识平台 `handoff-public-contract-interface.zh-CN.md`（2026-06-16）描述了 Knowledge Workbench 自身暴露的接口：

| 接口 | 方法 | 提供内容 |
|------|------|----------|
| `/api/status` | GET | 知识包状态（source_root、document_count、各 tier 文档数量） |
| `/api/manifest` | GET | 完整文档索引（relative_path、tier、doc_role、evidence_type、canonical、not_for、use_for、related_docs） |
| `/api/rebuild` | POST | 触发 manifest 重建 |
| `/api/ask` | POST | 整体问答：路由+检索+五段式回答合成 |
| `/api/evaluate` | POST | 运行验收场景评测 |

## 四、逐项对照：满足与缺口

| 场景 | 接口需求 | Open WebUI 当前是否满足 | Knowledge Workbench 是否可能满足 | 缺口 |
|------|---------|----------------------|-------------------------------|------|
| 场景1：浏览绑定 | 知识库列表 + 知识对象清单（含 tier/doc_role/evidence_type/canonical/use_for/not_for） | **部分满足**——有库列表和文件列表（id/title/type/tags/summary），但无 tier、doc_role、evidence_type、canonical、use_for、not_for | `/api/manifest` 提供了完整的结构化元数据（relative_path/tier/doc_role/evidence_type/canonical/not_for/use_for/related_docs） | **核心缺口**：知识对象缺乏权威层级和结构化元数据，创建者无法按权威层级选择绑定 |
| 场景2：知识检索 | RAG 检索含 tier/权威层级 | **部分满足**——有 RAG 检索（chunks + source + score），但检索结果不含 tier 信息 | `/api/ask` 含检索轨迹（retrieval_trace），但整体接口不可拆分；若拆分为 `/api/route` + `/api/retrieve` 则可能满足 | **核心缺口**：检索结果不含权威层级，角色无法在回答中区分制度级与参考级；**次要缺口**：边界检查用关键词匹配而非精确路由 |
| 场景3：版本快照 | 版本标识 | **满足**——`GET /api/v1/version` 返回 commit_hash | `/api/status` 可能替代，需确认是否返回不可变版本标识 | 无缺口（需确认 Knowledge Workbench 的 status 接口是否可替代） |
| 场景4：健康检查 | 可达性+认证 | **满足**——通过带认证的知识库列表接口验证 | `/api/status` 可能替代 | 无缺口（需确认） |
| 场景5：说明卡 | 知识范围结构化描述 | **部分满足**——同场景1缺口 | `/api/manifest` 可提供 | 同场景1缺口——无法生成"3篇P1+5篇P2+2篇P3"结构化描述 |

## 五、缺口汇总与需要知识平台回应的事项

### 核心缺口：知识结构化元数据

角色产品在场景1（浏览绑定）、场景2（知识检索）、场景5（说明卡）中，共同缺乏一个核心能力：**获取知识对象的结构化元数据（tier/doc_role/evidence_type/canonical/use_for/not_for），并将其贯穿到浏览、检索、说明卡全链路**。

从项目目标出发，这个缺口直接影响角色回答的可靠性——无法区分制度级依据与参考级材料，"可靠结论"的用户价值被削弱。

知识平台的 `/api/manifest` 已包含这些元数据，但当前角色产品未对接此接口。

### 需要知识平台确认与回应的事项

1. **现状确认**：角色产品上述对当前对接现状的理解是否准确？是否存在角色产品未感知的知识平台接口变更？

2. **Open WebUI 定位**：当前角色产品直接调用 Open WebUI 端点（localhost:3000）。知识平台文档显示 Knowledge Workbench 已有自己的接口层。请确认：今后角色产品应对接哪个服务？是继续对接 Open WebUI，还是转向 Knowledge Workbench 自身的接口？此变更是否涉及公共契约变更？

3. **核心缺口满足方案**：角色产品需要获取知识对象的结构化元数据（tier/doc_role/evidence_type 等），并在检索结果中携带 tier 信息。知识平台如何满足此需求？例如：
   - `/api/manifest` 是否可作为角色产品获取结构化元数据的正式接口？
   - 检索接口（当前 `/api/ask` 或拆分后的 `/api/retrieve`）是否能在返回结果中携带 tier 信息？

4. **接口拆分问题**：知识平台文档已识别 `/api/ask` 整体接口不可拆分的缺口。角色产品需要确认：角色产品是否需要只获取检索结果而自行合成回答（当前就是这样做的）？如果是，知识平台的接口拆分方案（方案A：拆分 route+retrieve+ask）是否是满足此需求的路径？

5. **次要缺口：路由分流**：角色产品当前的边界检查用关键词匹配，知识平台有更精确的路由能力（Q0-Q6）。角色产品是否需要对接路由接口？这取决于：当前关键词匹配在用户场景中是否足够，以及路由接口的引入是否会改变角色产品与知识平台的职责边界。

6. **版本标识与健康检查**：Knowledge Workbench 的 `/api/status` 是否可替代当前 Open WebUI 的 `/api/v1/version` 和健康检查功能？请确认返回字段与语义。

## 六、说明

1. 本评估仅梳理需求与缺口，不做方案结论，不自行决定接口对接路径变更。
2. 任何涉及公共契约变更的事项，须按组合层裁决流程处理，角色产品不单方面变更。
3. 角色产品的设计纲要原则（§1.1）明确记载：**角色产品只认接口契约语义，不对知识平台的内部实现做假设**。当前直接调用 Open WebUI 端点是首期联调的历史实现选择，不是契约层面的绑定。
4. 角色产品始终自行合成回答，不会委托知识平台的 `/api/ask` 代为合成——回答必须体现角色立场，而非仅展示知识事实。
