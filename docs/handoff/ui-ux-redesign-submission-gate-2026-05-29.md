# UI/UX 重构提交清单与审核门槛（2026-05-29）

> 项目：`virtual-actor`
> 用途：约束新工作方提交 UI/UE/UX 重构方案时的最小交付包
> 定位：`Handoff Only`，供规划方/审核方/工作方对齐，不替代版本真源

## 1. 总原则

本次重构先审设计包，再决定是否进入实现。

以下任一项缺失，都不应进入代码阶段：

1. 没有说明现状判断依据：真实运行态，或在无法访问时的截图参考包/代码/真源组合
2. 没有判断这次变更属于 `v0.4.x` 补强还是新版本重构
3. 没有覆盖关键页面和关键任务流
4. 只有视觉稿，没有交互、状态、文案和错误恢复说明
5. 没有说明如何回写 dossier 和测试材料

## 2. 现状参考材料使用原则

如工作方无法直接访问当前服务，可使用以下现状参考包辅助理解：

```text
/Users/baoyi/Documents/code_buddy/virtual-actor/docs/handoff/ui-ux-current-ui-reference-2026-05-29.md
```

但必须遵守以下原则：

1. 截图只用于理解现状问题，不是新设计的视觉或布局基线
2. 不得把“当前页面长这样”当成“后续只需优化现有页面”
3. 新方案仍应优先回到产品定位、用户任务、业务场景和真源设计来重做

## 3. 必交材料清单

| 项目 | 必须交付 | 最低要求 |
|---|---|---|
| A. 当前状态审计 | 是 | 优先覆盖真实运行态；如无法直接访问，则基于截图参考包 + 代码 + 真源给出问题清单，并标注判断限制；问题需标 P0/P1/P2 |
| B. 版本处理建议 | 是 | 明确建议 `v0.4.x` 或新版本，并说明为什么 |
| C. 信息架构方案 | 是 | 给出全局导航、页面关系、主路径和返回路径 |
| D. 视觉系统方案 | 是 | 给出商务风视觉方向、层级、组件和状态规范 |
| E. 关键页面线框图/原型 | 是 | 覆盖核心页面，不得只做 1-2 个页面 |
| F. 交互说明 | 是 | 说明主操作、确认弹窗、错误态、空态、加载态、不可操作态 |
| G. 文案与字段引导策略 | 是 | 解释如何降低表单理解成本和使用门槛 |
| H. 实现切分与回写计划 | 是 | 明确 P0/P1/P2、dossier 回写文件、测试更新范围 |

## 4. 页面覆盖门槛

以下页面必须被纳入审计和重构方案：

1. 登录页
2. 全局布局与导航
3. 角色资产列表页
4. 角色详情页
5. 角色创建/编辑页
6. 知识绑定浏览与选择体验
7. 测试台
8. 使用台
9. 资产市场
10. 运营看板

以下页面至少要给到策略，不可完全忽略：

1. 版本列表/版本详情
2. 统一空态、错误态、加载态、Toast、Modal
3. 长文本和结构化结果展示组件

## 5. 任务流覆盖门槛

方案必须明确覆盖以下任务流：

1. AI 协作创建角色
2. 手动创建/编辑角色
3. 知识绑定与回显
4. 角色测试与查看结果
5. 已发布角色正式使用
6. 资产市场发现与试用
7. 运营方查看看板并判断下一步动作

## 6. 重点审核问题

提交方案时，必须正面回答以下问题：

1. 当前体验里最影响用户独立完成任务的 5 个问题是什么？
2. 新方案如何降低角色配置的理解门槛，而不是只把表单做得更漂亮？
3. 新方案如何让“资产市场”更像业务发现入口，而不是角色列表的另一种皮肤？
4. 新方案如何让“测试台”和“使用台”在用户心智上更清晰地区分？
5. 新方案如何让“运营看板”更像经营和治理界面，而不是统计页？
6. 新方案如何保持中国企业商务风，而不是通用 SaaS 模板风？

## 7. 风格与体验硬要求

以下要求在方案中必须有明确回应：

1. 中文商务风，稳重、专业、清晰
2. 桌面优先，兼容平板宽度
3. 信息密度适中，不空、不挤、不娱乐化
4. 关键路径主按钮明确，返回/取消/确认顺序符合 human 习惯
5. 长文本可读、可滚动、可分段
6. 复杂结果必须结构化展示，不得回退成原始 JSON dump
7. 字段有解释、示例、推荐写法或模板辅助
8. AI 生成内容必须可识别、可确认、可继续编辑

## 8. 禁止事项

提交方案时，以下行为直接判定不通过：

1. 只提视觉美化，不提信息架构和交互重构
2. 只提组件库替换，不回答产品体验问题
3. 自行删除或弱化核心主链路
4. 自行修改 6 状态、boundary_status、版本快照或公共契约边界
5. 把 `prototype` 重新当成正式交付入口
6. 用 mock/fixture 设计虚假的使用路径
7. 把当前 `v0.4.0` 冻结设计直接覆写成新方案，而不先做版本判断和设计提案

## 9. 提交格式建议

建议按以下顺序提交：

1. 当前运行态审计
2. 版本建议
3. 设计原则
4. 信息架构
5. 关键页面方案
6. 关键任务流方案
7. 状态与组件规范
8. 实现切分与 dossier 回写计划

## 10. 审核通过标准

满足以下条件，才可以进入实现评审：

1. 新方案覆盖了关键页面和关键任务流
2. 新方案没有越界改动冻结业务语义和治理边界
3. 新方案能明显回答“为什么用户会更容易用”
4. 新方案能明显回答“为什么更符合中国企业商务场景”
5. 新方案给出了清晰的实现切分，不会把所有工作一次性混成大爆改
6. 新方案给出了 dossier 回写和测试更新计划
