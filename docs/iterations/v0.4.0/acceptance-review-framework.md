# v0.4.0 验收审核框架

> 版本：v0.4.0 | 日期：2026-05-27 | 用途：作为规划方 / AI 审核方 / 终审方评估设计、实现、测试、交付和验收声明的统一标尺
> 适用范围：`virtual-actor` 当前 v0.4 迭代
> 关系说明：本文件定义“如何审核是否成立”，不替代 `scope.md`、`design-delta.md`、`traceability.md` 对产品范围和行为的定义；如存在冲突，产品行为以真源设计文档为准，审核判定以本框架为准

---

## 1. 定位

本项目后续审核不只做代码工程检查，而是做三层验收审核：

1. **工程门槛**：代码、运行态、部署、自动化和证据真实性是否达标。
2. **产品验收**：是否按冻结设计实现，是否覆盖核心用户任务流，是否满足人能理解、能操作、能恢复的产品要求。
3. **价值证明**：是否已经证明本产品对治理方、业务用户、集成方和运营方产生了起初定义的用户价值与商业价值。

审核结论必须同时回答：

1. 这个提交是否“能跑”。
2. 这个提交是否“把设计做对了”。
3. 这个提交是否“证明了产品价值成立”。

---

## 2. 审核原则

1. **工程通过不等于验收通过。** 自动化测试、构建和部署通过，只说明具备进入更高层审核的资格。
2. **运行态高于仓库态。** 以当前实际验收环境运行的版本为准，不以“仓库代码看起来已修复”替代“当前服务已生效”。
3. **证据高于口头声明。** 所有“已支持”“已通过”“已集成”“real integration”都必须有真实证据。
4. **价值高于功能清单。** 审核不以“做了多少页面/接口”为核心，而以“是否证明了对应价值”为核心。
5. **冻结设计不得被实现阶段单方面降级。** 若实现与设计不一致，先视为偏差，再判断是否允许。
6. **mock / stub / fixture / 代码走查不能冒充真实证明。**

---

## 3. 三层审核结构

### 3.1 工程门槛

任一项不通过，直接退回，不进入更高层审核。

| 维度 | 通过标准 | 不通过判定 |
|---|---|---|
| 运行态与仓库态一致 | 当前验收服务运行的就是本次提交代码 | 运行服务仍是旧代码，或关键修复只存在于仓库未生效 |
| 主链路无阻塞性故障 | 核心主链路在真实运行态无 500 / 空响应 / 路由错配 / 关键状态错判 | 主链路任一关键步骤阻断 |
| 质量工具链通过 | 当前版本对应的自动化、构建、lint、guard 与交付文档一致 | 工具链结果与交付证据不一致，或结果虚报 |
| 部署入口可用 | 当前交付形态下的健康检查、登录、主入口、必要依赖可用 | 只在本地测试 client 或单测里通过，部署态不可用 |
| 证据真实性 | 明确区分自动化、人工冒烟、代码走查、真实集成 | 用代码走查/fixture 冒充真实运行或真实集成 |

### 3.2 产品验收

工程门槛通过后，再审“是否把设计做出来了”。

| 维度 | 通过标准 | 不通过判定 |
|---|---|---|
| 冻结设计一致性 | 实现与 `scope.md`、`design-delta.md`、任务流、线框图和验收点一致 | 自行降级范围、改弱关键路径、改变验收语义 |
| 核心任务流覆盖 | AI 创建、资产治理、测试发布、统一消费、运营证据等核心任务流可走通 | 页面存在但任务流断裂，或必须靠口头说明才能完成 |
| UI/UX 可用性 | 中文商务化表达、字段可理解、错误可恢复、长文本可读、操作顺序符合习惯 | 仍是“后台配置感”，用户难以理解、难以完成或容易误操作 |
| 集成体验产品化 | 试用、消费、来源、状态、追溯信息对用户和集成方可理解 | 只有接口，没有足够的产品化展示和行为闭环 |
| 边界与异常处理 | 非 success、越界、知识不足、系统失败等状态有清晰展示和处理建议 | 状态语义模糊、错误假装成功、边界不透明 |

### 3.3 价值证明

产品验收通过后，再审“是否已经证明该产品值得交付和继续推进”。

#### 3.3.1 角色资产化价值

| 项目 | 审核标准 |
|---|---|
| 价值定义 | 角色不是 prompt 配置，而是可治理、可发布、可追溯、可复用的企业资产 |
| 成立标准 | 治理属性、边界、知识来源、版本、发布信息、使用记录在真实链路中可查看、可追溯 |
| 必备证据 | 创建 -> 绑定知识 -> 测试 -> 发布 -> 版本详情 -> 知识追溯 -> 使用记录真实跑通 |
| 常见误判 | 只有字段和表结构，没有真实链路证据；只有设计文档，没有运行态闭合 |

#### 3.3.2 AI 创建提效价值

| 项目 | 审核标准 |
|---|---|
| 价值定义 | 用户可借助 AI 明显降低角色创建门槛，而不是继续靠复杂填表 |
| 成立标准 | 用户输入自然语言可生成草案，草案可编辑、可保存，不依赖额外解释完成创建 |
| 必备证据 | 真实前端人工冒烟记录，证明 AI 草案、字段说明、示例、模板选择和保存闭环可用 |
| 常见误判 | 只有 AI 接口返回 JSON，就宣称“AI 原生创建已成立” |

#### 3.3.3 业务发现与试用价值

| 项目 | 审核标准 |
|---|---|
| 价值定义 | 业务用户能发现合适角色、理解其价值，并直接试用 |
| 成立标准 | 资产市场能支撑业务发现，不只是后台列表；角色卡片和详情能说明适用场景、输出类型、边界和试用途径 |
| 必备证据 | 真实页面和任务流证明：发现 -> 理解 -> 试用 -> 返回结果 |
| 常见误判 | 只要有 published 列表就算“资产市场成立” |

#### 3.3.4 系统复用价值

| 项目 | 审核标准 |
|---|---|
| 价值定义 | 已发布角色可被决策产品、Dify 等外部系统稳定消费 |
| 成立标准 | 外部消费方真实调用统一消费能力，角色产品侧记录与对端日志能闭合 |
| 必备证据 | 决策产品真实消费证据 + Dify 代表场景证据 + 双方日志/usage record 对账 |
| 常见误判 | 单侧 API 自测通过，就宣称“系统复用价值成立” |

#### 3.3.5 结构化输出可消费价值

| 项目 | 审核标准 |
|---|---|
| 价值定义 | 输出不仅给人阅读，也能被系统可靠消费 |
| 成立标准 | `status = success` 时，`structured_result` 符合模板，`references` 满足治理底线 |
| 必备证据 | 自动化测试 + 真实运行样例，证明成功态不是空壳结构，不合规结果不会静默冒充成功 |
| 常见误判 | 有 `structured_result` 字段就算成立，哪怕内容是默认空对象 |

#### 3.3.6 运营闭环价值

| 项目 | 审核标准 |
|---|---|
| 价值定义 | 平台能基于创建、使用、风险和缺口信号持续优化资产供给 |
| 成立标准 | 看板和相关记录能反映创建来源、消费状态、风险分布和资产缺口线索 |
| 必备证据 | 真实使用后看板变化、无匹配/低使用/风险状态等信号可被观察和解释 |
| 常见误判 | 有几张数字卡片就算“运营能力成立” |

## 4. 审核输出规则

### 4.1 结论类型

| 结论 | 适用条件 | 允许表述 |
|---|---|---|
| 工程退回 | 工程门槛任一项失败 | 仅允许表述为“当前提交不可进入用户测试/终审验收” |
| 产品退回 | 工程通过，但冻结设计或任务流未成立 | 仅允许表述为“实现未满足设计验收要求” |
| 价值证明不足 | 工程与产品基本可用，但关键价值未被证明 | 仅允许表述为“可继续内部补齐，不得宣称商业价值闭环成立” |
| 可进入用户测试 | 工程门槛通过，核心产品路径成立，当前提交值得进入真实人工使用验证 | 允许申请用户测试，但不等于最终验收通过 |
| 可进入最终验收 | 工程、产品、价值三层均成立，且外部集成与交付证据闭合 | 可请求最终验收或 Accepted 判断 |

### 4.2 与 Formal Status 的关系

| Formal Status / 阶段 | 审核含义 |
|---|---|
| Draft | 设计或实现未到可对外自测声明阶段 |
| Self-Tested | 工作方已完成自测声明，但仍需按本框架接受独立复审 |
| User-Acceptance-Candidate | 仅当审核方确认“可进入用户测试”后，才可升级到此口径 |
| Accepted | 仅当审核方确认“可进入最终验收”，且用户/终审方完成接受后，才可升级 |

注意：

1. `Self-Tested` 不是豁免审核的状态。
2. 若当前运行态复核失败，已声明的 `Self-Tested` 视为证据失效，需要回退实际口径。
3. 对 v0.4 而言，`DD-14`、`DD-15` 未闭合时，不得宣称“v0.4 完整通过”。

---

## 5. v0.4 当前特别审核要求

以下要求来自当前 v0.4 冻结范围，不得在审核中被忽略：

1. **核心主链路固定**：`AI 创建 -> 资产治理 -> 测试发布 -> 统一消费 -> 运营证据`。
2. **DD-14 不降级**：决策产品真实集成证据闭合前，不得把版本表述为 v0.4 全量通过。
3. **DD-15 不可口头替代**：Dify 代表场景必须有真实消费和 usage record 对账证据。
4. **DD-16 不降级**：6 状态和 `boundary_status` 必须按冻结语义审核，不接受 4 状态降级。
5. **结构化输出必须审“可消费性”**：不能只审字段是否存在。
6. **UI/UX 必须审“人能否独立完成任务”**：不能只审页面是否有。

---

## 6. 审核记录最小格式

后续审核工作方提交物时，至少按以下结构输出：

1. **发现优先**：先列问题，再给总结。
2. **按层归类**：工程门槛 / 产品验收 / 价值证明。
3. **给出判定**：说明该问题属于设计缺口、实现缺口、运行态缺口还是证据缺口。
4. **给出结论**：工程退回 / 产品退回 / 价值证明不足 / 可进入用户测试 / 可进入最终验收。

推荐格式：

| 编号 | 层级 | 问题 | 缺口类型 | 影响 | 结论 |
|---|---|---|---|---|---|
| R-01 | 工程门槛 | 当前运行态仍是旧部署 | 运行态缺口 | 主链路证据失效 | 工程退回 |

---

## 7. 使用边界

1. 本框架用于审核，不授权实现方自行改变产品范围、验收标准或口径。
2. 若审核中发现当前设计本身不能支撑价值判断，应回到 dossier 做设计收口，而不是在实现侧默认修改。
3. 本框架可作为后续版本的基础，但新版本必须显式确认哪些价值项沿用、哪些新增、哪些调整。
