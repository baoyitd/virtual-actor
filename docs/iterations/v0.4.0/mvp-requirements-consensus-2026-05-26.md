## 0. 文档使用规则

1. 本文是需求业务梳理稿，不是实现方案。
2. 正文记录当前已形成共识、属于 MVP 产品设计范围的内容。
3. 附录记录超出当前正文、仍需评估或可作为后续增强的建议。
4. 工作方收到后，应基于正文评估设计、接口、迭代切分和实现风险，并对附录建议给出采纳、延期或替代方案。
5. 产品设计范围和实现批次必须分开。实现复杂度可以影响版本切分，但不应反向削弱产品本质目标。

## 1. 固定原则

1. 先判断“什么是对的”，再判断“如何实现”。
2. 不用执行困难、工程工作量或短期交付压力倒推改变产品本质。
3. 用户提出的判断不默认视为正确，规划方必须结合市场、业务场景、商业价值、技术趋势和项目事实进行挑战与完善。
4. 关键判断、核心原则、待决问题和最终定论必须落档，后续完整传递给工作方。
5. MVP 设计范围必须保持核心链路完整性、表现力和商业说服力。

## 2. 产品定位

当前产品定位：

```text
企业数字角色资产运营平台
```

完整表达：

```text
帮助集团企业把专家经验、岗位职责、业务知识、能力边界和 AI 能力沉淀为可治理、可发布、可复用、可观测、可集成的数字角色资产，并让这些角色逐步参与业务问答、决策支持、产物生成和受控执行。
```

定位含义：

1. 角色不是 prompt，也不只是 chatbot。
2. 角色是一种企业资产，应有所有者、知识来源、能力边界、版本、质量证据、使用记录和分发方式。
3. 平台价值不只在“创建角色”，更在“让角色被组织持续使用、治理和优化”。

## 3. 目标问题

本产品针对集团企业 AI 转型中的以下问题：

1. 专家能力不可复制：专家经验散在个人、文档和群聊中，人员变化后难以延续。
2. AI 能力不可治理：企业内部可能有大量 bot、prompt、知识库问答入口，但缺少统一资产目录、所有者、版本和生命周期。
3. 知识与角色脱节：知识平台解决“文档可检索”，但不解决“哪个角色基于哪些知识、以什么边界回答”。
4. 质量不可追溯：角色什么时候测试、谁确认、基于什么知识版本发布、效果如何，缺少证据链。
5. 复用方式不足：角色发布后如果只能在管理台使用，无法成为组织级生产力。
6. 执行边界不清：角色从问答走向产物生成或执行动作时，需要能力分层、权限边界和审计机制。

## 4. 用户与客户分层

买单人和商业用户不能简单等同。

狭义预算方通常包括：

1. 集团 AI / 数字化部门。
2. IT 平台团队。
3. 知识运营 / 数据治理团队。
4. 合规、风控、审计等治理部门。

商业用户范围包括：

1. 高管决策层。
2. 数字化 / AI 平台团队。
3. 业务部门负责人。
4. 业务部门一线人员。
5. 业务系统或 Agent 搭建者。
6. 合规、风控、审计等利益相关方。

业务部门参与成熟度分两类：

1. 运营管理型参与：业务部门直接创建、维护、发布和运营自己的角色资产。前期通常由数字化部门或知识运营团队代运营，后期逐步下沉给业务部门。
2. 消费集成型参与：业务部门不一定运营角色资产，但会在自己的 Agent、问答系统、工作流或信息系统中消费角色资产。

因此，产品必须同时解决：

1. 角色资产如何被治理方管理。
2. 角色资产如何被业务方消费。
3. 角色资产如何在使用后产生证据并反哺治理。

## 5. MVP 核心链路

v0.4 MVP 设计范围应覆盖：

```text
AI 创建 -> 资产治理 -> 测试发布 -> 统一消费 -> 运营证据
```

这条链路是产品成立的核心，不应因为实现复杂而在设计层面缩减。

## 6. AI 原生原则

本产品应按 AI 原生产品形态设计，而不是“传统信息化系统 + AI 辅助按钮”。

AI 原生不等于 AI 全自动。集团企业语境下必须坚持：

1. AI 生成草案，但人确认后才落库。
2. AI 提供测试与运营建议，但不能绕过发布门禁。
3. AI 可以推荐角色或改进方向，但不能擅自改变已发布资产。
4. A3 执行动作必须经过跨项目裁决、权限设计和审计设计。

当前定义：

```text
AI 优先参与流程，人承担确认、发布和责任边界。
```

## 7. MVP 正文能力

### 7.1 AI 原生角色创建

产品需求：

1. 用户用自然语言描述角色需求。
2. AI 生成结构化角色草案。
3. 用户确认或编辑后保存为 draft。
4. AI 创建与手动创建并存。

AI 创建不应只是“一个字段建议按钮”，而应服务角色创建主路径。

### 7.2 角色资产治理

角色资产应具备：

1. 治理属性：分类、所有者、维护人、业务域、可见范围。
2. 知识边界。
3. 能力边界。
4. 能力层级。
5. 知识绑定。
6. 版本与发布状态。
7. 质量和使用证据。

### 7.3 资产目录

资产目录是基础项，应设计为企业内部角色资产市场，而不是普通管理列表。

资产目录应支持：

1. 已发布角色发现。
2. 角色适用场景说明。
3. 所有者、业务域、知识边界、能力边界展示。
4. 版本、质量状态、使用情况展示。
5. 直接试用入口。
6. 调用 / 集成入口说明。

资产目录的产品原则：

1. 默认面向业务发现，治理信息作为可信证据嵌入。
2. 应显式按“企业内部角色资产市场”设计，而不是后台列表。
3. 首屏应展示轻量接入信息，例如可调用标识、业务输出 Schema、调用说明入口。
4. 业务发现视图默认只展示 published 角色；治理方可切换查看 draft、test、archived。
5. 业务输出 Schema 应作为目录筛选项。

资产市场不应只有列表形态。

MVP 设计应支持更具表现力和 AI 原生感的资产发现方式：

1. 场景入口：按业务场景组织角色，例如决策支持、风险分析、制度合规、专业审查。
2. 推荐入口：用户输入业务问题或目标后，AI 推荐合适角色。
3. 资产卡片：用业务能力、可信证据、使用入口和接入方式表达角色价值。
4. 角色详情资产包：展示治理属性、知识边界、能力边界、业务输出 Schema、当前版本、质量记录、使用记录、调用说明。
5. 列表 / 表格视图：作为治理方的管理视图，而不是唯一入口。

因此，资产市场应至少包含三种视图：

1. 业务发现视图：面向业务用户，按场景、推荐和搜索发现角色。
2. 资产治理视图：面向运营 / 治理方，支持筛选、状态管理、质量和使用指标。
3. 接入视图：面向 Agent / 业务系统搭建者，展示 output_type、调用说明和版本信息。

资产市场 AI 推荐入口已确认：

1. 本质是“业务任务到角色资产的匹配器”，不是直接回答用户问题的聊天助手。
2. 用户用自然语言描述业务任务、目标或场景后，系统推荐合适的已发布角色资产。
3. 推荐对象默认只应是可消费的 published 角色资产；草稿、测试中或归档角色不面向业务消费推荐。
4. 每个推荐结果必须可解释，至少说明推荐理由、适用问题、业务输出类型、知识范围、质量状态、版本信息和可用消费入口。
5. 推荐结果应连接真实消费路径，例如直接试用、Dify 接入说明或决策产品消费路径；不能停留在静态展示。
6. 如果没有合适角色，系统不应硬推荐，应提示当前缺口，并形成角色需求或资产运营信号。
7. `v0.4` 不要求复杂个性化推荐，不基于用户画像、历史行为或协同过滤；先实现业务意图到已发布角色资产的解释型推荐。
8. 推荐失败、频繁无匹配和高频搜索词应作为资产运营线索，供运营看板或需求池使用。

### 7.4 统一角色消费能力

统一角色消费能力是平台底座。

不同消费方不应各自拥有割裂链路。资产目录、开放 Agent 平台、决策产品应复用统一角色消费能力。

统一消费链路：

```text
已发布角色资产
-> 稳定角色版本
-> 明确输入
-> 角色运行 / 问答 / 建议
-> 结构化输出
-> 使用记录
-> 版本与知识追溯
```

### 7.5 统一消费输入模型

输入模型：

```text
role_id 必填
role_version_id 可选
```

最小输入字段：

1. `role_id`：必填，角色资产 ID。
2. `role_version_id`：可选，指定已发布角色版本；不填时使用当前 published 版本。
3. `query`：必填，用户问题或业务请求。
4. `context`：可选，业务上下文。
5. `output_type`：可选，不填时使用角色版本配置的业务输出 Schema。
6. `caller_type`：建议记录，例如 `human`、`agent_platform`、`decision_product`、`system`。
7. `caller_id`：建议记录，调用方标识。

版本选择规则：

1. 只传 `role_id` 时，系统使用该角色当前 published 版本，并在输出中明确实际使用的 `role_version_id`。
2. 同时传 `role_id` 和 `role_version_id` 时，系统校验版本归属和状态，严格使用指定版本。
3. `role_version_id` 不属于 `role_id` 时，拒绝调用。
4. 指定版本已归档或不可消费时，明确报错，不自动 fallback。

### 7.6 统一消费输出模型

输出采用：

```text
固定治理外壳 + 可配置业务 Schema
```

固定治理外壳：

1. `answer`：给人阅读的自然语言回答。
2. `role_id`：角色资产 ID。
3. `role_version_id`：本次消费绑定的角色版本。
4. `usage_record_id`：本次使用记录。
5. `created_at`：调用时间。
6. `sources`：知识来源 / 引用来源。
7. `boundary_status`：知识边界、能力边界是否触达或越界。
8. `output_type`：输出类型。
9. `structured_result`：按角色业务 Schema 生成的结构化结果。

### 7.7 业务输出 Schema

角色设置中应有配置项：

```text
业务输出 Schema / Output Schema
```

用途：

1. 定义该角色被消费时，`structured_result` 应该按什么结构输出。
2. 支持不同类型角色返回不同业务结构。
3. 避免通用模板对角色多样性造成格式阉割或语义错位。

业务输出 Schema 是角色资产的一部分，应进入版本快照。已发布角色的 Schema 不应直接覆写，编辑应产生新版本。

已确认产品规则：

1. 可发布、可消费的角色资产必须配置业务输出类型和业务输出结构；草稿和内部测试阶段可以不完整，但进入资产市场、Dify 或决策产品消费前必须补齐。
2. 业务输出配置面向业务语言，而不是面向普通用户暴露技术 Schema；用户看到的是输出格式、字段含义、示例和适用场景。
3. AI 应在角色创建和编辑时，根据角色描述、知识范围、适用场景和能力边界推荐输出类型与字段结构。
4. 系统应提供首批业务模板，同时允许自定义字段，避免固定模板阉割不同角色资产的表达能力。
5. 自定义字段必须受治理，至少需要中文名称、业务含义、是否必填、示例和适用场景；具体技术表达方式由工作方在设计阶段提出。
6. 发布后的业务输出结构属于版本快照内容，后续修改应形成新草稿或新版本，不能直接覆写已发布版本。

首批业务输出 Schema 模板：

1. `decision_advice`：决策建议。
2. `risk_analysis`：风险分析。
3. `policy_explanation`：制度解释。
4. `review_findings`：专业审查。

不作为首批核心模板：

1. 会议纪要。
2. 文案创作。
3. 通用问答。

### 7.8 三类消费形态

MVP 应考虑 3 类消费形态：

1. 角色资产目录：人类发现、理解和试用角色资产。
2. 开放 Agent 平台消费：以 Dify 作为 MVP 代表平台，通过统一消费能力调用角色资产。
3. 决策产品集成：产品组合内的受治理消费方，基于统一消费能力消费角色资产。

三者不是同一层：

1. 角色资产目录是资产发现层。
2. 开放 Agent 平台是外部分发 / 生态接入层。
3. 决策产品是产品组合内受治理业务消费层。

但三者应共用统一消费能力。

决策产品是 MVP 的核心消费方之一，必须在本版本完成集成。

集成要求：

1. 决策产品应通过统一角色消费能力消费已发布角色资产。
2. 至少支持 `decision_advice` 类型的决策消费场景。
3. 调用结果必须包含固定治理外壳、结构化 `structured_result`、`role_id`、`role_version_id`、`usage_record_id`、`sources` 和 `status`。
4. 决策产品消费应保留版本冻结、知识追溯和使用记录。
5. 正式集成验收涉及上位治理和决策产品协同确认，不由角色产品单方面声明完成。
6. 如集成过程中发现公共契约、跨项目依赖、读写边界或版本规则需要调整，必须按上位治理规则上提裁决。

决策产品集成验收边界已确认：

1. 决策产品集成不是“能调到接口”，而是在真实决策业务链路中消费已发布角色资产，并把角色建议、依据、版本和责任边界纳入决策过程。
2. 角色产品提供可治理的角色资产能力，不替决策产品完成最终决策；决策产品负责决策事项、流程、用户操作、决策记录和最终责任。
3. 最小真实场景链应覆盖：决策产品中的决策事项 -> 调用已发布角色资产 -> 角色产品按 published 版本生成 `decision_advice` -> 返回结构化建议、来源、状态和版本信息 -> 决策产品展示或记录建议 -> 角色产品生成使用记录 -> 双方证据可互相对上。
4. 该链路必须发生在决策产品消费语境中，不能仅以角色产品测试台或 API 自测替代。
5. 角色产品侧验收证据应证明：只消费 published 角色版本、支持 `role_id` 必填和 `role_version_id` 可选、返回 `decision_advice`、返回角色版本 / 知识来源 / 状态 / 使用记录、非成功状态不假装成功。
6. 决策产品侧验收证据应证明：有真实决策事项或决策场景调用角色资产、传入足够业务上下文、展示或保存角色建议、保留角色版本 / 使用记录 / 来源等追溯信息、能处理非成功状态。
7. 只有双方证据闭合，并且不存在未裁决公共契约、读写边界或版本规则问题，才能声明决策产品集成通过。
8. 上述字段和能力是本轮集成需求和验收证据要求，不单方面表述为已冻结跨项目公共契约。

开放 Agent 平台消费的 MVP 正文要求：

1. Dify 是本轮开放 Agent 平台消费的代表对象。
2. 业务目标不是提前裁决 HTTP、OpenAPI、插件、MCP 或其他技术形态，而是证明开放 Agent 平台能够消费已发布角色资产。
3. 最低可用证明应覆盖：Dify 发起调用、角色资产按当前 published 版本响应、返回固定治理外壳和业务输出、生成使用记录、记录调用方为开放 Agent 平台、可追溯到角色版本和知识来源。
4. 具体接入方式、配置样例和协议形态由工作方在设计与实现阶段提出方案，经规划方复审后纳入实现。
5. 当前需求阶段不固定某一个具体业务场景为唯一验收场景；只要求工作方选择一个能体现企业业务价值的代表场景，并证明该场景不是单纯聊天，而是对角色资产的真实消费。
6. 风险分析类场景可作为推荐参考实例，用于具象化标准，但不是固定实现承诺；工作方可以沿用，也可以替换为同等证明力的业务场景。
7. 无论采用哪个场景，都必须证明：有明确业务任务、调用的是已发布角色资产、能体现版本 / 知识来源 / 边界 / 输出类型等治理价值，并生成外部 Agent 平台消费记录。

### 7.9 角色资产运营看板

看板不是列表增强，而是运营闭环的关键组成。

设计目标应是“角色资产运营看板”，覆盖：

1. 资产总览：角色数量、发布数量、草稿数量、归档数量。
2. 创建运营：AI 草案接受率、人工修改率、草稿沉睡资产。
3. 质量运营：测试通过率、最近评分、失败原因分布。
4. 使用运营：使用次数、最近使用、低使用资产、高价值资产。
5. 风险运营：知识版本过期、边界缺失、长期未维护角色。

### 7.10 版本与证据

MVP 必须坚持：

1. 已发布角色版本不可直接覆写。
2. 消费记录保存当时使用的 `role_version_id`。
3. 业务输出 Schema 进入版本快照。
4. 使用记录保存输入、输出、调用方、时间、版本和来源。
5. 角色消费必须可追溯。

## 9. 统一消费结果状态

### 9.1 设计原则

统一消费结果状态用于描述一次角色资产调用的业务结论，不只是技术状态码。

它要回答：

1. 本次调用是否成功。
2. 如果未成功，是输入不足、知识不足、边界阻断、系统失败，还是无法分类。
3. 结果是否可以被资产目录、开放 Agent 平台、决策产品继续使用。
4. 本次记录应该如何进入运营看板。

状态设计原则：

1. 状态数量要控制，避免过度复杂。
2. 每个状态必须有明确命中规则。
3. 能明确规则的状态应尽量纳入正文，而不是全部丢给兜底。
4. 必须有兜底状态，处理无法稳定归类的情况。
5. 本轮状态数量固定为 6 个，不再扩展；后续新增状态需要有明确业务规则和消费方处理方式。
6. 每次角色消费必须返回 `status` 和 `status_reason`。
7. 非 `success` 结果不应被消费方当作正常业务结论继续流转。
8. `undefined` 允许作为兜底状态，但应作为运营复盘信号，不能被长期大量使用。

### 9.2 MVP 状态清单

MVP 正文纳入 6 个状态：

1. `success`
2. `insufficient_context`
3. `insufficient_knowledge`
4. `boundary_blocked`
5. `system_failed`
6. `undefined`

### 9.3 状态规则表

| 状态 | 中文名 | 命中规则 | 消费方处理 | 运营含义 |
|---|---|---|---|---|
| `success` | 成功 | 角色在知识边界和能力边界内完成回答或结构化输出 | 可展示、可继续流程、可进入正式记录 | 正常使用 |
| `insufficient_context` | 上下文不足 | 用户请求属于角色范围，但输入信息不足以给出可靠结果 | 提示补充信息，或由上游 Agent 继续收集上下文 | 输入质量问题，不归因于角色质量 |
| `insufficient_knowledge` | 知识不足 | 请求属于角色能力范围，但绑定知识或当前知识版本无法支撑可靠回答 | 不应作为正式结论，可提示补充知识或换角色 | 知识缺口、知识过期或绑定不足 |
| `boundary_blocked` | 边界阻断 | 请求超出角色知识边界、能力边界或能力层级，例如 A1 角色被要求执行动作 | 停止使用该角色结果，转人工、换角色或进入更高能力流程 | 边界治理生效，不应简单视为失败 |
| `system_failed` | 系统失败 | LLM、知识平台、数据库、网络、超时等系统性异常导致无法完成调用 | 可重试或提示系统错误 | 系统稳定性问题，不归因于角色质量 |
| `undefined` | 未定义 | 无法稳定归类到上述状态，或规则不足以判断 | 谨慎展示，标记为需人工复核 | 状态规则缺口，需产品和运营复盘 |

### 9.4 输出要求

消费输出应包含：

1. `status`
2. `status_reason`
3. `boundary_status`
4. 固定治理外壳字段
5. `structured_result`

示例：

```json
{
  "status": "boundary_blocked",
  "status_reason": "该请求要求角色执行付款动作，超出 A1 问答建议能力层级",
  "answer": "该请求超出本角色能力边界，无法执行付款动作。",
  "structured_result": {},
  "role_id": "...",
  "role_version_id": "...",
  "usage_record_id": "...",
  "sources": [],
  "boundary_status": {
    "knowledge_boundary": "not_applicable",
    "capability_boundary": "out_of_scope"
  }
}
```
