# v0.4.0 工作方反馈规划方回应

> 日期：2026-05-26
> 对象：`worker-feedback-2026-05-26.md`
> 状态：规划方回应，待终审方确认后进入 dossier 回写

## 1. 总体结论

工作方反馈有效，已准确识别当前共识稿与原 dossier 之间的主要差距。

规划方采纳以下判断：

1. `v0.4` 产品方向已经从原“角色资产化与使用入口”升级为“企业数字角色资产运营平台”，原 dossier 必须回写。
2. 原 `DD-04` “消费侧 API 只产出文档、不改变接口”已经不再支撑当前 MVP 主链路。
3. 统一消费 API 是 `AI 创建 -> 资产治理 -> 测试发布 -> 统一消费 -> 运营证据` 的必要连接点。
4. 设计视图与实现批次必须分开；可以分批实现，但不能把设计目标和最终验收标准降级。
5. 工作方可继续提出质疑和拆分建议，但不得自行把已确认的产品本质降级为较弱交付。

## 2. P0 裁决建议

### 2.1 DD-14 交付范围

裁决建议：坚持共识稿，不接受把 `DD-14` 降级为“消费能力就绪、决策产品真实集成延后后再说”。

理由：

1. 决策产品是当前产品组合内的核心消费方，不是可选展示样例。
2. 如果 `v0.4` 只完成角色产品侧消费能力，而没有决策产品消费语境中的真实链路证据，则不能证明“角色资产进入产品组合业务链路”。
3. 工作方提出的外部依赖风险成立，但这是协同和验收风险，不应反向修改产品本质。

允许的实现切分：

1. 可以先做角色产品侧统一消费能力、结构化输出、使用记录和证据链。
2. 可以把“决策产品真实集成”作为 `v0.4` 内的后置里程碑或 `v0.4.x` 子批次执行。
3. 在决策产品真实集成证据闭合前，不得声明 `v0.4` 的 `DD-14` 通过，不得把版本升级为完整可验收状态。
4. 如果决策产品团队无法在本轮配合，应记录为外部阻塞，而不是把 `DD-14` 从 MVP 验收范围移出。

终审方需要协调：

1. 决策产品团队配合窗口。
2. 双方对接负责人。
3. 最小真实决策场景和双方证据格式。

### 2.2 Dossier 回写与统一消费 API

裁决建议：批准本地 dossier 回写，将原“消费侧 API 不改变”修订为“新增统一消费 API，作为本轮角色产品统一消费能力的内部候选接口和集成验证接口”。

边界：

1. 该回写是角色产品本地 dossier 修订，不等同于冻结跨项目公共契约。
2. 统一消费 API 可以用于资产目录、Dify 代表验证和决策产品联调，但在上位治理确认前不得表述为长期冻结公共契约。
3. 如果决策产品要求稳定依赖该 API 的输入、输出、状态字段或版本规则，则必须上提公共契约裁决。
4. `portfolio-sync.md` 后续应明确 `Interface Delta` 为候选或待裁决状态，不得写成 Accepted public contract。

工作方需回写：

1. `scope.md`：移除“消费侧 API 不改变”的旧约束，新增统一消费 API 为 MVP 主链路必要能力。
2. `design-delta.md`：补 `DD-04` 从纯文档升级为统一消费 API 设计与实现，并明确公共契约边界。
3. `traceability.md`：补统一消费 API 对 `DD-03`、`DD-11`、`DD-14`、`DD-15`、`DD-16` 的支撑关系。
4. `delivery/test-plan-v0.4.md` / `delivery/test-cases-v0.4.md`：补统一消费 API、Dify、决策产品和 6 状态验收证据。

## 3. 其他关键确认

### 3.1 DD-10 范围扩展

批准将 `DD-10` 扩展为：AI 创建角色草案时同时推荐 `output_type` 和 `applicable_scenarios`。

理由：

1. 否则 AI 创建只生成角色基础信息，用户仍需手工补结构化输出和适用场景，AI 原生体验断裂。
2. `output_type` 是 `DD-11/DD-12` 的前置。
3. `applicable_scenarios` 是资产市场 AI 推荐的前置。

工作方需补完整规格：AI 生成范围、用户可编辑范围、保存逻辑、默认值、失败回退和版本快照影响。

### 3.2 DD-16 交付范围

不接受把 `DD-16` 在 `v0.4` 降级为 4 状态。

裁决口径：

1. `v0.4` 统一消费结果状态固定为 6 个。
2. 每次消费必须返回 `status` 和 `status_reason`。
3. `insufficient_context` 和 `insufficient_knowledge` 可以采用保守判定策略，但不能从交付语义中移除。
4. 如某些复杂情况无法稳定判断，应进入 `undefined`，但验收用例必须覆盖 6 状态的基本命中路径。

### 3.3 业务输出 Schema

采纳工作方关于 `DD-11/DD-12` 的风险判断。

进入实现前必须补齐 4 个模板的完整字段定义：字段名、中文名称、业务含义、是否必填、示例、适用场景、与 `structured_result` 的关系。

### 3.4 资产市场实现切分

采纳“完整设计视图 + 分批实现”的建议，但分批不得改变产品方向。

`v0.4` 至少应交付：

1. 业务发现视图的最小形态。
2. AI 推荐入口的最小形态。
3. 资产卡片和角色详情资产包的关键治理信息。
4. 从推荐结果进入真实消费路径的能力。

治理视图和接入视图可以分阶段细化，但不能从设计蓝图删除。

### 3.5 UI/UX 原型产出

批准将 UI/UX 原型加入进入实现前的 P0 材料清单。

理由：

1. `DD-10`、`DD-12`、`DD-13`、`DD-03`、`DD-09` 均强依赖用户界面和交互流程。
2. 如果产品设计阶段只有字段、接口和规则规格，开发方会自行决定关键交互，产品体验会失控。
3. `v0.4` 是“企业数字角色资产运营平台”的 MVP，必须先让终审方看到关键产品体感，再进入实现。

产出要求：

1. 不要求高保真视觉稿。
2. 必须提供关键交互线框图或等价低保真原型。
3. 必须覆盖关键页面、关键流程、状态切换、异常/空状态和主要确认点。
4. 必须标注哪些交互属于 `v0.4` 必交，哪些属于 `v0.4.x` 后续增强。
5. UI/UX 原型需经规划方和终审方确认后，工作方才能进入相关页面实现。

最低覆盖场景：

1. AI 协作创建主流程：意图输入 -> 草案展示 -> 编辑确认 -> 保存。
2. 业务输出配置界面：模板选择 -> AI 推荐 -> 字段确认。
3. 资产市场业务发现视图：场景入口 -> AI 推荐 -> 资产卡片 -> 试用 / 消费。
4. 使用台 / 消费结果展示：固定治理外壳、`structured_result`、`status`、`boundary_status` 的可视化。
5. 运营看板：资产总览、创建运营、质量运营、使用运营、风险运营五类信息的最小展示方案。

### 3.6 设计期强化与实现防漂移

鉴于 `v0.3` 交付后仍出现多轮显而易见的流程问题、操作问题和不符合 human 使用习惯的交互问题，`v0.4` 必须强化设计期并约束实现阶段漂移。

`v0.4` 不允许“文档 / API 先行、UI 后补”。进入实现前必须完成：

1. 用户任务流。
2. 低保真原型或关键交互线框图。
3. 场景走查。
4. UI/UX 验收点。
5. 设计冻结记录。

任务流要求：

1. 每个核心场景必须说明用户是谁、任务是什么、从哪里进入、每一步看到什么、填什么、如何成功、如何失败、如何返回或撤销。
2. 至少覆盖 AI 协作创建、资产市场发现、角色消费、业务输出配置、运营看板、Dify 消费证明、决策产品消费证据。

原型要求：

1. 不能只提交静态页面截图。
2. 必须标注入口、主路径、空状态、错误状态、加载状态、不可操作状态、确认弹窗和返回路径。
3. 必须能支撑终审方按真实用户任务进行场景走查。

实现约束：

1. 设计冻结后，工作方不得自行改变关键交互、信息架构、流程顺序或验收语义。
2. 如实现阶段发现原设计不可行，必须提交设计偏差说明，包含原设计、实际限制、替代方案、影响范围和验收影响。
3. 设计偏差需经规划方和终审方确认后再进入实现，不能边做边改成另一个产品。

交付前自测要求：

1. 工作方交付终审方测试前，必须先完成人工冒烟。
2. 人工冒烟必须覆盖高风险核心用户路径，并记录操作人、时间、环境、步骤、预期、实际和结果。
3. 工作方必须提交实现与设计的偏差清单；没有偏差清单视为未完成设计一致性检查。

Human 使用习惯专项检查：

1. 文案是否业务化。
2. 字段是否有解释和示例。
3. 按钮顺序是否符合用户操作习惯。
4. 危险操作是否有确认。
5. 错误提示是否可理解、可恢复。
6. 长文本是否可读、可滚动。
7. 多数据列表是否可搜索、筛选或分组。
8. 保存、发布、返回、取消等状态是否明确。

## 6. 结论

本轮产品方向不降级。

允许分批实现，但 `v0.4` 的最终验收仍必须证明主链路成立：

```text
AI 创建 -> 资产治理 -> 测试发布 -> 统一消费 -> 运营证据
```

其中，统一消费 API 是必要能力；Dify 是开放 Agent 平台最低可用证明；决策产品是真实产品组合消费证明。缺少任一关键证据时，不得声明 `v0.4` 完整通过。
