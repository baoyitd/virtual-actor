# v0.4.0 产品定位讨论记录

> 日期：2026-05-26
> 状态：讨论中，非 Scope 冻结文件
> 用途：记录终审方与规划方关于产品未来走向、市场定位、商业价值和迭代原则的关键讨论，后续完整传递给工作方，避免信息 gap。

## 1. 固定协作原则

1. 规划方 / AI 审核方必须以 partner 方式参与讨论，不做单纯执行者。
2. 用户提出的判断不默认视为正确结论，必须结合市场、行业、用户场景、商业价值、技术趋势和本项目事实进行验证。
3. 如发现方向存在弱假设、过度包装、商业价值不足或实现越界，必须直接指出，并给出替代建议。
4. 关键判断、核心原则、待决问题和最终定论必须落档，后续传递给工作方，避免口头讨论丢失。
5. 讨论阶段不等于 Scope 冻结；只有经终审确认并同步更新 dossier 后，才可进入实现。
6. 产品判断必须先回答“什么是对的”，再回答“如何实现”。不能用执行困难、工程工作量或短期交付压力倒推改变事情的本质目标。
7. 执行约束可以影响版本节奏、拆分方式和验收边界，但不能替代产品定位、平台逻辑和商业价值判断。
8. 设计范围和单次实现范围必须区分。MVP 的产品设计范围要保证核心链路完整性、表现力和商业说服力；`v0.4`、`v0.4.x`、`v0.5` 只是实现切分方式，不能随意在设计层面缩减目标。

## 2. 当前定位假设

工作定位：

```text
企业数字角色资产运营平台
```

更完整的表达：

```text
帮助集团企业把专家经验、岗位职责、业务知识、能力边界和 AI 能力沉淀为可治理、可发布、可复用、可观测、可集成的数字角色资产，并让这些角色逐步参与业务问答、决策支持、产物生成和受控执行。
```

该定位强调：

1. 角色不是 prompt，也不只是 chatbot。
2. 角色是一种企业资产，必须有所有者、知识来源、能力边界、版本、质量证据、使用记录和分发方式。
3. 平台价值不只在“创建角色”，更在“让角色被组织持续使用、治理和优化”。

## 3. BP 逻辑讨论框架

### 3.1 AI 转型中的问题

待讨论和验证的核心假设：

1. 企业不缺大模型入口，缺“可进入业务流程的 AI 资产”。
2. 大量 AI 试点停在 demo 或个人效率工具阶段，难以形成组织级复用和可衡量价值。
3. AI 转型真正困难的部分不是调用模型，而是：
   - 业务知识如何组织
   - 专家经验如何资产化
   - AI 输出如何被治理
   - 责任边界如何定义
   - 角色如何进入业务流程
   - 运行效果如何被持续评估

### 3.2 本产品试图解决的痛点

初步痛点清单：

1. 专家能力不可复制：专家经验散在个人脑中、文档中、群聊中，人员变化后难以延续。
2. AI 能力不可治理：企业内部可能有很多 bot、prompt、知识库问答入口，但缺少统一资产目录、所有者和生命周期。
3. 知识与角色脱节：知识平台解决“文档可检索”，但未必解决“哪个角色基于哪些知识、以什么边界回答”。
4. 质量不可追溯：角色什么时候测试过、谁确认过、基于什么知识版本发布、效果如何，缺少证据链。
5. 复用方式不足：角色发布后如果只能在管理台使用，无法成为组织级生产力。
6. 执行边界不清：角色从问答走向产物生成或执行动作时，需要能力分层、权限边界和审计机制。

### 3.3 市面方案的利弊

初步分类：

1. Agent / Bot Builder
   - 优点：创建快、演示强、集成模型和工具能力。
   - 局限：往往以单个 bot/app/agent 为中心，企业资产治理、版本追溯、知识版本绑定、发布门禁和运营证据通常不是核心。

2. 知识库 / RAG 平台
   - 优点：知识接入、检索、内容管理能力强。
   - 局限：解决“知识可问”，不一定解决“谁以什么角色、什么边界、什么版本使用知识”。

3. 企业 Copilot / 办公套件 AI
   - 优点：渠道强，贴近日常办公流。
   - 局限：企业自定义角色资产的治理深度、跨业务系统沉淀和资产生命周期可能受平台边界限制。

4. 工作流 / 自动化平台
   - 优点：能进入业务流程和工具调用。
   - 局限：角色身份、知识边界、质量验证和版本治理可能不足，容易变成流程节点而不是企业角色资产。

### 3.4 本产品可能的差异化

待验证的差异化主张：

1. 不是“创建一个 AI bot”，而是“沉淀一个可运营的数字角色资产”。
2. 不是“知识库问答”，而是“带角色身份、知识边界、能力边界和版本证据的专业角色服务”。
3. 不是“个人 prompt 效率工具”，而是“集团企业可管理、可发布、可复用、可审计的角色资产体系”。
4. 未来不是单纯问答，而是按 A1/A2/A3 分层推进：
   - A1：问答建议
   - A2：生成业务产物
   - A3：受控执行动作

## 4. 当前需要展开讨论的问题

1. 这个产品是否是企业 AI 转型的“必要件”？
   - 如果是，必要性来自哪里：治理、知识、流程、组织能力，还是平台集成？
   - 如果不是，它更像哪个类别：工具、平台、业务应用、治理中台？

2. 第一商业用户是谁？
   - 集团 AI / 数字化 / 知识运营团队
   - 业务部门负责人
   - IT 平台团队
   - 合规 / 风控 / 审计团队

3. 付费价值来自哪里？
   - 降低专家经验流失
   - 提高知识复用
   - 降低合规风险
   - 提高决策质量
   - 支撑 AI 能力进入业务流程

4. 市面方案已经解决了哪些问题？
   - 哪些能力我们不应该重复做
   - 哪些能力必须借鉴
   - 哪些能力是我们的差异化位置

5. v0.4 应该证明什么？
   - AI 创建体验
   - 发布后真实使用
   - 最小系统调用
   - 运营看板
   - 资产包与版本追溯

## 5. 第一商业用户与买单人讨论

### 5.1 已形成的判断

买单人和商业用户不能简单等同。

在集团企业里，狭义买单人通常更可能是：

1. 集团 AI / 数字化部门
2. IT 平台团队
3. 知识运营 / 数据治理团队
4. 可能包含合规、风控、审计等治理部门

但商业用户范围更大，至少包括：

1. 高管决策层
2. 数字化 / AI 平台团队
3. 业务部门负责人
4. 业务部门一线人员
5. 业务系统或 Agent 搭建者
6. 合规、风控、审计等利益相关方

业务部门虽然未必直接持有预算，但会强影响采购和落地，因为角色资产最终要进入业务部门的决策、问答、分析和流程场景。

### 5.2 业务部门参与的成熟度分层

业务部门参与可能分为两个阶段：

1. **运营管理型参与**
   - 业务部门直接在本平台创建、维护、发布和运营自己的角色资产。
   - 这可能是终局理想态。
   - 前期由于治理、AI 能力、知识组织和质量控制成熟度不足，更多可能由数字化部门或知识运营团队代运营。

2. **消费集成型参与**
   - 业务部门不一定直接运营角色资产，但会在自己的 Agent、问答系统、工作流或信息系统中消费这些角色资产。
   - 如果业务部门自行搭建 Agent 或业务应用，就需要稳定、清晰、低摩擦地调用角色资产。
   - 这要求平台提供可发现、可调用、可追溯、可治理的消费接口，而不仅是管理台页面。

### 5.3 规划方补充判断

当前产品应按“双层客户模型”设计：

1. **预算 / 治理客户**
   - 关心统一管理、合规、复用、资产沉淀、治理证据、风险控制。
   - 决定是否采购和是否纳入集团 AI 基础设施。

2. **业务消费客户**
   - 关心能不能快速拿来用、能不能嵌入自己的场景、调用是否稳定、答案是否可信。
   - 决定产品是否真正有使用量和业务价值。

因此，产品不能只服务“管理者建角色”，也不能只服务“一线用户问问题”。它必须同时解决：

1. 角色资产怎么被治理方管理。
2. 角色资产怎么被业务方消费。
3. 角色资产怎么在使用后产生证据并反哺治理。

### 5.4 对 v0.4 的影响

如果接受上述双层客户模型，v0.4 需要避免只做“创建与管理侧体验”。

v0.4 至少应证明：

1. 治理方可以把角色当资产创建、发布和追踪。
2. 业务方可以通过一个正式使用入口消费已发布角色。
3. 平台能留下使用和运营证据。
4. 后续系统或 Agent 能看见明确的调用路径，最好具备最小真实消费入口。

这进一步支持前述判断：

1. `DD-10 AI 协作创建` 应保留，但不是唯一核心。
2. `DD-09` 应从质量看板升级为运营看板。
3. `E-4` 应优先补真实消费入口，至少不能只停留在 iframe 和文档。

## 6. v0.4 MVP 与 AI 原生产品原则

### 6.1 已形成的定论

`v0.4` 应同时满足两个要求，二者不冲突：

1. **核心链路全覆盖**
   - `v0.4` 必须做最小真实消费入口。
   - 更准确地说，`v0.4` 应覆盖“企业数字角色资产运营平台”定位中的核心链路。
   - 这才是 MVP 的价值，而不是只做单点体验。

2. **AI 原生产品体感**
   - 作为支持集团 AI 转型的核心平台，产品本身不能呈现为传统信息化系统再外挂 AI。
   - 如果核心体验仍是复杂填表、人工搬运和手动解释，会显著提高用户对新产品的接受难度。
   - AI 不只是体验层装饰，而应降低产品使用门槛，并围绕完整用户场景参与创建、运营、使用、评估和优化。

### 6.2 对“AI 创建体验”的修正

`AI 协作创建` 不应被理解为单独的“炫酷功能”，而应被理解为 AI 原生产品原则在创建阶段的体现。

但 AI 原生不应只停留在创建环节，后续还应逐步覆盖：

1. 创建：从自然语言意图到结构化角色草案。
2. 运营：自动发现草案缺口、质量风险、长期未发布资产、低使用资产。
3. 测试：辅助生成测试问题、识别失败原因、提出修订建议。
4. 发布：提示边界风险、知识版本风险和能力层级风险。
5. 使用：根据场景引导用户选择合适角色或组合角色。
6. 优化：基于使用记录和反馈建议角色迭代。

### 6.3 对 v0.4 的直接影响

`v0.4` 的 MVP 应至少覆盖以下闭环：

1. **AI 原生创建**
   - 用户用自然语言描述需求。
   - AI 生成结构化角色草案。
   - 用户确认 / 编辑后保存为 draft。

2. **资产治理**
   - 角色具备治理属性、边界声明、能力层级、版本和知识绑定。

3. **发布与使用**
   - 角色经过测试后发布。
   - 已发布角色有正式使用入口。

4. **最小真实消费**
   - 业务系统 / Agent 搭建者能通过一个真实入口消费已发布角色资产。
   - 该入口必须支持版本冻结或至少明确消费的是哪个已发布版本。

5. **运营证据**
   - 平台记录创建、测试、发布、使用的关键证据。
   - 运营者能看到角色是否被创建后沉睡、是否被发布、是否被使用、使用效果如何。

### 6.4 规划方补充边界

AI 原生不等于 AI 全自动。

本产品在集团企业语境下必须坚持：

1. AI 生成草案，但人确认后才落库。
2. AI 提供测试与运营建议，但不能绕过发布门禁。
3. AI 可以推荐角色或改进方向，但不能擅自改变已发布资产。
4. A3 执行动作必须经过跨项目裁决、权限设计和审计设计。

因此，本产品的 AI 原生方向应定义为：

```text
AI-first workflow with human accountable control.
```

中文表达：

```text
AI 优先参与流程，人承担确认、发布和责任边界。
```

## 7. 暂定原则

1. v0.4 不应只做“更酷的创建器”。
2. v0.4 至少要证明：角色能被创建、治理、发布、使用，并留下运营证据。
3. AI 协作创建是入口创新，不是全部商业价值。
4. 真实消费入口和运营看板的重要性不低于 AI 创建。
5. 后续所有功能都必须能回答：它如何让角色更像企业资产，而不是又多一个聊天入口？
6. `v0.4` 应覆盖核心链路 MVP：AI 创建、资产治理、测试发布、真实消费、运营证据。
7. 产品形态应按 AI 原生设计，不按“传统信息化系统 + AI 辅助按钮”设计。
8. AI 原生必须保留人类确认、发布门禁、版本追溯和责任边界。

## 8. v0.4 消费入口候选讨论

### 8.1 已确认优先考虑的 3 类消费形态

1. **角色资产目录**
   - 这是基础项。
   - 业务方、治理方和平台方都需要看到有哪些已发布角色资产、适用什么场景、由谁负责、基于什么知识、质量状态如何、如何使用。

2. **开放 Agent 平台消费角色资产**
   - 这很重要。
   - 典型对象包括 Dify、Coze 等开放型 Agent / Bot / Workflow 平台。
   - 核心问题是：这些平台如何接入已发布角色资产，是通过 API、插件、工具、OpenAPI schema，还是后续 MCP / A2A。

3. **决策产品集成**
   - 这是产品组合内必须考虑的集成。
   - 它和“开放 Agent 平台消费”有相似之处：都是外部消费者调用角色资产。
   - 但它不是普通第三方接入，而是上位产品组合内的受治理消费方，可能有更明确的字段、版本、调用边界和验收规则。

### 8.2 规划方初步判断

三者不是同一层：

1. **角色资产目录** 是资产发现层。
2. **开放 Agent 平台消费** 是外部分发 / 生态接入层。
3. **决策产品集成** 是产品组合内的受治理业务消费层。

但三者底层应尽量共用同一个“角色消费能力”：

```text
已发布角色资产
-> 稳定角色版本
-> 明确输入
-> 角色运行 / 问答 / 建议
-> 结构化输出
-> 使用记录
-> 版本与知识追溯
```

因此 v0.4 不应分别为 Dify、Coze、决策产品各做一套逻辑。

更合理的方式是先定义一个内部统一的“角色消费能力”，再为不同消费方提供不同外壳：

1. 资产目录：人查看和试用。
2. 开放 Agent 平台：通过 API / OpenAPI schema / 后续 MCP 接入。
3. 决策产品：通过产品组合治理约定的接口或适配层接入。

该判断的底层逻辑不是“因为多做几条线太重”，而是平台产品逻辑本身要求如此：

1. 先定义角色资产如何被消费。
2. 再定义不同消费方如何接入这个消费能力。
3. 不为 Dify、Coze、决策产品分别定制互相割裂的独立链路。

执行工作量会影响阶段拆分，但不改变这个平台化原则。

### 8.3 待继续讨论

1. v0.4 是否直接把决策产品集成纳入 Scope In，还是只做消费能力并为决策产品预留适配？
2. 对 Dify / Coze 这类开放平台，v0.4 的最低可用形态是：
   - 只提供 API 文档和样例？
   - 提供 OpenAPI schema？
   - 提供一个可复制的 HTTP 工具调用样例？
   - 提供 MCP 服务端？
3. 是否需要把“角色资产目录”设计成一个面向业务方的资产市场，而不仅是管理列表？

### 8.4 关于开放 Agent 平台消费提问边界的修正

用户对规划方提问边界提出校正：

1. 同意开放 Agent 平台消费需要有 MVP 最低可用证明。
2. 不在业务需求阶段确认 `HTTP`、`OpenAPI`、插件、`MCP` 等具体技术形态。
3. MVP 开放 Agent 平台代表对象指定为 Dify。
4. 当前阶段不需要固定某个具体业务场景作为唯一实现样例，场景应在实现设计阶段结合可用角色资产、业务价值和集成可行性确认。

规划方修正后的判断：

1. 业务需求方应确认的是“Dify 能否消费已发布角色资产，并形成可追溯、可治理、可复核的使用证据”，不是确认技术协议。
2. `HTTP`、`OpenAPI`、插件、`MCP` 等属于实现方案候选，应由工作方在设计阶段提出，经复审后确定。
3. MVP 正文应要求 Dify 消费证明覆盖：Dify 发起调用、角色资产按 published 版本响应、输出固定治理外壳和业务结构、生成使用记录、记录调用方为开放 Agent 平台、可追溯角色版本和知识来源。
4. 代表业务场景不应在规划讨论阶段被拍成单一固定答案；当前只定义选择原则：能体现企业业务价值、不是单纯聊天、能展示角色资产被外部 Agent 消费、能产生运营证据。
5. 后续规划方提问必须先区分：产品原则问题、业务场景问题、实现机制问题、验收证据问题。不得把实现机制问题前置给业务方做产品裁决。

## 9. 关于“缩减建议”的修正

### 9.1 已形成的修正原则

此前规划方对 `DD-09 运营/质量看板`、`DD-08 中文枚举`、`iframe 嵌入` 等项提出过“降级或让位”的表述。该表述需要修正：

1. 如果这些能力属于“企业数字角色资产运营平台”的完整设计链路，则不应在设计层面随意缩减。
2. 可以拆分到 `v0.4`、`v0.4.x` 或 `v0.5` 实现，但设计视图应保持完整。
3. 缩减只能发生在实现排期和验收批次，不应改变产品本质和目标蓝图。

### 9.2 对看板的重新判断

看板不应被理解为可有可无的列表增强。

在“企业数字角色资产运营平台”定位下，看板是运营闭环的关键组成：

1. 没有看板，治理方无法判断哪些角色值得继续运营。
2. 没有看板，业务方无法判断哪些角色可信、常用、有效。
3. 没有看板，AI 原生创建无法形成后续优化闭环。

因此，`DD-09` 不应被缩减为“最近评分 + 使用次数”。

更合适的设计目标是“角色资产运营看板”，至少覆盖：

1. 资产总览：角色数量、发布数量、草稿数量、归档数量。
2. 创建运营：AI 草案接受率、人工修改率、草稿沉睡资产。
3. 质量运营：测试通过率、最近评分、失败原因分布。
4. 使用运营：使用次数、最近使用、低使用资产、高价值资产。
5. 风险运营：知识版本过期、边界缺失、长期未维护角色。

实现可分批：

1. `v0.4`：交付最小运营看板，覆盖资产状态、发布状态、使用次数、最近评分、草稿沉睡。
2. `v0.4.x`：补 AI 草案接受率、人工修改率、失败原因分布。
3. `v0.5`：补知识过期、评分门禁、生命周期策略。

### 9.3 对消费入口的重新判断

消费入口也不应被设计缩减为“iframe + 文档”。

完整设计应包含：

1. 资产目录中的人类试用入口。
2. 开放 Agent 平台可调用入口。
3. 决策产品受治理消费入口。
4. 后续 MCP / A2A 扩展方向。

实现可分批：

1. `v0.4`：统一角色消费能力 + 资产目录试用 + 开放平台调用样例 + 决策产品最小联调能力。
2. `v0.4.x`：Dify / Coze 类平台样例包、调用模板和配置说明。
3. `v0.5`：正式消费侧 API 契约、权限、审计和更多集成方式。

## 10. 统一消费输出与业务 Schema

### 10.1 已形成的原则

统一角色消费能力必须支持结构化输出，但不能把所有角色强行压进同一套业务字段。

正确设计是：

```text
固定治理外壳 + 可配置业务 Schema
```

固定治理外壳用于保证角色资产可追溯、可治理、可被系统消费。

业务 Schema 用于表达不同角色资产的业务输出差异。

### 10.2 固定治理外壳

所有已发布角色被消费时，输出外壳应尽量一致：

1. `answer`：给人阅读的自然语言回答。
2. `role_id`：角色资产 ID。
3. `role_version_id`：本次消费绑定的角色版本。
4. `usage_record_id`：本次使用记录。
5. `created_at`：调用时间。
6. `sources`：知识来源 / 引用来源。
7. `boundary_status`：知识边界、能力边界是否触达或越界。
8. `output_type`：输出类型。
9. `structured_result`：按角色业务 Schema 生成的结构化结果。

### 10.3 可配置业务 Schema

角色设置中需要新增一个配置项：

```text
业务输出 Schema / Output Schema
```

用途：

1. 定义该角色被消费时，`structured_result` 应该按什么结构输出。
2. 支持不同类型角色返回不同业务结构。
3. 避免通用模板对角色多样性造成格式阉割或语义错位。

示例：

1. 经营分析角色：`risk_analysis`
   - 关键发现
   - 风险项
   - 建议动作

2. 制度解释角色：`policy_explanation`
   - 适用条款
   - 条款解释
   - 可做事项
   - 不可做事项

3. 会议纪要角色：`meeting_minutes`
   - 议题
   - 决策
   - 待办事项

4. 技术审查角色：`review_findings`
   - 问题项
   - 严重等级
   - 修复建议

### 10.4 对 v0.4 的影响

`v0.4` 设计上应纳入业务 Schema 配置能力。

实现可以分层：

1. `v0.4`：提供最小 Output Schema 配置项，允许选择通用模板或填写 JSON Schema / 字段描述；消费输出使用固定外壳 + `structured_result`。
2. `v0.4.x`：提供常用业务 Schema 模板库，例如风险分析、制度解释、会议纪要、审查意见。
3. `v0.5`：支持更强校验、Schema 版本管理、消费方按 schema 自动适配。

### 10.5 关键约束

1. 业务 Schema 是角色资产的一部分，应进入版本快照。
2. 已发布角色的业务 Schema 不应被直接覆写，编辑应产生新版本。
3. 消费记录应保存当时使用的 `role_version_id` 和输出结构，避免后续 schema 变化影响历史记录。
4. 如果业务 Schema 要成为跨项目公共契约字段，必须按上位治理规则裁决。

### 10.6 已确认的 v0.4 首批业务输出 Schema 模板

`v0.4` 首批内置 4 类业务输出 Schema 模板：

1. `decision_advice`：决策建议
   - 适用：高管决策、决策产品、重大事项评估。
   - 输出方向：立场 / 倾向、关键理由、主要风险、前置条件、建议动作、引用依据。

2. `risk_analysis`：风险分析
   - 适用：经营分析、风控、财务、项目管理。
   - 输出方向：关键发现、风险项、风险等级、影响范围、建议缓解措施、引用依据。

3. `policy_explanation`：制度解释
   - 适用：制度、合规、人力、财务、行政流程。
   - 输出方向：适用条款、条款解释、可做事项、不可做事项、注意事项、引用依据。

4. `review_findings`：专业审查
   - 适用：法务、合同、方案、技术、项目文档审查。
   - 输出方向：问题项、严重等级、问题说明、修改建议、需确认事项、引用依据。

不作为 v0.4 首批核心模板：

1. 会议纪要
2. 文案创作
3. 通用问答

原因：

1. 它们可用，但与“企业数字角色资产运营平台”的首批商业价值主线不如上述 4 类强。
2. 可作为后续模板库或 `v0.4.x` 补充。

已确认设计结论：

```text
DD-11 业务输出 Schema 首批内置 4 类模板：
decision_advice、risk_analysis、policy_explanation、review_findings。
角色可以选择模板；AI 协作创建时可推荐模板；消费输出采用固定治理外壳 + structured_result；Schema 进入角色版本快照。
```

### 10.7 业务输出 Schema 配置体验收口

用户确认以下产品判断：

1. 可发布、可消费的角色资产必须配置业务输出类型和业务输出结构。
2. 业务输出配置应面向业务语言，而不是让普通业务用户理解技术 Schema。
3. `v0.4` 应要求 AI 在角色创建和编辑时推荐输出类型和字段结构。

规划方补充后的产品口径：

1. 业务输出 Schema 不是技术人员专用配置，而是角色资产对外交付什么业务结果的产品定义。
2. 草稿和内部测试阶段可以允许输出结构不完整，但进入资产市场、Dify 或决策产品消费前必须补齐。
3. 系统应提供首批业务模板，同时允许自定义字段，避免固定模板造成角色能力阉割或语义错位。
4. 自定义字段必须受治理，至少需要中文名称、业务含义、是否必填、示例和适用场景。
5. AI 的职责是降低配置门槛：根据角色描述、知识范围、适用场景和能力边界推荐输出类型与字段结构；人仍负责确认、发布和责任边界。
6. 具体技术表达形式不在需求阶段裁决，由工作方在设计阶段提出，并由规划方复审是否符合业务语言、版本快照和消费稳定性要求。

已确认设计结论：

```text
DD-12 业务输出配置体验：
可发布、可消费角色必须配置业务输出类型和结构；
配置界面面向业务语言；
AI 应推荐输出类型和字段结构；
模板与自定义字段并存；
自定义字段必须具备中文名称、业务含义、是否必填、示例和适用场景；
具体技术 Schema 表达由工作方设计后交回复审。
```

## 11. 资产市场 AI 推荐入口

### 11.1 问题定义

资产市场的 AI 推荐入口不是“猜你喜欢”，也不是把列表搜索换成聊天框。

它要解决的问题是：

```text
业务用户不知道有哪些角色资产，也不知道哪个角色适合当前任务时，
平台能把业务意图翻译成可用角色资产。
```

### 11.2 用户确认的关键判断

用户确认：

```text
资产市场的 AI 推荐入口，本质是“业务任务到角色资产的匹配器”，
不是直接回答用户问题的聊天助手。
```

### 11.3 产品原则

规划方补充后的产品口径：

1. AI 推荐入口应服务于角色资产发现与消费，不应绕过角色资产直接回答业务问题。
2. 推荐对象默认只应是可消费的 published 角色资产；草稿、测试中或归档角色不面向业务消费推荐。
3. 推荐结果必须可解释，至少说明推荐理由、适用问题、业务输出类型、知识范围、质量状态、版本信息和可用消费入口。
4. 推荐结果必须连接真实消费路径，例如直接试用、Dify 接入说明或决策产品消费路径。
5. 如果没有合适角色，系统不应硬推荐，应提示当前角色资产缺口。
6. 推荐失败、频繁无匹配和高频搜索词应成为资产运营信号，进入运营看板或需求池。
7. `v0.4` 不要求复杂个性化推荐，不基于用户画像、历史行为或协同过滤；先做业务意图到已发布角色资产的解释型推荐。

### 11.4 已确认设计结论

```text
DD-13 资产市场 AI 推荐入口：
AI 推荐入口是“业务任务到角色资产的匹配器”；
用户用自然语言描述业务任务后，系统推荐 1-3 个已发布可消费角色资产；
推荐必须可解释，并展示推荐理由、适用问题、业务输出类型、知识范围、质量状态、版本信息和消费入口；
无合适角色时不硬推荐，应形成角色需求或资产运营信号；
v0.4 不做复杂个性化推荐，先实现解释型匹配推荐。
```

## 12. 决策产品集成验收边界

### 12.1 问题定义

决策产品集成不是“决策产品能调到一个接口”，而是：

```text
在一个真实决策业务链路中，
决策产品能消费已发布角色资产，
并把角色建议、依据、版本和责任边界纳入决策过程。
```

### 12.2 用户确认的关键判断

用户确认：

1. `v0.4` 正文应要求决策产品真实集成验收。
2. 角色产品侧能力证据与决策产品侧消费链路证据必须闭合。
3. 如果出现公共契约、读写边界或版本规则问题，必须按上位治理上提，不能由角色产品单方面裁决。

### 12.3 产品边界

1. 角色产品提供可治理的角色资产能力，不替决策产品完成最终决策。
2. 决策产品负责决策事项、流程、用户操作、决策记录和最终责任。
3. 角色产品负责角色资产、版本、知识来源、输出结构、边界状态和使用记录。

集成后，用户在决策产品中应能看到：

1. 某个决策场景调用了哪个已发布角色。
2. 角色输出了什么 `decision_advice` 建议。
3. 建议来自哪个角色版本。
4. 建议基于哪些知识或来源。
5. 是否存在边界阻断、知识不足、上下文不足或系统失败。

### 12.4 最小真实场景链

```text
决策产品中的决策事项
-> 调用已发布角色资产
-> 角色产品按 published 版本生成 decision_advice
-> 返回结构化建议、来源、状态和版本信息
-> 决策产品展示或记录该建议
-> 角色产品生成 usage record
-> 双方证据可互相对上
```

该场景不能只发生在角色产品测试台，也不能只用 API 自测替代。它必须发生在决策产品消费语境中。

### 12.5 双方责任

角色产品应提供并证明：

1. 只允许消费 published 角色版本。
2. 支持 `role_id` 必填、`role_version_id` 可选的消费方式。
3. 返回 `decision_advice` 输出结构。
4. 返回角色版本、知识来源、状态、使用记录等治理证据。
5. 调用失败、知识不足、边界阻断时有明确状态，不假装成功。

决策产品应提供并证明：

1. 有一个真实决策事项或决策场景调用角色资产。
2. 能传入足够业务上下文，而不是只发一句空泛问题。
3. 能展示或保存角色建议。
4. 能保留角色版本、使用记录、来源等追溯信息。
5. 能处理 `insufficient_context`、`insufficient_knowledge`、`boundary_blocked`、`system_failed` 等非成功状态。

### 12.6 治理边界

如果决策产品要求把 `status`、`usage_record_id`、`structured_result`、`sources` 等字段作为跨项目公共契约稳定依赖，可能触发上位治理确认。

当前需求阶段可以明确“需要这些能力和证据”，但不能单方面宣布公共契约已冻结。

只有双方证据闭合，并且没有未裁决公共契约问题，才能说决策产品集成通过。

### 12.7 已确认设计结论

```text
DD-14 决策产品集成验收边界：
v0.4 要求决策产品真实集成验收；
集成链路必须发生在决策产品消费语境中；
角色产品提供可治理角色资产能力和 usage record；
决策产品负责决策事项、流程、展示/记录和最终责任；
双方证据必须能互相对上；
如触发公共契约、读写边界或版本规则问题，必须上提治理裁决。
```

## 13. Dify 代表场景与验收证据

### 13.1 问题定义

Dify 代表场景不是为了证明“能接 Dify”，而是证明：

```text
开放 Agent 平台可以把角色资产作为企业能力来消费。
```

因此，场景不能退化成“在 Dify 里问一句话”。它需要体现角色资产的治理价值、版本追溯、知识来源、输出类型和外部消费记录。

### 13.2 用户确认的边界

用户确认：

1. 同意使用 Dify 做 MVP 开放 Agent 平台消费的最低可用证明。
2. 风险分析类场景可以作为参考实例，用于具象化验收标准。
3. 当前阶段不固定具体实现场景；工作方后续可以使用该场景，也可以换成同等证明力的业务场景。
4. 需求阶段不定义 Dify 的具体插件、HTTP、OpenAPI、工作流配置或其他实现形态。

### 13.3 场景选择原则

Dify 代表场景必须满足：

1. 有明确业务任务，而不是泛问答。
2. 需要调用一个已发布角色资产，而不是 Dify 自己直接回答。
3. 能体现角色资产的治理价值，例如版本、知识来源、边界、输出类型。
4. 调用后能留下 usage record，证明这个角色被外部 Agent 平台消费过。

推荐参考实例：

```text
合同 / 方案风险分析 Agent：
Dify 接收一段合同条款或项目方案，
调用已发布的风险分析角色，
返回风险项、等级、依据、建议动作和需人工确认事项。
```

该实例只是标准具象化，不是唯一允许场景。工作方可以替换为制度解释、专业审查或其他同等证明力场景。

### 13.4 最低验收证据

Dify 侧需要证明：

1. 调用发生在 Dify 工作流或 Agent 场景中。
2. 调用了角色产品的已发布角色资产。
3. 传入了真实业务上下文，不是空泛测试句。
4. 能接收并展示角色输出。
5. 能处理非成功状态，至少不把失败当成功。

角色产品侧需要证明：

1. 使用记录中调用方类型为开放 Agent 平台，或具备等价可识别标识。
2. 记录了 Dify 或该 Agent 的调用方标识。
3. 记录了实际使用的 `role_id` 和 `role_version_id`。
4. 输出包含 `status`、`structured_result`、`sources`、`usage_record_id`。
5. 被消费角色是 published 版本，不是草稿或测试角色。

### 13.5 验收声明边界

通过该场景只能声明：

```text
Dify 作为代表开放 Agent 平台，完成了本轮最低可用消费证明。
```

不能外推为：

1. 所有开放 Agent 平台均已支持。
2. 所有 Dify 插件或部署形态均已支持。
3. 技术接入方式已经成为长期冻结公共契约。
4. 所有业务场景都已完成开放 Agent 平台验收。

### 13.6 已确认设计结论

```text
DD-15 Dify 代表场景与验收证据：
v0.4 使用 Dify 作为开放 Agent 平台消费代表对象；
风险分析类场景作为推荐参考实例，用于具象化标准，不是固定实现承诺；
最终场景可由工作方在设计阶段确认或替换，但必须满足同等证明力；
验收必须证明 Dify 消费的是 published 角色资产，并生成可追溯 usage record；
不得把该证明外推为所有开放平台或长期冻结技术契约均已支持。
```

## 14. 统一消费结果状态

### 14.1 问题定义

统一消费结果状态不是技术错误码，而是一次角色资产消费的业务结论。

它要告诉人和系统：

1. 这次调用能不能被使用。
2. 如果不能使用，是用户输入不够、知识不够、角色边界阻断、系统异常，还是无法归类。
3. 该结果能否继续进入资产市场试用、Dify 消费、决策产品消费或运营看板。

### 14.2 用户确认的关键判断

用户确认：

1. `v0.4` 本轮统一消费结果状态固定为 6 个，不再扩展。
2. 每次角色消费必须返回 `status` 和 `status_reason`。
3. 非 `success` 不应被消费方当作正常业务结论继续流转。
4. `undefined` 允许存在，但应作为运营复盘信号，不能被长期大量使用。

### 14.3 MVP 状态清单

`v0.4` 正文纳入 6 个状态：

1. `success`：成功。
2. `insufficient_context`：上下文不足。
3. `insufficient_knowledge`：知识不足。
4. `boundary_blocked`：边界阻断。
5. `system_failed`：系统失败。
6. `undefined`：未定义。

### 14.4 状态规则

1. `success`：角色在知识边界和能力边界内完成回答或结构化输出；结果可以展示、记录并进入后续流程。
2. `insufficient_context`：用户任务属于角色范围，但输入信息不足以可靠判断；消费方应提示补充上下文，不应归因为角色质量失败。
3. `insufficient_knowledge`：用户任务属于角色能力范围，输入也足够，但绑定知识或当前知识版本无法支撑可靠回答；运营上视为知识资产缺口。
4. `boundary_blocked`：请求超出角色知识边界、能力边界或能力层级；这是治理生效，消费方应停止使用该结果并转人工、换角色或进入更高能力流程。
5. `system_failed`：LLM、知识平台、数据库、网络、超时等系统异常导致无法完成调用；消费方可重试或提示系统错误，运营上归为系统稳定性问题。
6. `undefined`：无法稳定归类到上述状态，或规则不足以判断；这是兜底，不应被长期大量使用，出现频率高时需要产品和运营复盘。

### 14.5 已确认设计结论

```text
DD-16 统一消费结果状态：
v0.4 统一消费结果状态固定为 success、insufficient_context、insufficient_knowledge、boundary_blocked、system_failed、undefined；
每次角色消费必须返回 status 和 status_reason；
非 success 不应被消费方当作正常业务结论继续流转；
undefined 是兜底和复盘信号，不应长期大量使用；
后续新增状态必须有明确命中规则、消费方处理方式和运营含义。
```

## 15. 统一角色消费输入模型

### 15.1 纠偏原则

统一角色消费输入不应被设计成 `role_id` 和 `role_version_id` 二选一。

更合理的模型是：

```text
role_id 必填
role_version_id 可选
```

原因：

1. `role_id` 代表消费的是哪个角色资产。
2. `role_version_id` 代表是否显式指定某个已发布版本。
3. 大多数业务消费方只需要调用当前稳定发布版本。
4. 高治理、强追溯或回放场景可以显式指定版本。

类似模型：

```text
默认使用当前稳定版本，也允许高级消费方指定历史或特定版本。
```

### 15.2 v0.4 建议输入模型

统一消费能力的最小输入：

1. `role_id`：必填，角色资产 ID。
2. `role_version_id`：可选，指定已发布角色版本；不填时使用当前 published 版本。
3. `query`：必填，用户问题或业务请求。
4. `context`：可选，业务上下文。
5. `output_type`：可选，不填时使用角色版本配置的业务输出 Schema。
6. `caller_type`：可选但建议记录，例如 `human`、`agent_platform`、`decision_product`、`system`。
7. `caller_id`：可选但建议记录，调用方标识。

### 15.3 版本选择规则

1. 如果只传 `role_id`：
   - 系统使用该角色当前 published 版本。
   - 返回中必须明确写出实际使用的 `role_version_id`。

2. 如果同时传 `role_id` 和 `role_version_id`：
   - 系统校验该版本属于该角色。
   - 系统校验该版本可被消费，通常应为 published 或允许回放的历史 published 版本。
   - 返回中使用指定版本。

3. 如果传入的 `role_version_id` 不属于该 `role_id`：
   - 必须明确拒绝调用。

4. 如果指定版本已归档或不可消费：
   - 必须返回明确错误，而不是自动 fallback 到当前版本。

### 15.4 对消费方的意义

1. 资产目录试用：
   - 默认只传 `role_id`，使用当前发布版本。

2. Dify / Coze / 自建 Agent：
   - 默认配置 `role_id`，保持简单。
   - 如业务方需要稳定复现，可配置固定 `role_version_id`。

3. 决策产品：
   - 可优先使用显式 `role_version_id`，确保决策记录可追溯、可复现。

### 15.5 已形成结论

```text
v0.4 统一角色消费输入模型采用：
role_id 必填，role_version_id 可选。
默认使用当前 published 版本；指定 role_version_id 时严格按指定版本消费并校验归属和状态。
```
