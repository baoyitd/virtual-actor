# v0.4.0 提案战略复审记录

> 复审日期：2026-05-26
> 复审角色：规划方 / AI 审核方（战略与商业化视角）
> 复审对象：`docs/iterations/v0.4.0/proposal-user-feedback.md`
> 结论：修改后批准

## 1. 总体判断

方向 B 成立。

把 `DD-10` 从“一个表单字段建议按钮”升级为“AI 协作式角色创建”，比原 dossier 更符合终审方对“产品要有可感知 AI 范式变化”的要求，也符合当前企业 Agent 产品普遍采用自然语言创建、人工确认、持续优化的趋势。

但当前提案仍有一个核心偏差：

**它把“AI 创建更酷”当成了 v0.4 的主要价值锚点，而没有把“角色资产如何被真实使用、治理、追踪和接入业务流程”同步提升到同样强度。**

结果会是：

1. 演示效果会提升。
2. 用户首次创建体验会更好。
3. 但商业化价值、组织级复用价值和未来平台护城河仍不够强。

因此本轮不建议驳回方向 B，但建议按“修改后批准”处理。

## 2. 主要问题

### P0-1 `DD-10 AI 协作创建` 适合作为加速器，不适合作为 v0.4 的主护城河

当前提案把 v0.4 的“范式转变”几乎全部押注在 `DD-10` 上，认为“角色创建从人填表变成 AI 对话式创建”就是产品质变。

这个判断有演示价值，但商业护城河判断偏强。

原因：

1. 角色/Agent 的自然语言创建，已经是当前主流 Agent 平台的常见能力。
2. 企业真正付费的，不是“创建时更像 AI”，而是“创建后的角色能被持续治理、被多渠道使用、被系统调用、被追责、被优化”。
3. `DD-10` 更接近“获客/激活体验升级”，不是长期壁垒本身。

对本项目的含义：

1. `DD-10` 应保留，而且优先级可以是 `P1`。
2. 但不能让 `DD-10` 占据 v0.4 的唯一核心叙事。
3. v0.4 的真正差异化锚点，仍应是“角色资产治理 + 版本追溯 + 运行期质量闭环 + 可被接入”。

建议：

1. 将 v0.4 的主标题从“AI 范式转变”调整为“角色资产可运营化 + AI 协作创建入口”。
2. 在 `proposal-user-feedback.md` 中明确：`DD-10` 是“用户入口创新”，不是“唯一差异化来源”。
3. 在终审口径中避免把“AI 对话式创建”表述成 v0.4 的唯一核心价值。

### P0-2 `E-4 多样化系统集成方式` 当前仍然没有被真正回答

当前提案对 `E-4` 的主要回应是：

1. 在使用台展示 iframe 嵌入代码片段。
2. 展示 OpenAPI 端点调用方式文档。
3. 对已有端点做可达性验证。

这能改善“看起来可以接入”，但还不足以构成“多样化系统集成方式”。

根本问题是：

**iframe 是分发方式，不是集成能力本身。**

它最多证明“问答页面可以嵌进去”，但没有解决：

1. 外部系统如何以编程方式调用角色。
2. 外部系统如何拿到版本冻结后的稳定行为。
3. 外部系统如何做身份、授权、审计和会话管理。
4. 后续如何走向 MCP / A2A 这类更先进的互操作方式。

当前提案把真正的消费侧 API 推迟到 `v0.5`，把 `MCP/A2A` 推迟到 `v0.6`，这会导致：

1. v0.4 更像“内部管理台 + 更聪明的创建器”。
2. 而不是“一个开始具备平台属性的角色资产产品”。

建议：

1. `DD-03` 的 iframe 展示可以保留，但明确降级为“渠道分发指引”，不作为 `E-4` 主回应。
2. 在 v0.4 里补一个**最小真实消费入口**，二选一即可：
   - 方案 A：最小只读调用接口，例如一个受控的 `invoke/use` 类接口，用于让外部系统程序化调用已发布角色。
   - 方案 B：最小 MCP 服务端只读暴露，先把“发现角色 / 读取版本 / 发起问答”暴露为工具集合。
3. 如果 v0.4 坚持不做真实消费入口，则终审口径必须收敛为：`E-4 仅完成方向验证，不构成已交付的集成能力`。

### P0-3 当前提案对“AI 运营”的理解仍偏前台体验，缺少运行期治理闭环

终审方的 `E-2` 是“AI 加持的全生命周期运营，而非大量人工处理”。

当前提案主要用 `DD-10` 回答这个问题，但 `DD-10` 只覆盖**创建阶段**。

这会带来一个明显问题：

1. 角色创建时很 AI。
2. 角色发布后、被使用后、质量波动后，运营体系仍然主要靠人工。

`DD-09` 当前只是“最近评分 + 发布状态 + 使用次数”的聚合展示，这更像列表增强，不像运营闭环。

如果 v0.4 想在商业化上更站得住，至少需要一个“AI 运营最小闭环”：

1. AI 草案生成后，记录用户做了哪些修改。
2. 发布后，记录该角色被使用后是否有效。
3. 运营者能看到哪些字段经常被改、哪些角色创建后从未发布、哪些 AI 草案转化率低。

建议：

1. 将 `DD-09` 从“质量看板 MVP”升级为“角色运营看板 MVP”。
2. 至少增加 4 个指标：
   - AI 草案接受率
   - AI 草案人工修改率
   - draft -> published 转化率
   - 最近测试通过率 / 最近失败原因分布
3. 如果实现量受限，优先砍掉“中文枚举映射”这类低战略价值项，把资源让给运营看板。

### P1-1 路线图对“商业价值产生点”的排序还可以更务实

当前路线图把：

1. `v0.4` 定位为 AI 协作创建
2. `v0.5` 才开始真正消费侧 API
3. `v0.6` 才开始 A2 生成产物

这个顺序更像“先把创建做得更惊艳，再补使用和集成”。

但从企业价值角度看，很多组织不是缺“更酷的创建器”，而是缺：

1. 能被组织内多处复用的角色资产。
2. 能嵌入业务流程的调用面。
3. 能被运营和治理团队持续优化的运行证据。

建议：

1. 如果资源有限，可以保留 `DD-10`，但同时把“最小真实消费入口”提前到 v0.4 或 v0.4.x。
2. 如果不能提前，就把 `v0.5` 的目标压缩明确为：**先完成程序化调用与发布后消费闭环**，不要再继续扩 scope。

### P1-2 “完整角色资产管理平台”的回应还不够像平台

当前提案对 `E-1` 的回应已经比原 dossier 强，但平台感仍然不足。

缺口主要在 3 个维度：

1. **资产包视角不足**：现在仍然偏“一个角色页面”，而不是“一个可发布、可复用、可分发的资产包”。
2. **分发视角不足**：缺少版本发布后“给谁用、怎么用、在哪用”的正式对象。
3. **运营视角不足**：缺少“哪些资产值得保留 / 升级 / 下架”的决策面板。

建议：

1. 把“角色版本详情”设计成“资产版本包详情”，至少明确：
   - 角色说明
   - 治理属性
   - 知识版本快照
   - capability_level
   - 可用入口（手工使用 / 嵌入 / API / 未来 MCP）
2. 在发布页或详情页新增“分发方式”区块，而不是只在使用台放 iframe 代码。

## 3. 建议的 v0.4 调整方案

### 3.1 建议保留

1. `DD-10 AI 协作式角色创建`
2. `DD-01~05` 原底座
3. `DD-07 历史版本详情`

### 3.2 建议升级

1. `DD-09`：从“质量看板 MVP”升级为“角色运营看板 MVP”
2. `DD-03/DD-04`：从“iframe + 文档展示”升级为“至少一个真实消费入口 + 文档/验证”

### 3.3 建议降级或让位

1. `DD-08 中文枚举映射`
   - 保留可以，但不应继续占用与 `DD-09`、消费入口同等级的资源优先级
2. iframe 嵌入代码展示
   - 保留为渠道分发补充项，不作为系统集成主回答

## 4. 建议的终审口径

不建议直接写“通过，进入实现”。

建议终审口径为：

```text
方向 B 原则同意，但需按以下优化后冻结 Scope 再进入实现：
1. 保留 DD-10 AI 协作创建
2. 下调 DD-10 作为唯一核心卖点的叙事强度
3. 将 DD-09 升级为运营看板 MVP
4. 为 E-4 增加一个真实消费入口，或明确收窄为“方向验证而非已交付集成能力”
```

## 5. 后续迭代方向建议

结合当前行业趋势和本项目已有基础，建议把未来版本按 4 条产品主线持续推进：

1. **Authoring（创建）**
   - AI 协作创建
   - 多轮优化
   - 模板 / 最佳实践复用

2. **Runtime（运行）**
   - 使用台
   - A2 生成产物
   - A3 执行动作（裁决后）

3. **Distribution（分发）**
   - 嵌入
   - API
   - MCP / A2A / 多渠道

4. **Governance（治理）**
   - 版本
   - 质量
   - 审计
   - 运营看板
   - 生命周期管理

当前提案最强的是 Authoring，最弱的是 Distribution 和 Governance。  
v0.4 如果继续只强化 Authoring，会更像“好用的创建器”；  
v0.4 如果同步补一点 Distribution + Governance，才更像“可商业化的角色资产平台”。
