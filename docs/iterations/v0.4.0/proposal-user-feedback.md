# v0.4.0 终审反馈整合提案（修订版）

> 版本：v0.4.0 | 日期：2026-05-25 | Formal Status：Draft
> 提案方：AI 工作方 | 提案依据：终审方反馈 + AI 审核方复审 + 当前 dossier 产出
> 修订说明：方向 B — v0.4 交付后产品体验有可感知的 AI 范式转变

## 0. 战略论证

终审方反馈的本质不是"缺几个展示字段"，而是**产品整体交互范式仍是"人填表 → 人问答 → 人看板"，AI 只在角落出现一次**。如果 v0.4 只交付信息化标配功能，产品在终审方眼中仍然是"没什么意思的传统信息化产品"。

方向 B 的核心判断：**v0.4 必须让终审方在交付后能感知到"AI 在驱动产品"的范式转变**。不是全生命周期 AI 化（这在单轮内不可控），而是让一个关键路径从"人做"变为"AI 做、人确认"——用户打开产品时，能感受到"这个产品和传统信息化不一样"。

具体做法：把 AI 辅助从"一个表单字段的建议按钮"升级为**角色创建全流程的 AI 协作体验**。用户不再逐项手动填写 5 层配置，而是与 AI 对话式完成角色定义——用户说出意图，AI 生成完整角色草案，用户确认或调整后保存。这改变了产品最核心的交互路径（角色创建），让 AI 从角落走到中心。

**为什么这是必要基石而非可跳过的阶段**：治理属性（DD-01）和使用台（DD-03）是 AI 创建流程的底座——AI 生成的角色草案必须落地到有治理属性的数据结构中，AI 生成的角色必须进入有版本冻结的使用台。没有这些底座，AI 创建只是玩具；有了这些底座，AI 创建是资产化流程的第一步。v0.4 同时交付底座和 AI 入口，让终审方看到"底座 + AI 范式"的组合效果。

**质变时间锚点**：

| 版本 | 预计周期 | 范式转变 |
|---|---|---|
| v0.4 | 6-8 周 | 从"人填表"到"AI 对话式创建 + 人确认"——角色创建路径的范式转变 |
| v0.5 | 6-8 周 | 从"人手动调用"到"消费方可 API 调用角色"——使用路径的范式转变 |
| v0.6 | 8-10 周 | 从"角色只问答"到"角色可生成产物"——能力路径的范式转变 |
| v0.7 | 待裁决 | 从"角色只建议"到"角色可执行动作"——决策路径的范式转变（依赖跨项目裁决） |

每个版本有一条可感知的范式转变线，v0.4 的是"AI 协作创建"。

| # | 终审方期望 | 当前 v0.4 交付 | 落差评估 |
|---|---|---|---|

## 2. 提案：方向 B — AI 范式转变 + 底座补齐

核心策略：v0.4 有两条主线——**底座主线**（治理属性、使用台、边界声明）和**AI 主线**（AI 协作式角色创建）。底座主线是原 dossier 的 P0/P1 项（DD-01~05），AI 主线是新增的范式转变项（DD-10 升级为 AI 协作创建）。两条主线互为支撑：底座为 AI 创建提供落地结构，AI 创建为底座提供可感知的产品体验。

### 2.1 v0.4 范围调整提案

#### A-1：DD-03 使用台升级 — 嵌入使用指引

| 维度 | 说明 |
|---|---|
| 原状态 | DD-03 定义使用台为独立页面 /roles/:id/use |
| 调整 | 使用台页面提供 **iframe 嵌入代码片段展示** 和 **OpenAPI 端点调用方式文档展示**（非实际 API 实现）。嵌入代码指向使用台页面的问答 widget（即 /roles/:id/use 页面本身），消费方可以将已发布角色的问答界面 iframe 嵌入到自己的业务页面中 |
| 理由 | 终审方期望 E-4（系统集成）在 v0.4 只有一份设计文档。嵌入代码和端点文档展示让消费方从"看文档"变为"看到具体操作指引和可嵌入的 UI 入口" |
| 风险等级 | 低（相对：低；绝对：低）。嵌入代码指向的是使用台页面本身（v0.4 已实现的问答界面），不是指向未实现的消费侧 API |
| 缓解 | 明确标注"此为嵌入指引，使用台页面为 v0.4 已实现的问答界面；消费侧 API 端点为设计建议，v0.5 实现" |

#### A-2：新增 DD-09 — 角色资产质量看板 MVP

| 维度 | 说明 |
|---|---|
| 原状态 | 无 |
| 调整 | 新增 P2 范围项：角色列表页补质量状态聚合展示（最近测试评分、发布状态、使用次数） |
| 理由 | 终审方期望 E-1 的核心落差之一是"没有治理看板"。质量状态聚合展示为治理者提供一览式资产健康视图 |
| 风险等级 | 低 |
| 实现量 | **需新增后端聚合读取逻辑**（修改列表 API 返回结构，聚合 test_runs 最近评分和 usage_records 使用次数），不是"只补展示字段" |
| **数据依赖** | **DD-09 的 usage_count 字段依赖 DD-03 的 usage_records 表有数据**。如果 DD-03 延期，DD-09 降级为：仅展示 test_runs 最近评分 + 发布状态，不展示 usage_count，待 DD-03 实现后补齐 |
| 缓解 | 看板数据来源为已有 test_runs + 新增 usage_records，不新增权限逻辑；标注"v0.4 不基于 visibility 实现访问控制" |

#### A-3：DD-10 升级 — AI 协作式角色创建（从"字段建议"升级为"全流程 AI 协作"）

| 维度 | 说明 |
|---|---|
| 原状态 | AI 辅助填充 Scope Out |
| 调整 | **从原提案的"AI 辅助边界声明建议（一个按钮）"升级为"AI 协作式角色创建全流程"**。用户不再逐项手动填写角色配置，而是通过对话式交互完成角色定义 |
| 理由 | 这是方向 B 的核心——让产品交互范式从"人填表"转变为"AI 对话式创建 + 人确认"。终审方反馈"不够 sexy"的本质是产品没有可感知的 AI 体验。一个表单字段的建议按钮无法改变范式，但对话式创建可以 |

**AI 协作式角色创建的具体交互流程**：

1. 用户点击"AI 创建角色"入口（创建页新增按钮，与手动创建并存，不替代）
2. 用户输入角色意图描述（如"我需要一个经营分析专家，能帮管理层分析集团月度经营数据，提出风险预警和改进建议"）
3. AI 基于意图描述，调用已有 PromptBuilder + LLMService，生成完整角色草案，包含：
   - 角色名称、bio（L1/L2）
   - knowledge_boundary（L3）
   - capability_boundary（L4）
   - capability_level（L4，默认 A1）
   - 治理属性建议：category、owner、business_domain、visibility
4. 草案以结构化卡片形式展示给用户，每项可单独编辑调整
5. 用户确认后，一键保存为 draft 角色——数据落地到已有的 RoleAsset + RoleVersion + RoleVersionField (EAV) 结构中
6. 用户后续仍可手动绑定知识库、手动测试、手动发布

**AI 协作式创建与手动创建的关系**：

| 维度 | 手动创建 | AI 协作创建 |
|---|---|---|
| 入口 | 原创建页（逐项填写表单） | 新增"AI 创建"入口（对话式） |
| 数据落地 | 同一结构（RoleAsset + RoleVersion + EAV） | 同一结构 |
| 用户控制 | 全手动 | AI 生成草案 + 人确认/调整 |
| 适用场景 | 精确配置、已有明确需求 | 快速创建、探索性需求 |
| 互斥性 | 不互斥——两种入口并存 | 不互斥——两种入口并存 |

**实现量（完整 AI 功能闭环）**：

| 需新增的工作 | 说明 |
|---|---|
| Prompt template 设计 | 角色意图 → 角色草案的 LLM prompt，输出结构化 JSON |
| LLM 返回解析 | JSON 解析 + 异常处理 + fallback 逻辑 |
| 前端 AI 创建入口 | "AI 创建"按钮 + 对话输入框 + 草案卡片展示 + 逐项编辑 + 一键保存 |
| 前端交互状态管理 | 加载态、错误态、超时态、部分生成态 |
| AI 草案质量验证 | 测试用例覆盖 AI 生成的角色草案可正常保存和使用 |

**风险等级**：

| 维度 | 等级 | 说明 |
|---|---|---|
| 相对（vs 其他 AI 功能） | 最低 | 只涉及角色创建路径，不涉及运行时执行或跨系统调用 |
| 绝对 | 中 | AI 生成内容可能不准确；LLM 调用有成本和延迟风险；前端交互比简单表单更复杂 |

**缓解措施**：

1. AI 草案不自动保存——用户必须逐项确认或调整后才可提交
2. AI 草案的每项字段可单独编辑覆盖——AI 生成是起点而非终点
3. UI 标注"AI 生成草案，请根据实际情况确认和调整"
4. 如果 LLM 调用成本/延迟不可控，降级为"仅生成边界声明建议文本（原 DD-10 方案）"，不生成完整角色草案
5. 手动创建入口始终保留——AI 创建不是唯一路径
6. **如果 DD-01/02/05 延期，DD-10 降级为仅生成角色名称+bio 草案（不涉及治理属性和边界声明），待底座实现后扩展完整版**——与 DD-09→DD-03 的降级方案保持对称性

#### A-4：DD-04 升级 — 设计文档 + 端点可达性验证

| 维度 | 说明 |
|---|---|
| 原状态 | DD-04 产出一份设计说明文档，不改变接口 |
| 调整 | 新增验证标准：确认已有 API 端点（GET /role-assets, GET /role-versions/{id}）的响应 schema 是否支撑消费侧调用，记录差距 |
| 风险等级 | 低（验证结果可能发现差距，但差距记录作为 v0.5 输入） |
| 缓解 | 差距记录入 DD-04 文档，不新增接口 |

### 2.4 多版本路线图提案

| 版本 | 主线定位 | 预计周期 | 范式转变 | 关键交付 | 外部依赖 |
|---|---|---|---|---|---|
| v0.4 | 角色资产化与使用入口 | 6-8 周 | **角色创建从"人填表"到"AI 对话式创建 + 人确认"** | DD-01~05, 07~10 | 无 |
| v0.5 | 角色资产治理闭环 + 消费侧 API 实现 | 6-8 周 | **角色使用从"人手动访问"到"消费方可 API 调用"** | 评分门禁、归档策略、知识过期检测、消费侧 REST API 实现 | 无（v0.4 端点验证结果作为输入） |

**路线图关键约束**：

1. v0.5 的消费侧 API 实现需 v0.4 的端点可达性验证结果作为输入。
2. v0.7 的 A3 和决策产品集成需公共契约裁决。**如果裁决延迟**：v0.7 可独立推进 AI 创建深化（从单次对话到多轮迭代优化）和 MCP 服务端扩展，A3 和决策集成待裁决后推进。
3. 每个版本需独立验收，不跨版本承诺。
4. 路线图是方向参考，不是冻结承诺——每个版本启动前需重新做 dossier。

## 3. 对终审方 4 项期望的逐项回应

### E-1：完整的角色资产管理平台

v0.4 交付：治理属性 + 使用台 + 质量看板 MVP + 边界声明补齐 + 中文枚举 + 版本详情 + AI 协作创建。
**仍缺**：RBAC/多租户、评分门禁、归档策略、知识过期检测、模板库。
**补齐路径**：v0.5 补评分门禁+归档策略+过期检测；v0.6 补模板库；RBAC 需裁决。

### E-2：AI 加持的全生命周期运营

v0.4 交付：**AI 协作式角色创建**（DD-10）——首次引入 AI 范式转变。不是"一个表单字段的建议按钮"，而是"角色创建全流程的 AI 对话式交互"。用户说出意图，AI 生成完整角色草案，用户确认后一键保存。
**仍缺**：AI 辅助角色创建深化（多轮迭代优化）、自动质量评估、智能边界维护、使用反馈分析。
**补齐路径**：v0.5 可扩展 AI 辅助测试建议；v0.7 深化 AI 创建（多轮迭代）。

### E-3：数字角色参与业务决策和执行流程

v0.4 交付：使用台为问答式入口。嵌入代码展示提供"如何接入业务系统"的可视指引。
**仍缺**：A2 生成产物、A3 执行动作、决策流程嵌入。
**补齐路径**：v0.6 实现 A2；v0.7 实现 A3（需裁决）和决策流程嵌入。E-3 是产品差异化核心，但需要 3 个版本逼近——v0.4 先建立"角色可被使用"的底座（使用台），后续版本在底座上叠加"可生成"和"可执行"。

### E-4：多样化系统集成方式

v0.4 交付：设计说明文档 + iframe 嵌入代码展示 + OpenAPI 端点文档展示 + 端点可达性验证。
**仍缺**：消费侧 API 实际实现、MCP 服务端、A2A 协议适配。
**补齐路径**：v0.5 实现消费侧 REST API；v0.6 适配 MCP/A2A。
