## 一、理解复述

两份文档的核心信息：

1. **定位升级**：从原 dossier 的"角色资产化与使用入口"升级为"企业数字角色资产运营平台"。平台价值不仅在于"创建角色"，更在于"让角色被组织持续使用、治理和优化"。

2. **MVP 主链路**：`AI 创建 -> 资产治理 -> 测试发布 -> 统一消费 -> 运营证据`。这条链路是产品成立的底线，不应在设计层面缩减。

3. **双层客户模型**：预算/治理客户（关心管理、合规、复用）和业务消费客户（关心拿来用、嵌入场景、调用稳定）。产品必须同时解决治理、消费和证据反哺。

4. **AI 原生原则**：AI 优先参与流程，人承担确认、发布和责任边界。不是"信息化系统 + AI 按钮"，而是 AI 从创建到运营到推荐贯穿产品。

5. **新增设计项**（相比原 dossier 和提案）：
   - DD-11：业务输出 Schema（4 类内置模板 + 自定义字段 + 版本快照）
   - DD-12：业务输出配置体验（面向业务语言 + AI 推荐 + 模板与自定义并存）
   - DD-13：资产市场 AI 推荐入口（业务意图 → 角色匹配 + 可解释推荐 + 运营信号）
   - DD-14：决策产品集成验收边界（双方证据闭合 + 真实决策场景链路）
   - DD-15：Dify 代表场景与验收证据（开放 Agent 平台消费证明）
   - DD-16：统一消费结果状态（6 状态 + 命中规则 + 消费方处理方式）

6. **统一消费能力**：role_id 必填 + role_version_id 可选 + 固定治理外壳 + 可配置业务 Schema + 6 状态 + caller_type/caller_id 记录。三类消费形态（资产目录、Dify、决策产品）共用统一消费能力。

7. **资产市场**：三种视图（业务发现、资产治理、接入），不是普通管理列表。场景入口、推荐入口、资产卡片、角色详情资产包。

## 二、主要赞同点

### 2.1 定位升级方向正确

"企业数字角色资产运营平台"比原"角色资产化与使用入口"更准确。原定位只描述了"做什么动作"，新定位描述了"产品是什么"。运营平台隐含了创建、治理、发布、消费、证据、优化的完整闭环，这与双层客户模型一致。

### 2.2 MVP 主链路逻辑自洽

`AI 创建 -> 资产治理 -> 测试发布 -> 统一消费 -> 运营证据` 是一条完整的价值链。如果只做前半段（创建+治理+发布）而不做后半段（消费+证据），角色只是"被管理的配置对象"，不是"被运营的企业资产"。消费入口和运营证据是让资产从"管理侧工具"升级为"组织级平台"的关键转折点。

### 2.3 统一消费能力是正确平台化原则

三类消费形态共用统一消费能力，不为 Dify、决策产品分别定制割裂链路，这是平台产品的正确架构方向。先定义角色如何被消费，再定义不同消费方如何接入。实现切分可以分批，但设计原则不应妥协。

### 2.4 业务输出 Schema 解决了真实问题

没有 structured_result 的角色消费只是"拿到一段自然语言回答"，消费方（尤其决策产品和 Dify workflow）需要的是可解析、可对比、可审计的结构化结果。固定治理外壳 + 可配置业务 Schema 的设计既保证了治理一致性，又允许角色多样性。

### 2.5 消费结果状态规则清晰且务实

6 状态覆盖了主要消费结果场景，每个状态有明确命中规则、消费方处理方式和运营含义。boundary_blocked 不等于失败而是治理生效——这个语义区分很重要，符合产品定位。

### 2.6 AI 原生原则边界清晰

"AI 优先参与流程，人承担确认、发布和责任边界"——这条线划得准确。AI 生成草案但人不确认不落库；AI 推荐但不硬推荐；AI 建议但不绕过门禁。这避免了"AI 全自动"和"AI 只是装饰按钮"两个极端。

### 2.7 决策产品集成验收边界设计严谨

双方证据闭合的要求（角色产品侧 5 条 + 决策产品侧 5 条）是可验收的标准，不是模糊的"能调到接口"。明确声明"不由角色产品单方面声明完成"是正确的治理态度。

## 三、主要疑问/挑战

### 3.1 Scope 量级问题：从 7 项到 16 项

原 dossier Scope In 是 7 项（DD-01~05, 07, 08），提案修订后增加到 9 项（+DD-09, DD-10），当前共识稿增加到 **16 项**（+DD-11, 12, 13, 14, 15, 16）。新增的 6 项不是小修补——每一项都涉及新概念、新 API、新 UI、新数据结构和新交互流程。

| 新增项 | 涉及的新概念 | 影响面 |
|---|---|---|
| DD-11 | 业务输出 Schema（output_type + structured_result + 4 模板 + 版本快照） | 新增 schema 字段、EAV 存储、LLM 结构化输出能力、消费 API 输出结构 |
| DD-12 | 业务输出配置体验（面向业务语言 + AI 推荐 + 自定义字段治理） | 新增 UI 配置页、AI 推荐逻辑、自定义字段数据模型 |
| DD-13 | 资产市场 AI 推荐入口（业务意图→角色匹配 + 可解释 + 运营信号） | 新增推荐 API、推荐引擎、3 种市场视图、无匹配信号 |
| DD-14 | 决策产品集成（真实场景链路 + 双方证据闭合） | 跨项目协调、集成适配层、双方验收 |
| DD-15 | Dify 消费证明（开放 Agent 平台消费 published 角色） | Dify 集成代码、消费方身份记录、跨平台调用 |
| DD-16 | 统一消费结果状态（6 状态 + 命中规则 + 消费方处理） | LLM 调用链路改造（状态判定逻辑）、消费 API 响应结构 |

**疑问**：这 16 项是否可以在一个版本（v0.4）内同时保持产品质量和交付节奏？文档原则说"设计范围和实现批次必须分开"——我同意这个原则，但 16 项的设计收口本身就需要大量工作。如果设计收口不完整就进入实现，会回到"设计未收口时直接编码"的停止条件。

**我的判断**：设计目标全部正确，但需要明确切分。建议区分"v0.4 设计视图"（16 项完整设计蓝图）和"v0.4 实现批次"（第一批可验收交付），避免把设计蓝图当作单轮实现承诺。

### 3.2 业务输出 Schema 的技术可行性挑战

DD-11 要求 LLM 生成 conforming to a specific business schema 的结构化输出。这在技术上有真实挑战：

1. **LLM 结构化输出不稳定**：当前主流 LLM（包括 v0.3 已使用的模型）不能 100% 保证按指定 JSON Schema 输出。需要 prompt engineering + 输出解析 + fallback + 校验逻辑。这不是"配置一个 schema 字段就行"，是需要一套完整的结构化输出保障机制。

2. **自定义字段的治理成本**：DD-12 要求自定义字段具备"中文名称、业务含义、是否必填、示例和适用场景"。这意味着自定义字段不是自由 JSON，而是受治理的结构化定义。工作方需要提出具体数据模型来表达这些元信息，并且要设计 AI 如何基于角色描述推荐这些字段。

3. **4 模板不是"内置常量"**：decision_advice、risk_analysis、policy_explanation、review_findings 4 个模板需要具体的字段定义（字段名、类型、业务含义、是否必填、示例）。这些定义需要在 design-delta 中完整给出，不是在 UI 上加个下拉选项就行。

**我的判断**：设计目标正确（角色必须有结构化输出能力），实现需要分层。建议 v0.4 先做最小可行版本（4 模板固定字段 + LLM structured output + 基础校验），v0.4.x 再补自定义字段和 AI 推荐配置。

### 3.3 资产市场的三种视图是全新产品模块

原 dossier 的列表页只需要补 category/owner/visibility 篩选 + 中文枚举。当前共识稿要求三种视图（业务发现、治理、接入）+ AI 推荐入口 + 场景入口 + 资产卡片 + 角色详情资产包。

这不再是"列表页增强"，而是**资产市场——一个新产品模块**。它涉及：

1. 新 UI 架构（3 视图切换、场景分类、推荐交互、接入信息展示）
2. 新 API（推荐接口、资产包详情接口、消费入口信息接口）
3. 新数据结构（场景分类映射、资产卡片聚合信息、推荐理由数据）
4. AI 推荐引擎（意图→角色匹配的 LLM 调用链路）

**疑问**：资产市场的完整设计是否应该在 v0.4 单轮内全部收口？还是先定义完整蓝图，再分批实现？

**我的判断**：设计目标正确（资产目录应该是市场而不是列表），但实现需要切分。建议 v0.4 先做最小资产市场（业务发现视图 + AI 推荐 MVP + 基础资产卡片），治理视图和接入视图在 v0.4.x/v0.5 补齐。

### 3.4 统一消费能力需要新增消费侧 API

原 DD-04 是"纯文档产出，不改变接口"。当前共识稿的统一消费能力要求一个实际可调用的消费侧 API：

1. `POST /role-assets/{id}/consume`（或类似路径）——新增写入接口
2. 输入：role_id (必填) + role_version_id (可选) + query + context + output_type + caller_type + caller_id
3. 输出：固定治理外壳 + structured_result + status + status_reason + boundary_status
4. 生成 usage_record（含 caller_type、caller_id、status）

**这改变了原 dossier 的核心约束**——原 dossier 明确声明"消费侧 API (GET /role-assets, GET /role-versions/{id}) 不改变"和"如果使用台需要新增读写接口或改变已有 API 路径，必须先回写 dossier"。当前共识稿实质上要求新增消费侧读写接口。

**我的判断**：产品需求正确（没有可调用的消费 API 就没有真实消费），但这是一个设计变更，需要回写 dossier。同时，新增消费侧 API 可能触发公共契约裁决——如果决策产品要稳定依赖这个 API 的字段和状态，这个 API 就不是角色产品内部接口，而是跨项目公共接口。

### 3.5 决策产品集成的跨项目依赖风险

DD-14 要求"集成链路必须发生在决策产品消费语境中"，且"双方证据必须能互相对上"。这意味着：

1. 决策产品团队必须配合——角色产品无法单方面完成这个验收
2. 决策产品需要传入"足够业务上下文"、展示角色建议、保留版本和来源信息——这要求决策产品做对应开发
3. 集成过程中可能发现公共契约、读写边界或版本规则问题，必须上提裁决

**疑问**：决策产品团队是否已确认将在 v0.4 周期内配合？如果没有确认，DD-14 的验收可能被阻塞在外部依赖上。

**我的判断**：设计目标正确（决策产品是核心消费方），但需要明确协同条件。建议在进入实现前确认：(1) 决策产品团队的配合时间窗口；(2) 双方对接的技术负责人；(3) 如果决策产品无法在 v0.4 周期内配合，是否降级为"消费能力已就绪，集成待 v0.4.x 完成"。

**P0 级矛盾标注**：共识稿明确声明"决策产品是 MVP 的核心消费方之一，必须在本版本完成集成"（Section 7.8），且"v0.4 正文应要求决策产品真实集成验收"（Section 12.2）。工作方将真实集成延后到 v0.4.x（降级为"消费能力就绪"）与共识稿存在直接矛盾。**这不是工作方可以自行裁决的——必须由终审方/规划方裁决**：要么确认决策产品配合窗口使 v0.4 集成可行，要么修改共识稿措辞允许"能力就绪、集成延后"。

### 3.6 消费结果状态的命中规则需要 LLM 调用链路改造

6 状态不是简单的 HTTP 状态码映射。insufficient_context、insufficient_knowledge、boundary_blocked 需要基于 LLM 输出内容判定：

- boundary_blocked：请求是否超出知识边界/能力边界/能力层级——需要 LLM 在回答时识别并声明边界状态
- insufficient_knowledge：绑定知识是否支撑可靠回答——需要 LLM 或后处理逻辑判定
- insufficient_context：输入是否足够——需要 LLM 在回答时声明信息不足

这要求改造 v0.3 的 LLM 调用链路：在 prompt 中加入状态判定指令，在输出中增加 status/boundary_status 字段，在后端增加状态判定和校验逻辑。

**我的判断**：设计目标正确（消费结果需要有业务语义，不只是 HTTP 200/500），但实现需要评估 LLM 状态判定的可靠性。建议 v0.4 先实现 success + system_failed + boundary_blocked（这三个最可靠），insufficient_context/insufficient_knowledge 在 v0.4.x 补齐（需要更多 prompt 调优），undefined 作为兜底。

### 3.7 AI 推荐入口的"业务意图→角色匹配"精度问题

DD-13 定义推荐入口为"业务任务到角色资产的匹配器"。MVP 不做复杂个性化推荐，先做"解释型匹配推荐"。

但即使是"解释型匹配"，也需要：

1. 用户意图 → LLM 分析意图 → 匹配已发布角色的知识边界/能力边界/适用场景 → 生成推荐理由
2. 已发布角色需要有足够丰富的描述信息（适用场景、业务输出类型、知识范围）才能被准确匹配
3. 如果角色描述信息不够（很多角色可能只有名称和 bio），推荐质量会很低

**疑问**：当前角色的适用场景描述是否足够支撑 AI 推荐？还是需要先补齐角色的适用场景字段？

**我的判断**：设计目标正确，但需要前置条件。建议 v0.4 先要求 AI 创建流程生成的角色草案包含"适用场景描述"字段（由 AI 生成、人确认），为推荐入口提供匹配基础。

### 3.8 测试台与结构化输出/状态的兼容问题

v0.3 测试台只验证角色自然语言回答质量。v0.4 要求角色返回 structured_result + status + boundary_status，测试台必须升级为能验证：结构化输出是否符合 output_type Schema、status 判定是否正确、boundary_status 命中是否合理。这是主链路"测试发布"环节的必要改造——测试台是 consume API 的第一个内部消费方，如果测试台无法验证新增输出格式，角色"测试发布"环节不可走通。

### 3.9 v0.3 已有角色数据兼容性

现有角色缺少 applicable_scenarios、creation_source、output_type、structured_result Schema 等新增字段。如果不设计数据迁移策略，资产市场在 v0.4 上线后会出现大量"信息不完整"角色，影响 AI 推荐和业务发现视图的体验。需要明确：各新增字段的默认值或补填策略、是否需要批量补填 applicable_scenarios、creation_source 如何标记已有角色、是否强制已有角色配置 output_type 才能继续 published。

## 四、建议补充或调整项

### 4.1 补充：角色适用场景描述字段

当前治理属性有 category、owner、business_domain、visibility，但缺少"适用场景描述"——即这个角色适合解决什么类型的业务问题。没有这个字段，AI 推荐（DD-13）和资产市场的场景入口都无法准确运作。

建议：新增 `applicable_scenarios`（适用场景描述，自由文本或结构化），由 AI 创建时生成，人确认后保存。此字段进入版本快照（因为适用场景是角色版本的内容属性，不同版本可能适用不同场景）。**归类建议**：applicable_scenarios 更适合归类为"角色内容属性"（与 bio、边界声明同类）而非"治理属性"（与 category、owner 同类），因为它描述的是角色做什么而非谁管角色。归类不影响实现，但影响设计清晰度。

### 4.2 补充：AI 创建流程必须包含业务输出 Schema 推荐

DD-10（AI 协作创建）当前只生成角色名称/bio/边界声明/治理属性。但 DD-11/12 要求角色必须配置业务输出类型和结构。如果 AI 创建不包含 output_type 推荐，用户保存草案后仍需手动配置输出 Schema，AI 原生体验断裂。

建议：DD-10 的 AI 草案生成范围扩展为包含 output_type 推荐（基于角色意图自动选择 decision_advice/risk_analysis/policy_explanation/review_findings 之一），并在草案中生成该模板的默认字段结构。用户确认后一并保存。

### 4.3 调整：运营看板的数据来源声明

DD-09 运营看板要求覆盖 5 个维度（资产总览、创建运营、质量运营、使用运营、风险运营）。但"AI 草案接受率"和"人工修改率"需要记录 AI 创建的来源标记——当前 usage_records 和 RoleAsset 没有"创建来源"字段（手动创建 vs AI 创建）。

建议：在 RoleAsset 表新增 `creation_source` 字段（枚举：manual / ai_assisted），标记角色是否由 AI 创建流程生成。AI 草案保存时自动标记为 ai_assisted。运营看板基于此字段统计 AI 草案接受率和修改率。

### 4.4 调整：统一消费 API 路径命名

共识稿提到 role_id 必填、role_version_id 可选的输入模型。但当前 API 设计是 `/role-assets/{id}/usage`（usage_records 写入）。新的统一消费能力需要一个更通用的消费入口路径。

建议：消费侧 API 路径使用 `/consume`（而非 `/usage`），语义更准确——消费不只是"使用记录"，是"统一角色消费能力"。路径：`POST /role-assets/{role_id}/consume`。使用记录（usage_records）是消费的结果，不是消费本身。

### 4.5 补充：Dify 集成的技术形态需要早期评估

共识稿正确地不在需求阶段裁决技术形态。但 Dify 集成有几种可能方式（HTTP API tool、OpenAPI schema、自定义插件），每种方式的开发量和稳定性差异很大。工作方需要在设计阶段早期评估哪种方式最适合 MVP，避免实现时才发现选错路径。

建议：在进入实现前，工作方产出一份 Dify 集成技术评估短文（1-2 页），覆盖：(1) Dify 当前支持的接入方式；(2) 各方式的开发量、稳定性和限制；(3) 推荐的 MVP 接入方式及理由；(4) 对统一消费 API 设计的影响。规划方复审后确定。

### 4.6 补充：boundary_status 的具体枚举值

共识稿给出示例 `"knowledge_boundary": "not_applicable", "capability_boundary": "out_of_scope"`，但没有定义 boundary_status 的完整枚举值和命中规则。

建议：boundary_status 应采用**复合结构**（与共识稿 Section 9.4 示例一致），为 knowledge_boundary 和 capability_boundary 各定义独立枚举：

- `within_boundary`：请求在该维度边界内
- `near_boundary`：请求接近该维度边界但未越界
- `out_of_scope`：请求超出该维度边界
- `not_applicable`：该维度边界判定不适用（如系统失败时）

boundary_status 是二者的组合对象：

```json
{
  "knowledge_boundary": "within_boundary",
  "capability_boundary": "out_of_scope"
}
```

命中规则与 6 消费状态联动：success → 各维度 within_boundary 或 near_boundary；boundary_blocked → 至少一个维度 out_of_scope；其他状态 → 各维度 not_applicable。

## 八、总结

**产品方向自洽性**：定位、主链路、双层客户模型、AI 原生原则、统一消费能力——整体逻辑自洽，没有内部矛盾。

**核心链路完整性**：`AI 创建 -> 资产治理 -> 测试发布 -> 统一消费 -> 运营证据` 可以落到可验收场景，但需要统一消费 API（新增写入接口）作为关键连接点。

**设计缺口**：缺少 applicable_scenarios 字段（AI 推荐的前置）、creation_source 字段（运营看板的前置）、boundary_status 完整枚举（消费输出完整性）、AI 创建流程需包含 output_type 推荐（DD-10 与 DD-11/12 的衔接）。

**最大风险**：Scope 量级（16 项）、决策产品集成跨项目依赖、LLM 结构化输出和状态判定可靠性、新增消费侧 API 可能触发公共契约裁决。

**核心建议**：设计视图保持 16 项完整蓝图不缩减；实现分 v0.4 / v0.4.x / v0.5 三批交付；v0.4 优先保证主链路全链路可走通（最小可行版本）；决策产品真实集成延后到 v0.4.x（需终审方裁决）；进入实现前补齐 13 份材料（含审核方补充的 5 份遗漏材料）。
