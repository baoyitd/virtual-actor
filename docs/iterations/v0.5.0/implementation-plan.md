# v0.5.0 实施拆分与批次计划

> 版本：v0.5.0 | 日期：2026-06-11 | Formal Status：Self-Tested
> 当前状态：Design Freeze Status = Effective
> 用途：把已冻结的 `v0.5` 设计真源转成可执行的实施批次；只切分实现顺序，不缩减设计蓝图与最终验收目标

---

## 1. 使用规则

本计划只回答四件事：

1. `v0.5` 已冻结设计如何拆成可执行批次
2. 每个批次先做什么、后做什么
3. 每个批次做到什么程度才算可进入下一批
4. 哪些事情可并行，但不应混进产品批次定义

本计划不改变：

1. `Scope In / Scope Out`
2. 已冻结的 `DD-17 ~ DD-24`
3. 已冻结的 `US-22 ~ US-30`
4. 最终验收口径

固定原则：

1. 设计蓝图和实现批次必须分开；分批只改变落地顺序，不改变最终产品目标。
2. 任一批次若发现字段边界、页面结构、外供语义或治理规则需要改动，先登记到 `implementation-notes.md`，再回写真源。
3. 未完成真实运行效果验证前，不得把“字段保存成功”当成“能力已真实生效”。
4. 未完成代表环境真实调用前，不得把外供能力声明为已闭合。

## 2. 总体拆分

`v0.5` 主体实施按 4 个批次推进：

1. **Batch 1：领域基础与门禁后端**
2. **Batch 2：统一工作区与治理界面**
3. **Batch 3：运行效果与外部复用闭环**
4. **Batch 4：全链路自测与验收材料**

另有 1 条并行治理线：

- **Parallel G1：仓库治理与发布元数据清理**

它不属于 `v0.5` 产品能力本身，但应在升级 `Formal Status` 前清掉。

## 3. 批次计划

### 3.1 Batch 1：领域基础与门禁后端

**目标**

先把 `v0.5` 的数据结构、后端契约和门禁规则立住，避免前端和外供链路搭在不稳定底座上。

**覆盖设计项**

1. `DD-17` 角色定义层重构
2. `DD-18` 消费契约层后端与生命周期规则
3. `DD-21` 发布门禁补充
4. `DD-24` legacy 兼容后端
5. 管理员数据资产管理页对应的数据模型和接口底座

**覆盖用户场景**

1. `US-22` 部分
2. `US-23` 部分
3. `US-24` 部分
4. `US-25`
5. `US-29`
6. `US-30`

**本批必做**

1. 角色版本字段与存储结构升级，承接 `L1-L4`
2. `main_duty_cluster / point_of_view / knowledge_refs / knowledge_boundary / data_asset_bindings / output_mode / output_type / output_schema / model_binding` 的后端读写闭合
3. `applicable_scenarios / usage_notes / support_basis_summary` 的保存结构与说明卡生命周期状态
4. `待确认更新` 的判定与阻断规则
5. 治理主路径 `owner / business_domain / category` 的阶段门禁
6. `structured` 路径条件门禁
7. legacy 角色兼容读取、补齐提示与阻断规则
8. 数据资产管理最小模型、状态字段、角色绑定接口
9. AI 草案接口与保存接口对齐到 `v0.5` 字段骨架

**本批不宣称完成**

1. 高保真交互体验闭环
2. 知识 / 数据 / 输出契约的真实运行效果闭环
3. 外供生成与代表环境验证

**进入下一批条件**

1. 数据模型、迁移、Schema 和后端接口已稳定
2. 门禁规则能按冻结口径返回明确阻断
3. 说明卡生命周期不再依赖前端临时拼装
4. legacy 不会因新字段直接读坏
5. 数据资产已可被管理员维护、被角色绑定

把 `v0.5` 的主使用链路做出来，让角色创建者、治理方和消费方能在界面上按冻结后的信息架构完成主要动作。

**覆盖设计项**

1. `DD-17`
2. `DD-18`
3. `DD-19`
4. `DD-20`
5. `DD-21`
6. `DD-24`
7. 管理员数据资产管理页前端

**覆盖用户场景**

1. `US-22`
2. `US-23`
3. `US-24`
4. `US-25`
5. `US-26`
6. `US-29`
7. `US-30`

**本批必做**

1. 统一工作区骨架：章节导航、主编辑区、进度摘要
2. AI / 手工同骨架创建体验
3. `L1-L4` 页面表达与高级项折叠
4. `使用前说明与调用预览` 的说明卡优先结构
5. 说明卡轻量修订、重新生成、重新确认动作
6. 治理与发布页：主路径字段、补充治理项、发布检查与回跳
7. 数据资产管理页与角色页绑定选择器

**本批不宣称完成**

1. Tool / Skill 供给物真实生成
2. Dify / Codex 代表环境验证
3. 外供后的平台回写闭环

**进入下一批条件**

1. `US-22 ~ US-26`、`US-29 ~ US-30` 主界面路径基本可走通
2. 说明页、治理页、数据资产页已按冻结结构落地
3. UI 不再与高保真原型发生结构性偏差
4. AI 草案与手工编辑都回落到同一工作区模型

### 3.3 Batch 3：运行效果与外部复用闭环

**目标**

闭合 `v0.5` 最容易被“页面有了就算完成”偷换的两条链路：运行效果真实性和外部复用真实性。

**覆盖设计项**

1. `DD-17` 剩余运行效果部分
2. `DD-18` 说明卡与消费前预览对运行结果的对应关系
3. `DD-22` 外供稳定载体
4. `DD-23` 外部复用代表验证与回写闭环

**覆盖用户场景**

1. `US-23` 运行效果部分
2. `US-27`
3. `US-28`

**本批必做**

1. 平台内 `test / consume` 路径真实承接知识绑定语义
2. `knowledge_boundary` 对超边界输入的限制 / 降级表达
3. 数据能力真实走平台查询层，而不是只显示绑定摘要
4. 不同数据资产绑定导致不同结果
5. `freeform / structured` 两条输出路径在运行结果上真实分流
6. `Tool package / Skill package` 生成、版本绑定与文件契约闭合
7. 外供物复用同一张说明卡当前保存版
8. 外供后的平台回写、`usage_record`、状态与边界追溯闭合
9. `Dify` 与 `Codex` 代表环境真实调用验证

**本批不宣称完成**

1. 全量验收证据归档
2. `Formal Status = Self-Tested`

**进入下一批条件**

1. 运行效果型测试不再停留在接口字段层
2. 外供链路不是“下载文件成功”，而是代表环境真实可用
3. 回写闭环已能证明外部复用未绕开平台 `consume` 语义

### 3.4 Batch 4：全链路自测与验收材料

**目标**

把 `v0.5` 从“代码基本做完”推进到“可以主张 Self-Tested”的证据状态。

**覆盖设计项**

1. `DD-17 ~ DD-24` 全部

**覆盖用户场景**

1. `US-22 ~ US-30` 全部

**本批必做**

1. 执行并补齐自动化 API 测试
2. 执行并补齐程序化 UI 测试
3. 执行运行效果型测试
4. 执行 `Dify / Codex` 外部环境验证
5. 执行人工手动冒烟与 Human UI/UX 检查
6. 回写 `implementation-notes.md`
7. 产出 `test-results`、必要运行态证据与交付说明
8. 仅在证据闭合后，才允许把 `Formal Status` 从 `Draft` 升为 `Self-Tested`

**本批通过标准**

1. `delivery/test-plan-v0.5.md` 和 `delivery/test-cases-v0.5.md` 的范围被真实执行
2. 偏差已登记并裁决，不存在未登记的设计漂移
3. 高风险路径有人工证据，不用自动化代替人工验证
4. 外部复用与运行效果证据不再只靠代码走查主张

## 4. 并行治理线

### 4.1 Parallel G1：仓库治理与发布元数据清理

这条线不属于 `v0.5` 产品能力，但会影响后续版本状态升级与发布治理。

**当前问题**

1. `iteration-guard` 仍受 `portfolio-sync.md`
2. `delivery/release-notes.md`
3. `v0.4` 历史口径残留

影响，当前不构成 `v0.5` 开发启动阻塞，但会阻断后续正式状态升级或发布声称。

**处理原则**

1. 可与 Batch 1 / Batch 2 并行
2. 不得反向改变 `v0.5` 设计范围
3. 应在主张 `Self-Tested` 前清掉

## 5. 实施顺序与停止条件

推荐顺序固定为：

```text
Batch 1
  -> Batch 2
  -> Batch 3
  -> Batch 4
```

`Parallel G1` 可并行，不改变主批次顺序。

实施阶段出现以下情况必须停止并回写真源：

1. `L1-L4` 被实现成另一套步骤逻辑，导致骨架失真
2. `使用前说明与调用预览` 被重新实现成第二个大表单页
3. `L3` 再次退化为自由文本能力说明
4. `freeform` 被实现成“不完整占位态”
5. 外供被偷换成“导出接口地址或静态文档”
6. 运行效果型测试无法证明知识 / 数据 / 输出契约真实生效

## 6. 一句话结论

> `v0.5` 的实施顺序应先立住领域结构和门禁底座，再交付主工作区和治理体验，再闭合运行效果与外部复用真实性，最后才主张 `Self-Tested`。
