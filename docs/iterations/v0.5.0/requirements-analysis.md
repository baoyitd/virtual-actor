# v0.5.0 需求分析

> 版本：v0.5.0
> Formal Status：Self-Tested
> 最后更新：2026-06-11
> 用途：吸收上位项目对角色资产的逻辑框架，基于 `v0.4` 现有能力判断本产品下一轮应补的真实缺口

---

## 1. 输入来源与固定边界

本轮新增输入来自两部分：

1. 上位项目 `eve` 提供的角色资产逻辑框架与验证型 handoff：
   - `va-platform-role-asset-validation-handoff.md`
   - `role-asset-framework.md`
   - `ai-agent-capability-design-sop.md`
   - `terminology-standard.md`
2. 本项目既有定位与基线：
   - 本产品仍是“一个集团/企业的角色资产管理平台，帮助企业沉淀、管理、运营和复用角色资产”
   - `v0.4` 已具备角色创建、知识绑定、测试、发布、消费和部分市场化能力

本轮固定边界：

1. 上位项目交给我们的首先是**角色资产成立逻辑**，不是一个必须照抄的实现对象模型。
2. 角色资产不是个人、不是岗位名、不是 prompt 人设，也不是某个页面里的表单对象。
3. 角色资产的最小成立单元是 `职责簇`，不是完整岗位，也不是单个微动作。
4. 本轮重点不是“为了管理再加一层管理对象”，而是让当前平台产出的角色更符合真实世界角色的构成，并能被外部 AI 环境复用。
5. 如果某项吸收不能明显提升角色的真实度、可运行性、可复用性，就不应进入本轮主设计。

## 2. v0.4 基线与本轮问题定义

`v0.4` 已解决“平台里能不能跑出一个角色”的问题，但还没有完全解决两个更高一级的问题：

1. **平台里的角色，像不像一个真实世界的数字职责资产**
2. **这个角色，能不能被平台外的 AI 环境稳定复用**

当前基线已有：

1. 角色资产创建、编辑、测试、发布、归档和版本追溯。
2. 知识绑定、真实知识平台联动、结构化输出、消费状态与边界状态。
3. AI 协作创建、资产市场推荐、统一消费 API 等面向使用的主链路。

因此，v0.5 不是从零发明一套“角色能力清单”，而是在现有底座上补四类真实缺口：

1. **角色职责粒度仍不够清楚**：
   - 当前角色更像“配置好的 AI 角色”，还不够像“收口到一组稳定职责簇的数字角色资产”。
2. **角色资产说明能力不足**：
   - 对消费者和外部调用方来说，仍不够容易在调用前理解“这个角色怎么用、靠什么成立”。
3. **发布判断仍偏技术可跑**：
   - 当前更像“接口是否就绪”，还不够像“资产是否已经达到对外复用的最小成熟度”。
4. **外部复用缺少稳定供给载体**：
   - 当前已经有 `consume API`，但还不像一个可被 Codex、Dify 等外部 AI 环境直接拿走复用的稳定供给物。

除此之外，还存在一个直接影响本轮落地质量的体验缺口：

5. **角色创建 / 编辑表单理解与操作成本过高**：
   - 当前角色资产表单项较多，且以瀑布式长表单为主。
   - 这会直接抬高理解成本和操作门槛，削弱本轮新增角色规格与说明能力的真实可用性。
   - 因此，这不是单纯的视觉优化项，而是角色资产能力落地的必要 requirement。

本轮优先级也据此固定为：

```text
方向 2（如何被主流 AI 环境使用）
  ->
方向 1（数字角色本身的可信与清晰）
  ->
方向 3（更强的人类管理属性）
```

也就是说，本轮先组合推进：

```text
外部复用能力 + 角色本体强化
```

而不是先把管理层做重。

## 3. 2026-06-08 逐项复审结论

### 3.1 保留项：`main_duty_cluster` 收口到用户可理解的 `核心职责`

本轮确认：

1. `main_duty_cluster` 是角色成立的核心，但用户侧显示名应改成更直白的 `核心职责`。
2. `角色定位` 不保留；它对角色能力和消费理解的实际帮助不足，且容易与其他文字型字段重复。
3. 原 `来源物理世界角色` 不再放在 `L1`，而是转为治理侧的 `企业实际角色映射`：
   - 作用是表达数字角色与企业实际角色的映射关系
   - 支持多角色输入
   - 不进入角色本体主骨架
4. 目标是让角色粒度更准、消费者更容易理解，不是增加新的管理层。

结论：

> **保留。属于角色本体核心 requirement。**

### 3.2 不保留项：`负责什么 / 不负责什么` 不单列 requirement

本轮确认：

1. 这类控制可以由外部调用方和使用场景控制，不必全部由平台内部单独定义。
2. 当前平台已有的知识、能力、职责说明、输出结构等配置，已经在实质上限定了角色能干什么。
3. 单独再加一组“负责 / 不负责”字段，边际价值不足，且容易增加重复表达与治理负担。

结论：

> **不单列为本轮平台 requirement，不新增独立字段组，不单独设为发布门禁。**

### 3.3 合并保留项：角色资产最小说明能力

本轮将原先分开的“运行边界最小表达”和“支撑资产最小可解释性”合并为一项：

> **角色资产最小说明能力**

它不属于角色本体核心结构，而属于**发布 / 市场 / 复用侧的说明能力**，主要解决两类问题：

1. **怎么用**
   - 适合什么场景
   - 调用前需要什么前提
   - 当前更偏建议型还是执行辅助型
   - 命中不同状态时，上游系统怎么处理
2. **靠什么成立**
   - 这个角色主要靠什么支撑
   - 是知识主导、规则主导、流程主导，还是模型推理主导
   - 是否已有测试 / 验证基础

本轮确认：

1. 这项应该保留。
2. 它本质上是“角色资产说明”，不是一套新的治理系统。
3. 不要求这一轮把六类资产做成六套对象中心。
4. 不要求这项直接上升为权限系统、审批系统或动作控制系统。

结论：

> **保留。属于说明层 requirement，不做重对象化，不做重治理。**

### 3.4 保留项：发布门禁只做现有机制补充

本轮确认：

1. 不应新造一套“资产发布门禁系统”。
2. 平台已经有发布门禁机制；如果本轮新增了角色成立的核心 requirement，现有门禁自然应补充相应检查项。
3. 这属于已有机制的扩展，不是新流程、新审批系统或新产品对象。

结论：

> **保留，但只作为现有发布门禁机制的补充扩展。**

### 3.5 保留项：对外复用需有稳定供给载体

本轮确认：

1. 当前平台已有 `published role version + consume API + structured_result + status/boundary_status + usage_record` 的复用底座。
2. 但如果要让平台外的 AI 环境稳定复用一个角色，仅有原始 API 还不够。
3. 平台需要把“适合外部复用的已发布角色版本”包装为稳定供给载体。
4. 这一轮确认的对外供给形态先收口为：
   - `Tool package`
   - `Skill package`
5. 这些外部供给形态必须建立在现有 `consume API` 之上，而不是另起一套运行平面。
6. 不要求所有已发布角色默认都外供；但平台必须支持把**适合外部复用的已发布版本**生成稳定供给载体。
7. “是否进入外供”应由用户在已发布版本上显式执行“生成外供”动作表达，不新增独立外供开关字段。
8. 外部复用后，关键使用信号必须继续回写到平台侧，不能丢身份、版本、状态、边界和使用记录。
9. 当前 `L3` 不做版本快照，因此本轮外供冻结的是身份、消费契约、输出契约与回写语义；数据能力仍按当前生效配置工作，相关限制必须被如实写入说明卡、门禁与外供说明。

结论：

> **保留。属于本轮 P0 requirement。**

### 3.6 新增保留项：角色创建 / 编辑交互重设计

本轮新增用户要求：

1. 当前角色资产表单页涉及新建、编辑等场景，字段较多，且以瀑布式排列为主。
2. 这种组织方式不利于用户理解，也不利于操作完成。
3. 本轮新增的角色规格、资产说明和外部复用准备，如果仍叠加在现有表单形态上，用户端会出现更高的理解负担和填写门槛。

因此，本轮应把这项明确收口为：

> **以降低理解成本和降低操作门槛为目标，对角色资产表单页进行重新设计。**

边界同时固定：

1. 这不是单纯“做更好看”的 UI 美化项。
2. 这也不是现在就预先冻结具体交互解法。
3. 当前只在需求层确认：角色新建 / 编辑体验必须被重新组织，目标是让用户更容易理解、更容易完成，而不是继续堆字段。

结论：

> **保留。属于本轮 P0 requirement。**

## 4. 需求层最终收口

综合以上复审，本轮在需求层只正式保留以下六项：

1. **角色规格强化**
   - 核心是 `main_duty_cluster` 以用户可理解的 `核心职责` 方式被明确表达。
   - `企业实际角色映射` 进入治理侧，作为数字角色与企业实际角色的映射关系，支持多角色输入。
2. **角色资产最小说明能力**
   - 为市场、发布、复用和外部调用提供“怎么用、靠什么成立”的最小解释。
3. **AI 协作创建围绕角色规格与说明升级**
   - 延续 `v0.4` 已确定的“自然语言输入 -> 结构化角色草案 -> 人确认后保存”主链路。
   - `v0.5` 不是重写 AI 创建方案，而是在既有结构化草案能力上，继续把草案内容升级到“角色规格 + 消费契约”的层面。
4. **角色创建 / 编辑交互重设计**
   - 以降低理解成本和降低操作门槛为目标，重新组织角色资产表单页。
5. **现有发布门禁机制补充**
   - 把本轮新增的角色成立核心 requirement 纳入现有门禁检查项。
6. **对外复用的稳定供给载体**
   - 让合适的已发布角色版本能被稳定打包给外部 AI 环境复用，并继续回写关键使用信号。

明确不保留为本轮 requirement 的内容：

1. 独立 `RoleAssetDefinitionPackage` 对象。
2. 定义包中心、翻译工作台或导入中心。
3. 六类资产各自独立的一等子系统。
4. 单列“负责什么 / 不负责什么”字段组。
5. 新造一套发布门禁体系。
6. 动作执行平面、审批链、权限系统或完整外部分发中心。

## 5. 对方向 2 的固定约束

本轮既然把“如何被主流 AI 环境使用”放在更高优先级，需求层还应固定以下约束：

1. 外部复用的最小单位是**单个已发布角色版本**，不是模糊的“某个角色接口”。
2. 外部复用不得丢失以下关键语义：
   - `role_id`
   - `role_version_id`
   - `structured_result`
   - `status`
   - `boundary_status`
   - `usage_record`
3. 外部供给形态建立在现有 `consume API` 之上，不另造平行运行平面。
4. 本轮只先要求两类发布形态：
   - `Tool package`
   - `Skill package`
5. 本轮只要求**代表性外部环境验证**，不承诺一次冻结所有平台、所有协议、所有通道。
6. 外部复用后，关键使用信号必须继续回写到平台侧，不得切断运营和优化闭环。
7. 外供物里的角色说明应复用平台内同一张“使用前说明与调用预览”说明卡真源，不另造第二套说明。

## 6. 一句话结论

> **v0.5 最应该吸收的，不是“再新增一层角色管理对象”，而是把上位项目对“角色由什么构成”的逻辑框架收进当前角色资产本体与外部复用链路中，并同步降低角色创建 / 编辑的理解成本和操作门槛，让平台里的已发布角色版本既更像真实职责资产，也更适合被外部 AI 环境稳定复用。**

## 7. 2026-06-09 补充校准：三层结构与两类用户

本轮进一步确认：

`v0.5` 不应再把“角色定义”“消费前说明”“资产治理要求”揉成一块页面叙事。

概念上，应拆成 3 层：

1. **角色定义层**
   - 唯一主骨架调整为 `L1-L4`
   - 其中新的 `L1` 已吸收原 `L2` 的判断方式字段
   - 它回答的是：**一个角色本身由什么组成**
2. **消费契约层**
   - 它回答的是：**别人怎么用这个角色、为什么可以信它**
   - 它不是角色本体，但决定角色能否被正确选择、正确调用、正确接入
3. **资产治理层**
   - 它回答的是：**这个角色作为资产如何被管理、发布、分发和追溯**
   - 它不应反向定义角色本体

交互上，应按 2 类用户组织：

1. **角色能力侧用户**
   - 负责定义和维护 `L1-L4`
   - 同时维护与调用相关的消费契约
2. **资产治理侧用户**
   - 负责治理字段、测试证据、发布门禁、外供生成和追溯闭环
   - 不应把治理动作混成角色本体定义流程

### 7.1 字段校准结论

#### A. 必须保留在角色定义层（`L1-L4`）的字段

这些字段会直接影响角色的判断方式、知识依据、数据能力、输出方式或运行行为：

1. `name`
2. `bio`
3. `main_duty_cluster`
4. `point_of_view`
5. `decision_style`
6. `identity_background`
7. `speaking_style`
8. `knowledge_refs`
9. `knowledge_boundary`
10. 版本级数据能力绑定（暂以 `data_asset_bindings` 指代）
11. `output_mode`
12. `output_type`（仅在结构化输出路径下出现）
13. `output_schema`（仅在结构化输出路径下出现）
14. `model_binding`

固定口径：

1. 原 `L2` 不再单独保留为一层，而是并入新的 `L1`。
2. 独立 `responsibility_boundary` 不再作为本轮角色定义输入项保留。
3. 旧的 `capability_boundary / capability_level / collaboration_mode` 默认不再保留在当前正文中；只有后续形成真实运行时意义，才允许作为派生标签或附录议题回收。
4. `decision_style` 之所以继续保留，是因为它当前已经真实进入角色 prompt，确实会影响角色行为，不是纯展示字段。

#### B. 从角色定义层移出，进入消费契约层的字段

这些字段不定义“这个角色是什么”，而定义“这个角色怎么被正确使用”：

1. `applicable_scenarios`
2. `usage_notes`
3. `support_basis_summary`

它们仍然是本轮必需项，但应被视为**消费侧 requirement**，不是角色本体 requirement。

固定口径：

1. `applicable_scenarios` 有系统价值，会影响选择、推荐与发布门禁，但当前不作为 `consume` 运行时控制字段。
2. 这一层在页面外显上应命名为 `使用前说明与调用预览`，并以系统生成说明卡为主，而不是第二个重表单页。

#### C. 从角色定义层移出，进入资产治理层的字段

这些字段服务于治理、运营、分发和责任归属，不应占据 `L1-L4` 主骨架：

1. `category`
2. `owner`
3. `maintainer`
4. `business_domain`
5. `visibility`
6. `tags`
7. `enterprise_role_mapping`
8. 测试记录与测试评分
9. 发布门禁结果
10. 外供生成状态
11. 使用记录与追溯记录

固定口径：

1. 治理页主路径优先放 `owner / business_domain / category`。
2. `visibility / maintainer / tags / enterprise_role_mapping` 保留但降为补充治理项，其中 `visibility` 当前不按权限控制语义设计。

#### D. 降级为高级 / 补充项、不得做成本轮角色成立硬门禁的字段

这些字段可能影响体感或补充理解，但不应再抢占主路径：

1. `decision_style`
2. `identity_background`
3. `speaking_style`
4. `model_binding`

它们可以保留，但应满足以下约束：

1. 不属于角色成立硬门禁
2. 不应主导页面主叙事
3. 如果后续验证表明对真实使用帮助很弱，应允许继续弱化或隐藏

#### E. 默认移出当前正文、只有形成真实运行意义才允许回收的字段

这些字段当前更像说明文案或抽象标签，而不是会在运行时真实生效的能力真源：

1. `capability_boundary`
2. `capability_level`
3. `collaboration_mode`

固定口径：

1. 当前平台没有与这些字段严格对应的统一运行时授权链，不应先把它们继续写成角色资产正文。
2. 若后续形成真实的系统能力 / 通用能力 / 执行策略运行时闭环，它们最多以派生标签或重新定义后的字段回收。
3. 在此之前，它们不应继续主导 `L3` 叙事，也不应作为发布门禁前提。

### 7.2 对页面结构的直接影响

因此，后续设计与原型必须满足：

1. `L1-L4` 必须重新成为角色定义页的主叙事。
2. 页面外显名应为 `使用前说明与调用预览`；它属于**消费契约视图**，但应以系统生成说明卡为主，而不是第二个重表单页。
3. `发布前检查`、`治理字段`、`外供生成` 和 `追溯` 应明确落在**资产治理侧**。
4. `使用前说明与调用预览` 只表达事实限制，不承担 `待补齐 / 不可发布 / 不合格` 之类门禁裁决。
5. 任何页面组织都不得再让用户误以为：
   - `Step 01-04` 可以替代 `L1-L4`
   - 说明卡就是角色本体
   - 治理字段可以定义角色能力
6. `L3` 在角色页中应只表达“是否绑定版本级数据能力”，不再回到说明性能力文本。
7. `L4` 应先分清“自由输出 / 结构化输出”，再展示模板与高级运行配置。
8. `使用前说明与调用预览` 应固定为 5 个模块：
   - 头部摘要（只读）
   - 这个角色适合干什么
   - 怎么正确使用
   - 你将得到什么
   - 为什么可信 / 当前限制

### 7.3 阶段-必填矩阵

本矩阵回答一个关键问题：

> **角色能力侧和资产治理侧，是否必须在第一次创建时一次性全部定义完？**

结论是：

> **不用。**

这里定义的是**完成阶段**，不是新增数据库状态或版本状态枚举。它只是用来约束：

1. 起草时先补什么。
2. 进入 `test` / 开始试用前至少要补到什么程度。
3. 给别人消费前哪些信息必须完整。
4. 正式发布 / 外供前哪些治理项必须闭合。

平台 formal 状态仍只保留：

1. `draft`
2. `test`
3. `published`
4. `archived`

本轮固定语义：

1. `01 角色定义工作台` 保存后，当前可编辑版本处于 `draft`。
2. `02 使用前说明与调用预览` 保存当前说明卡后，当前可编辑版本进入 `test`。
3. `03 试用与测试` 只对 `test` 角色执行 / 复测，不再承接 `draft -> test` 状态切换。
4. `04 治理与发布` 承接 `publish / archive`。
5. `05 正式消费` 与 `06 外供与追溯` 都建立在已发布版本之上，是发布后的复用面，不是新增状态。
6. `archived` 也在 `04` 承接；归档后退出活跃市场、正式消费和新外供，但历史版本、使用记录和外供记录继续可查。

| 项目 | 起草角色 | 进入 `test` / 试用与测试 | 可供他人消费 | 正式发布 / 外供 |
| --- | --- | --- | --- | --- |
| 角色定义基础：`name` `bio` | 必填 | 必填 | 必填 | 必填 |
| 新 `L1` 核心锚点：`main_duty_cluster` | AI 应优先生成；允许草稿后补 | 必填 | 必填 | 必填 |
| 新 `L1` 主路径：`point_of_view` | AI 可先给草案；允许后补 | 推荐完整 | 推荐完整 | 推荐完整 |
| 新 `L1` 高级 / 补充项：`decision_style` `identity_background` `speaking_style` | AI 可先给草案；允许不完整 | `decision_style` 推荐完整；其余可选 | 推荐完整 | 推荐完整 |
| `L2` 真实绑定：`knowledge_refs` | 起草可暂空 | 可暂空；只要知识状态已明确即可进入 `test` 并开展试用 | 可暂空；但必须让消费方看到真实知识状态 | 若已绑定则纳入追溯；未绑定也合法，但不得误表述为知识支撑型角色 |
| `L2` 声明：`knowledge_boundary` | 可先由 AI 起草，允许后补 | 若已绑定知识则推荐补齐；无知识绑定则不强制填写 | 若已绑定知识则应完整；无知识绑定则系统展示“未绑定真实知识”状态 | 外供时必须展示真实知识状态；有绑定则展示边界，无绑定则展示未绑定说明 |
| `L3`：版本级数据能力绑定（`data_asset_bindings`） | 允许为空 | 允许为空；若已绑定，则应能在平台内测试链中真实生效 | 允许为空；若已绑定，则必须让消费方看到数据能力摘要；为空则明确显示未授权状态 | 允许为空；若已绑定，则必须引用管理员已配置的数据资产项；当前不做版本快照，外供仅冻结身份与契约，不冻结数据能力 |
| `L4`：输出方式（`output_mode`） | 系统默认 `freeform`；允许沿用默认 | 为真实试用应明确当前是自由输出还是结构化输出 | 必须对消费方可见 | 必须随外供说明展示 |
| `L4`：结构化输出（`output_type` `output_schema`） | 仅在选择 `structured` 时出现 | 若选择结构化输出，则试用前必须完整；若自由输出则不要求 | 若选择结构化输出，则必须完整；若自由输出则不要求 | 若选择结构化输出，则必须完整；并基于平台模板而非空白 schema |
| `L4`：运行配置（`model_binding`） | 默认继承系统值；不要求第一次改动 | 沿用默认即可；有明确需要时再覆盖 | 沿用默认即可；有明确需要时再覆盖 | 沿用默认即可；有明确需要时再覆盖 |
| 消费契约：`applicable_scenarios` `usage_notes` `support_basis_summary` | AI 可先给草案，系统预生成说明卡；不强制第一次补齐 | 推荐补齐 | 必填 | 必填，并进入外供说明 |
| 资产治理：`owner / business_domain / category` 为主路径；`visibility / maintainer / tags / enterprise_role_mapping` 为补充治理项 | 可后补，不应拦住创建 | 可后补；进入 `test` 后仍可继续补齐，不作为前置阻断 | 进入“可供他人消费”前，`owner / business_domain / category` 必须全部完整 | 发布 / 外供前必须按现有门禁闭合，且 `owner / business_domain / category` 全部为硬门禁 |
| 测试与发布证据 | 不要求 | 进入真实试用链路 | 至少已有可说明的试用 / 测试基础 | `v0.4` 既有门禁 + `v0.5` 新增项全部闭合 |

由此固定：

1. **起草阶段先保证角色能被描述出来**，而不是先把治理表单填满。
2. **进入 `test` 阶段先保证角色真的能跑起来**，因此运行项要先于治理项闭合。
3. **消费契约在“给别人用之前”必须完整**，但不必在第一次创建时强压用户一次性写完。
4. **治理项天然晚于角色能力项闭合**，否则会把“做出角色”变成“先填完资产台账”。
5. **治理主路径不是纯展示字段**：`owner / business_domain / category` 在“可供他人消费”和“正式发布 / 外供”阶段都必须完整。
6. **`05 / 06` 不是状态**：它们只是已发布版本的两种复用面。
7. **`archived` 是生命周期终态，不是后续页面**：归档后不再参与活跃市场、正式消费和新外供，但历史追溯持续保留。

### 7.3.1 页面主链顺序与动作归属

当前角色主链页面顺序固定为：

1. `01 角色定义工作台`
2. `02 使用前说明与调用预览`
3. `03 试用与测试`
4. `04 治理与发布`
5. `05 正式消费`
6. `06 外供与追溯`

补充说明：

1. `数据资产管理` 是管理员配套页，不进入角色主链编号。
2. `02 使用前说明与调用预览` 的保存动作会把当前可编辑版本推进到 `test`；因此 `03 试用与测试` 只承接对 `test` 角色的验证，不再负责 `draft -> test`。
3. `04 治理与发布` 承接治理字段、门禁和版本级 `publish / archive` 动作。
4. `05 正式消费` 与 `06 外供与追溯` 都是发布后的复用面；二者都依赖已发布版本，但不互为前置，也不新增状态。
5. `archived` 由 `04` 承接；归档后角色退出活跃市场、正式消费和新外供，但历史版本、外供记录与使用记录继续可查。
6. 页头只放当前页面的全局动作；依赖输入内容的执行动作留在输入区或对应模块内。
7. 跨页面跳转统一通过阶段导航、角色概览页和阻断提示里的“去补齐”入口承接，不在每个页面页头重复堆跳转按钮。
8. `03 试用与测试` 页只保留测试前必要摘要：角色 / 当前状态 / 说明卡状态 / 知识状态 / 数据能力状态 / 输出方式，以及“查看 02 使用前说明”的入口；完整说明卡不在该页重复铺开。

### 7.4 AI 协作创建的固定分工

本轮对 AI 的定义继续固定为：

> **用户输入一段自然语言描述，系统生成结构化角色草案，人再确认和补齐。**

因此：

1. AI 的主入口仍是**整段描述 -> 结构化草案**，不是零散字段上的“小建议按钮”。
2. AI 重点生成的是：
   - 角色定义层草案
   - 消费契约层草案
   - `L4` 的输出方式建议；若建议结构化输出，再一并生成模板选择与角色级扩展草案
3. AI 不负责直接确定：
   - 实际知识绑定对象
   - 实际数据能力绑定（`data_asset_bindings`）
   - `model_binding` 的运行时覆盖值
   - `owner / maintainer / visibility / enterprise_role_mapping / publish / export`
   - 测试证据与发布结论
4. 治理字段可以有默认值或推荐值，但**最终归属和发布动作必须由人确认**。
5. 字段级 AI 建议如果后续保留，也只能是**补充能力**，不能取代主入口。

### 7.5 新 `L1` 逐项收口结论

新的 `L1` 本轮要回答的是 3 个问题：

1. **这个角色是谁**
2. **这个角色最核心负责哪一组职责**
3. **这个角色默认从什么视角看问题**

因此，新的 `L1` 收口为：

| 字段 | 本轮定位 | 是否主路径 | 阶段要求 |
| --- | --- | --- | --- |
| `name` | 角色识别名 | 是 | 起草即必填 |
| `bio` | 一句话摘要 | 是 | 起草即必填 |
| `main_duty_cluster` | 角色核心职责锚点；用户侧显示为 `核心职责` | 是 | 进入 `test` 前必填 |
| `point_of_view` | 角色默认分析视角 | 是 | 进入 `test` 前推荐完整 |
| `decision_style` | 结论形成风格 | 否，高级项 | 推荐填写 |
| `identity_background` | 判断背景与专业来源 | 否，补充项 | 可选 |
| `speaking_style` | 表达方式与语气 | 否，高级项 | 可选 |

#### 新 `L1` 的固定解释

1. `name`
   - 只回答：**这个角色叫什么**
   - 不承担职责解释、能力解释和市场文案
2. `bio`
   - 只回答：**这个角色是谁，主要做什么**
   - 必须是短摘要，不能替代完整职责定义
3. `main_duty_cluster`
   - 只回答：**这个版本最核心的一组职责是什么**
   - 它比 `bio` 更靠近角色运行锚点
4. `point_of_view`
   - 只回答：**这个角色默认先看哪些维度**
   - 它定义分析镜头，不定义最终结论风格
5. `decision_style`
   - 只回答：**这个角色更偏审慎、平衡还是推进**
   - 它当前已经进入角色 prompt，因此保留；但不再占主路径
6. `identity_background`
   - 只回答：**这个角色凭什么有这样的判断背景**
   - 它更像专业来源说明，不是职责说明
7. `speaking_style`
   - 只回答：**这个角色如何表达**
   - 它影响体感，但不是核心判断锚点

#### 新 `L1` 的降门槛原则

1. 首次创建时，用户主路径先只面对：
   - `name`
   - `bio`
   - `main_duty_cluster`
   - `point_of_view`
2. `main_duty_cluster` 的输入框必须给出**模板句式**，帮助用户按填空题方式完成，而不是自己组织开放式长文本。
3. `point_of_view` 的输入框也必须给出模板句式，避免用户重新写成空泛大段话。
4. `decision_style / identity_background / speaking_style` 统一收进高级 / 补充项，不再拆成独立层。
5. 新 `L1` 的简化重点不是删语义，而是避免用户一开始就写一堆相近文字。

#### 新 `L1` 与 `v0.4` 基线的承接约束

1. `bio` 在本轮不能被移除或降为可无，因为 `v0.4` 既有列表、详情、消费 prompt 和推荐链路都已实际依赖它。
2. `main_duty_cluster` 是新增强化项，但在 `v0.5` 只能补强 `bio`，不能简单取代 `bio`。
3. `decision_style / point_of_view / identity_background / speaking_style` 当前已真实进入 prompt，本轮是**重排交互优先级**，不是否定其语义价值。
4. 独立 `responsibility_boundary` 本轮不再保留为输入项，因为它与 `main_duty_cluster`、`point_of_view` 以及大量说明性字段重叠过高。
5. `企业实际角色映射` 仍然保留，但它进入治理侧，不再与新的 `L1` 同层表达。

### 7.6 `L2` 逐项收口结论

新的 `L2` 本轮要回答的是：

1. **这个角色实际绑定了哪些知识对象**
2. **这些知识对象的覆盖范围大致到哪里**
3. **这些知识在发布时是否可以被版本追溯**

因此，新的 `L2` 明确拆成两类内容：

| 内容 | 本轮定位 | 是否主路径 | 阶段要求 |
| --- | --- | --- | --- |
| `knowledge_refs` | 真实知识绑定对象 | 是，但可为空 | 任何阶段都可为空；有则增强可信度与追溯 |
| `validated_knowledge_versions` | 发布后的最小追溯结构 | 否，发布结果 | 仅在存在知识绑定且进入发布后生成 |
| `knowledge_boundary` | 知识覆盖范围声明 | 是，但只有在有知识绑定时才需要编辑 | 无知识绑定时不强制填写，由系统明确展示未绑定状态 |

#### 新 `L2` 的固定解释

1. `knowledge_refs`
   - 回答：**这个角色真正基于哪些知识对象工作**
   - 它不是说明文案，而是真实运行依赖
   - 若为空，表示当前**未绑定真实知识**；这是一种合法状态
2. `validated_knowledge_versions`
   - 回答：**这个版本发布时，绑定知识的版本快照是什么**
   - 它不是用户起草字段，而是发布追溯结果
   - 只有在确实绑定了知识时才生成
3. `knowledge_boundary`
   - 回答：**这些知识大致覆盖什么，不覆盖什么**
   - 它是说明性声明，不等于真实绑定本身
   - 未绑定真实知识时，不要求用户手写说明，由系统直接显示未绑定状态，避免误导成“已有知识追溯”

#### 新 `L2` 的降门槛原则

1. 新 `L2` 的主动作应同时支持两条合法路径：
   - 暂不绑定真实知识
   - 选择知识 -> 再确认知识边界
2. 不应要求用户在还没绑定任何知识前，先写一段抽象的 `knowledge_boundary`。
3. `knowledge_boundary` 应优先基于：
   - 已绑定知识
   - `main_duty_cluster`
   - AI 草案
   生成可编辑初稿，而不是完全空白起写。
4. 无知识绑定时，页面应直接展示“当前未绑定真实知识”的合法状态，并保留后续再绑定入口。
5. `knowledge_boundary` 的提示句式建议固定为：
   - `基于【知识来源】回答，暂不覆盖【不覆盖范围】。`
6. 新 `L2` 的简化重点不是隐藏知识绑定，而是**让绑定动作更容易完成、让边界声明更容易确认，同时让“无知识绑定”不再被误判为不成立**。

#### 新 `L2` 与 `v0.4` 基线的承接约束

1. `v0.4` 的知识绑定操作必须继续保留在工作区内，不能被降级成“只展示摘要”。
2. 但 `knowledge_refs` 不再作为任何阶段的硬门槛；`v0.5` 需要把“有知识绑定”和“暂不绑定真实知识”都表达成合法状态。
3. 当前检索仍按知识库 collection 执行，文件级绑定主要用于：
   - 展示
   - 发布追溯
   - 测试 / 消费的知识范围声明
   本轮不得把它误表述成“严格文件级检索约束”。
4. `knowledge_boundary` 继续保留，但只在有知识绑定时作为可编辑声明；无知识绑定时应由系统直接显示未绑定状态。
5. `validated_knowledge_versions` 继续保持最小追溯结构，不扩成新的知识治理系统；无知识绑定时不生成此结果。

### 7.7 `L3` 逐项收口结论

新的 `L3` 本轮要回答的是：

1. **这个版本是否被授权读取结构化业务数据**
2. **如果被授权，它具体绑定了哪些可读数据资产项**
3. **如果没有被授权，是否也能以合法状态成立并被如实表达**

因此，新的 `L3` 当前只保留一类正文能力：

| 字段 | 本轮定位 | 是否主路径 | 阶段要求 |
| --- | --- | --- | --- |
| 版本级数据能力绑定（`data_asset_bindings`） | 绑定当前角色版本被授权读取的结构化业务数据资产项 | 是，但可为空 | 允许为空；若绑定则在测试 / consume / 外供链中按当前生效配置工作 |

#### 新 `L3` 的固定解释

1. `data_asset_bindings`
   - 只回答：**这个角色版本在运行时实际能读到哪些结构化业务数据**
   - 它不是知识库绑定，不是临时输入上下文，也不是公网访问能力
   - 它是版本级授权能力，不是描述性说明文字
2. `数据资产项`
   - 由平台管理员在独立的数据资产管理页维护
   - 角色页只负责选择绑定，不负责现场创建
   - 管理员页最小必填只保留：`display_name / datasource_ref / database_name / table_name / scope_summary`
   - 可选项只保留：`freshness / owner_team`
   - 不再单列 `usage_notes`，避免与 `scope_summary` 重复
3. `未绑定数据能力`
   - 是一种合法状态
   - 必须被系统明确表达为“当前未授权结构化业务数据”，而不是被暗示成缺失或报错

#### 新 `L3` 的降门槛原则

1. 角色版本可绑定 `0~多条` 数据资产项，不限制为单条。
2. `L3` 在角色页里不再提供自由文本输入，避免重新退回“写文案冒充能力授权”。
3. 角色页只展示：
   - 选择数据资产项
   - 默认只展示 `display_name + scope_summary` 的已绑定摘要卡
   - 明确空状态
4. 数据资产项本身只表达**只读的结构化业务数据能力**，不承载写入、修改或执行动作。
5. 当前不做版本快照；已发布角色运行时读取的是当前生效的数据资产项配置。
6. 因此外供当前只冻结：
   - `role_id / role_version_id`
   - 说明卡当前保存版
   - `consume` / 输出 / 回写契约
   不冻结数据能力配置本身。

#### 新 `L3` 与 `v0.4` 基线的承接约束

1. `v0.5` 当前只把**数据能力**纳入 `L3` 正文；系统能力 / 通用能力 / 执行策略在没有统一运行时闭环前，不进入当前正文。
2. 平台内测试、正式消费和外平台复用，都应通过平台服务端查询层让数据能力真实生效，不把数据库连接信息暴露到角色页或外部平台。
3. 因为不做版本快照，数据能力的复现性依赖当前生效配置；这降低了管理成本，但会牺牲发布时能力配置的冻结复现。
4. 因此，外供必须把“数据能力按当前生效配置运行，非版本冻结项”的限制写入说明卡、外供说明与代表性验证口径。
5. 数据资产项需要由平台管理员在独立页面维护，角色页只允许选择绑定。

### 7.8 `L4` 逐项收口建议

新的 `L4` 本轮要回答的是：

1. **这个角色默认走自由输出还是结构化输出**
2. **如果走结构化输出，消费方至少可以稳定依赖什么模板与扩展字段**
3. **这个版本是否需要覆盖系统默认运行模型**

因此，新的 `L4` 拆成两层：

| 字段 | 本轮定位 | 是否主路径 | 阶段要求 |
| --- | --- | --- | --- |
| `output_mode` | 输出方式总开关：`freeform` / `structured` | 是 | 系统默认 `freeform`；试用前应明确当前路径 |
| `output_type` | 结构化输出所选的平台预置模板类型 | 仅在 `structured` 路径下是主路径 | 若选结构化输出，则试用前必须完整 |
| `output_schema` | 在平台模板上的角色级业务字段扩展 | 仅在 `structured` 路径下是主路径 | 若选结构化输出，则试用前必须完整 |
| `model_binding` | 运行模型覆盖项 | 否，高级项 | 默认继承系统值；有明确需要时再覆盖 |

#### 新 `L4` 的固定解释

1. `output_mode`
   - 只回答：**这个角色默认是自由输出，还是结构化输出**
   - 自由输出是默认合法路径，不应再被视为“未完成配置”
2. `output_type`
   - 只回答：**如果走结构化输出，这个角色复用哪一种平台模板**
   - 它不是市场分类，不是适用场景，也不是治理标签
3. `output_schema`
   - 只回答：**在模板基础上增加哪些角色级业务字段**
   - 它不是空白 JSON 填空题，也不是让用户另起一套输出体系
4. `model_binding`
   - 只回答：**这个版本是否覆盖系统默认运行模型，以及覆盖成什么**
   - 它是运行配置，不是角色价值主张，也不是消费前说明卡的主内容

#### 新 `L4` 的降门槛原则

1. `L4` 主路径应先明确“自由输出 / 结构化输出”。
2. 只有在选择 `structured` 后，才出现：
   - `output_type`
   - `output_schema`
3. `output_type` 应优先用业务语言卡片表达，让用户先选“交付什么结果”，而不是先看技术字段。
4. `output_schema` 必须基于平台预置模板自动带出，并允许角色级新增业务字段；不允许从空白 schema 起写。
5. 角色级扩展只允许**新增业务字段**，不允许删除或改坏平台模板的核心字段。
6. `model_binding` 不应与输出方式并列压在主路径里，默认应折叠到高级设置，并默认继承系统值。
7. `temperature / max_tokens / fallback_enabled` 等运行参数不应占据角色定义首屏。

#### 新 `L4` 与 `v0.4` 基线的承接约束

1. `v0.5` 的需求口径不再把“未配置结构化输出”直接视为角色天然不完整；自由输出是合法路径。
2. 只有选择结构化输出时，`output_type / output_schema` 才成为必须完整的消费契约。
3. 当前消费链、结构化结果校验和外部复用都真实依赖 `output_type`，因此一旦角色选择结构化输出，它仍必须继续作为角色版本默认输出契约保留。
4. 当前 AI 草案应继续能够产出：
   - `output_mode` 建议
   - 若建议结构化输出，则一并产出 `output_type + output_schema` 初稿
5. `model_binding` 当前已经真实影响测试与消费运行行为，因此它不能被删除；但交互上可以降为高级项，并默认继承系统值。

### 7.9 提示性例句统一规则

本轮补充确认：

1. 所有文本型输入的提示性例句都应统一遵守：
   - **模板句式优先**
   - **完整例句次之**
2. 模板句式必须让用户可以直接替换槽位，做填空题，而不是自己组织开放式简答题。
3. 在交互上，模板句式应优先直接放进输入框的 `placeholder` 中，以灰色提示词方式出现。
4. 输入框下方的辅助说明只负责解释：
   - 这个字段为什么要填
   - 填完后起什么作用
   - 与相邻字段如何区分
   不再承载主模板内容。
5. 完整例句只用来帮助用户校准粒度和语气，不应被写成“标准答案展示”。
6. 对 tag / 单值输入类字段，提示也应优先写成：
   - `输入【字段类型】`
   - `选择【字段类型】`
   再补一个例子。
7. `usage_notes / support_basis_summary` 在实际交互中应由系统先预生成，以下句式主要用于生成与补充时统一风格。

当前已明确的模板句式建议：

| 字段 | 模板句式 |
| --- | --- |
| `bio` | `面向【对象/场景】，提供【结果/价值】。` |
| `main_duty_cluster` | `围绕【对象/场景】，负责【动作1】、【动作2】，并输出【结果1】与【结果2】。` |
| `point_of_view` | `优先从【维度1】、【维度2】看问题，重点关注【关键矛盾/指标】。` |
| `identity_background` | `具备【经验/专业背景】，擅长从【维度】判断问题。` |
| `speaking_style` | `先【顺序1】，再【顺序2】，使用【语气/风格】表达。` |
| `knowledge_boundary` | `基于【知识来源】回答，暂不覆盖【不覆盖范围】。` |
| `data_asset.scope_summary` | `可读取【业务对象/指标】，粒度到【组织/周期】；不包含【明显不含范围】。` |
| `usage_notes` | `系统预生成：面向【使用者】，在【输入前提】下输入【输入】，获得【输出】。` |
| `support_basis_summary` | `系统先拼接知识/数据/测试依据；人工补充【业务依据/限制】。` |
| `enterprise_role_mapping` | `输入【部门/岗位/职责角色】` |
| `applicable_scenarios` | `输入【业务阶段/任务】` |

### 7.10 系统生成说明卡生命周期

本轮补充确认：

1. `applicable_scenarios / usage_notes / support_basis_summary` 共同组成**说明卡当前保存版**。
2. 说明卡首次进入页面时应由系统自动生成初稿；AI 草案路径可一并产出说明卡草案。
3. 说明卡的唯一生效文本是**当前保存版**：
   - 使用前前置卡读取当前保存版
   - 发布 / 外供门禁检查当前保存版
   - 外供包在生成时读取当前保存版
4. 当以下来源变化后，系统不得静默覆盖当前保存版，而应把说明卡标记为`待确认更新`：
   - `L1-L4` 相关字段
   - 知识状态与知识边界
   - 数据能力状态与绑定摘要
   - 最近验证 / 测试摘要
5. `待确认更新` 不是新的 Formal Status，只是说明卡自身的待处理标记。
6. 重新生成时，系统产出一版新的说明卡草案；**不自动合并或覆盖人工修订**，而是由用户确认替换或继续手工调整后再保存。
7. 用户也可以选择沿用当前文字，但必须通过一次显式保存来清除`待确认更新`标记。
8. 只要说明卡仍处于`待确认更新`，就不得进入正式发布 / 外供。
9. 若外供包已生成，之后说明卡来源再次变化，外供页应提示“供给物说明可能已过期，需要重新生成后再对外分发”。

### 7.11 外供最小可交付契约

本轮补充确认：

1. `Tool package` 与 `Skill package` 都必须包含一组**共同必需文件**：
   - `package-manifest.json`
   - `role-brief.md`
   - `consume-contract.json`
   - `output-contract.json`
   - `writeback-policy.md`
2. 其中：
   - `role-brief.md` 必须复用平台内同一张说明卡当前保存版
   - `consume-contract.json` 固定描述 `role_id / role_version_id / consume API / 输入输出边界`
   - `output-contract.json` 固定描述 `output_mode`，若为 `structured` 再包含 `output_type / output_schema`
   - `writeback-policy.md` 固定描述回写前提、必须保留的治理语义和不可绕开平台运行的要求
3. 形态专属文件固定为：
   - `Tool package`：`tool-manifest.json`
   - `Skill package`：`SKILL.md`
4. 以上文件是**规范必需项**，不是示意清单；额外 README、截图或演示材料都只能作为补充项。
5. “可直接使用”的最小判定标准是：
   - 不需要再由接入方手工拼接 `role_id / role_version_id / consume` 契约
   - 接入方仅需填写环境相关配置项，即可在代表性环境完成一次真实调用
   - 完成调用后，平台侧能看到对应 `usage_record`
6. 代表性验证当前固定为：
   - `Dify`：可导入 `Tool package` 并完成一次真实调用
   - `Codex`：可安装 `Skill package` 并完成一次真实调用
7. 外部复用链路中必须保留的治理语义固定为：
   - `role_id`
   - `role_version_id`
   - `status`
   - `boundary_status`
   - `structured_result` 或自由输出结果摘要
   - `usage_record`
8. 由于 `L3` 当前不做版本快照，外供说明必须显式声明：数据能力按当前生效配置运行，不承诺版本冻结复现。
