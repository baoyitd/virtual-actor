# v0.5.0 需求清单与边界清单

> 版本：v0.5.0
> Formal Status：Self-Tested
> 最后更新：2026-06-11
> 用途：把 2026-06-09 已达成的需求共识压缩成可核对清单，供后续设计评审和工作方同步使用
> 真源依据：`requirements-analysis.md`、`scope.md`

---

## 1. 使用方式

本清单只回答三件事：

1. 本轮需求到底保留哪些项。
2. 哪些问题已经明确排除，不应再反复回到原点。
3. 当前还处于什么阶段，下一步能做什么、不能做什么。

本文件不是设计稿，不定义页面解法、字段解法或接口解法。

## 2. 需求清单

### R1. 角色规格强化

必须达成：

1. `main_duty_cluster` 是角色本体核心 requirement，用户侧显示为 `核心职责`。
2. 原 `L2` 判断方式不再独立成层，而是并入新的 `L1`，形成“角色身份与判断”的统一层。
3. `分析视角` 保留在新的 `L1` 主路径。
4. `决策风格 / 身份背景 / 表达风格` 保留，但进入新的 `L1` 高级 / 补充项。
5. 独立 `职责说明 / 职责边界` 删除，不再作为本轮单独字段保留。
6. `角色定位` 删除，不再作为本轮字段保留。
7. `企业实际角色映射` 进入治理侧，用来表达数字角色与企业实际角色的映射关系，并支持多角色输入。
8. `L3` 重构为可选的版本级数据能力：角色页只选择绑定，管理员页维护可绑定的数据资产项。
9. `L4` 重构为“输出方式 + 运行配置”：默认自由输出，只有结构化输出路径才需要模板与扩展。
10. 旧的 `capability_boundary / capability_level / collaboration_mode` 默认移出当前正文，不再默认保留。
11. 本轮重点是让角色粒度更准、消费者更容易理解。

明确不要求：

1. 不新增独立定义包对象。
2. 不把完整岗位整体镜像成一个角色。
3. 不把这组 requirement 直接做成重门禁或组织系统。

### R2. 角色资产最小说明能力

必须达成：

1. 角色在发布、市场、复用侧要能说明“怎么用”。
2. 角色在发布、市场、复用侧要能说明“靠什么成立”。
3. 页面外显统一为 `使用前说明与调用预览`，并以系统生成说明卡为主。
4. `applicable_scenarios` 影响选择、推荐和发布门禁，但不表述为直接控制 `consume` 运行时行为。
5. `usage_notes` 由系统预生成整段说明、人工微调。
6. `support_basis_summary` 由系统生成主体、人工补充一句业务说明。
7. 这项说明服务于调用前理解，不是新的治理层。
8. 说明卡必须有明确生命周期：当前保存版、待确认更新、重新生成与外供读取口径都要冻结。

明确不要求：

1. 不做成权限系统。
2. 不做成审批系统。
3. 不要求把六类资产做成六套对象中心。

### R3. AI 协作创建升级

必须达成：

1. AI 草案要继续保持“自然语言 -> 结构化草案”的主链路，并进一步升级为更完整的“角色规格草案”。
2. 必须明确承接 `v0.4` 已有的“自然语言输入 -> 结构化草案 -> 人确认后保存”能力，不能把 `v0.5` 设计成另一条独立产品线。
3. AI 草案与人工编辑必须落回同一套角色理解模型。

明确不要求：

1. 不允许把复杂性完全甩给 AI。
2. 不允许用户后续仍看不懂、改不动。

### R4. 角色创建 / 编辑交互重设计

必须达成：

1. 目标是降低理解成本和操作门槛。
2. 本质是把“字段填写任务”改成“可理解的角色构建任务”。
3. 主成功标准优先是理解成本下降，操作门槛下降是结果。

明确不要求：

1. 不得降级为纯视觉换肤。
2. 不得通过删能力来假装更易用。
3. 不得把创建和编辑做成两套割裂心智模型。

### R5. 现有发布门禁补充

必须达成：

1. 不新造门禁体系。
2. 只在现有发布门禁上补充本轮新增 requirement 的检查项。
3. 发布判断要从“技术可跑”适度提升到“资产达到最小可复用性”。
4. `owner / business_domain / category` 在“可供他人消费”和“正式发布 / 外供”阶段都不得退化为软提示。

明确不要求：

1. 不新增审批流。
2. 不新增独立资产门禁系统。
3. 不把发布流程做重到拖垮使用效率。

### R6. 稳定外部供给载体

必须达成：

1. 对外复用的最小单位是**单个已发布角色版本**。
2. 平台要支持把“适合外部复用的已发布角色版本”变成稳定供给物。
3. 当前供给形态先收口为 `Tool package` 与 `Skill package`。
4. 供给物建立在现有 `consume API` 之上。
5. 供给物必须能随附最小说明，而不是只给一个裸 API。
6. 外部复用后，关键使用信号必须继续回写平台侧。
7. `Tool package / Skill package` 的最小必含文件、可直接使用标准和代表性验证通过标准必须冻结。
8. 当前 `L3` 不做版本快照，因此外供必须明确声明“数据能力按当前生效配置运行，不承诺版本冻结复现”。

明确不要求：

1. 不要求所有已发布角色默认都外供。
2. 不做完整外部分发中心。
3. 不冻结所有平台、所有协议、所有适配矩阵。

### R7. 分阶段补齐，不一次性压满

必须达成：

1. 起草角色时，优先完成角色定义最小骨架，不把治理项一次性压满。
2. 进入 `test` / 开始试用前，先补齐真实运行所需项。
3. 给别人消费前，再把消费契约补完整。
4. 正式发布 / 外供前，才要求治理项和现有门禁闭合。

明确不要求：

1. 不新增一套状态枚举来表达这些阶段。
2. 不把第一次创建强行变成“填完整资产台账”。

## 3. 固定约束

以下约束已确认，不应在后续设计评审中被悄悄改写：

1. 角色资产的最小成立单元仍是 `职责簇`。
2. “负责什么 / 不负责什么”不单列为本轮 platform requirement。
3. `L1-L4` 是角色定义的唯一主骨架，其中新的 `L1` 已吸收原 `L2` 的判断方式字段，不得再被流程步骤文案替代。
4. `applicable_scenarios / usage_notes / support_basis_summary` 属于消费契约层，不属于角色定义主骨架。
5. `category / owner / maintainer / business_domain / visibility / tags / enterprise_role_mapping / 发布 / 外供 / 追溯` 属于资产治理层，不属于角色定义主骨架。
6. 外部复用不得丢失：
   - `role_id`
   - `role_version_id`
   - `structured_result`
   - `status`
   - `boundary_status`
   - `usage_record`
7. 外部复用后，平台侧必须还能追溯身份、版本、状态、边界和使用记录。
8. 角色新建 / 编辑降门槛是本轮主线 requirement，不是附属 UI 优化。
9. “起草角色 / 内部试用 / 可供他人消费 / 正式发布 / 外供”是完成阶段，不是新状态枚举。
10. AI 主入口继续是“自然语言输入 -> 结构化草案 -> 人确认后保存”，不能回退成零散字段建议。
11. 知识绑定不是任何阶段的硬门槛；有知识绑定与暂不绑定真实知识都是合法状态，但消费侧和外供侧必须如实表达。
12. `L3` 当前正文只纳入数据能力；系统能力 / 通用能力 / 执行策略在没有统一运行时闭环前，不进入当前正文。
13. `使用前说明与调用预览` 只表达事实限制，不承担 `待补齐 / 不可发布` 等门禁判定。
14. `visibility` 保留但降为补充治理项，不按 ACL 语义设计。
15. 数据资产最小模型只保留 `display_name / datasource_ref / database_name / table_name / scope_summary` 为必填，`freshness / owner_team` 为可选，不再单列 `usage_notes`。
16. 角色版本可绑定 `0~多条` 数据资产项；未绑定是合法状态；当前不做版本快照。
17. `L4` 默认 `freeform`；只有选择 `structured` 时，`output_type / output_schema` 才成为必须完整的消费契约。
18. `model_binding` 继续保留，但默认继承系统值，并降为高级配置。
19. 外供通过已发布版本上的显式生成动作表达，不新增独立外供开关字段；外供说明复用同一张说明卡。
20. `owner / business_domain / category` 在 `test` 阶段可后补；进入“可供他人消费”和“正式发布 / 外供”阶段时三项全部为硬要求。
21. 说明卡以“当前保存版”为唯一生效文本；来源变化后进入`待确认更新`，未确认不得发布 / 外供。
22. 外供冻结的是身份、说明卡当前保存版、输出契约与回写语义；不冻结 `L3` 数据能力配置本身。
23. `Tool package / Skill package` 共同必需文件固定为 `package-manifest.json / role-brief.md / consume-contract.json / output-contract.json / writeback-policy.md`；形态专属文件分别为 `tool-manifest.json` 与 `SKILL.md`。
24. 知识绑定、数据能力和 `freeform / structured` 输出契约不得只停留在页面说明、字段保存或发布门禁上；后续测试 / 消费 / 外部复用链路必须能观察到真实运行差异。
25. 角色主链页面顺序固定为 `01 角色定义工作台 -> 02 使用前说明与调用预览 -> 03 试用与测试 -> 04 治理与发布 -> 05 正式消费 -> 06 外供与追溯`；`数据资产管理` 是配套管理员页，不进入角色主链编号。
26. 页头只保留当前页面的全局动作；跨页跳转通过阶段导航、角色概览页和阻断提示承接，不在每页页头重复堆按钮。
27. `02 使用前说明与调用预览` 的保存动作负责把当前可编辑版本推进到 `test`；`03 试用与测试` 页面只负责执行 / 复测；`04 治理与发布` 页面承接 `publish / archive`。
28. `archived` 是生命周期终态，不是后续页面；归档后角色退出活跃市场、正式消费和新外供，但历史追溯保留。
29. `使用前说明与调用预览` 的重生成动作必须显式表达为“根据最新角色信息重生成说明卡”，且只在 `待确认更新 / stale` 上下文出现，不得再使用模糊的“重新生成草案”文案。

## 4. 边界清单

以下内容当前明确不在本轮主需求范围内：

1. 独立 `RoleAssetDefinitionPackage` 产品对象。
2. 定义包中心、翻译工作台、导入中心。
3. 六类资产各自独立的一等子系统。
4. 新造一套发布门禁体系。
5. 单列“负责什么 / 不负责什么”字段组。
6. 完整动作执行平面、审批链、动作审计系统。
7. 企业级 RBAC、多租户、完整组织权限体系。
8. 全平台一次性冻结的外部协议 / 适配矩阵。

## 5. 阶段边界

当前仍处于：

```text
v0.5 / Self-Tested / Design Freeze Effective / 可进入最终用户测试
```

当前允许：

1. 基于本清单、现行真源和测试证据进入最终用户测试。
2. 若用户测试阶段出现设计偏差，先回写真源并登记偏差，再继续修复。

当前不允许：

1. 把未同步的设计草稿当成实现真源。
2. 把已排除事项重新偷渡回本轮主设计。
3. 未经偏差管理擅自突破已冻结口径。

## 6. 一句话总结

> **本轮不是做一套更重的角色管理系统，而是在现有 `RoleAsset + RoleVersion + consume API` 底座上，把角色做得更像真实职责资产、更容易被创建和理解，并能被外部 AI 环境稳定复用。**
