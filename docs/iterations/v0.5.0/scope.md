# v0.5.0 范围说明

> 版本：v0.5.0
> Formal Status：Self-Tested
> 最后更新：2026-06-11
> 前置文档：`requirements-analysis.md`、上游 `va-platform-role-asset-validation-handoff.md`

## 1. 本轮目标

从 `v0.4` 的“企业数字角色资产运营平台”继续升级为：

```text
企业数字角色资产管理平台（角色能力强化与外部复用准备版）
```

完整表达：

```text
让平台中的角色资产更接近现实世界职责角色，
并能以受控、可追溯、可解释的方式供给外部 AI 环境复用。
```

本轮新的主链路：

```text
业务意图 / 现实职责来源
  -> 角色定义（L1-L4）
  -> 使用前说明与调用预览（消费契约）
  -> 资产治理 / 发布门禁
  -> 外部供给载体
  -> 外部消费与追溯
```

本轮不把“上游定义包输入对象”作为主设计，不新增额外的定义包管理层。

## 3. Scope Out

1. 不新增独立的 `RoleAssetDefinitionPackage` 产品对象。
2. 不新增定义包中心、翻译工作台或导入中心。
3. 不新增六类资产各自独立的一等对象中心。
4. 不单列“负责什么 / 不负责什么”字段组作为本轮 requirement。
5. 不新造一套发布门禁体系或审批流。
6. 不在本轮实现完整动作执行平面、审批链和动作审计系统。
7. 不做企业级 RBAC、多租户或完整组织权限体系。
8. 不要求所有已发布角色默认都对外供给；只要求平台支持对“适合复用的已发布版本”进行稳定供给。
9. 不在本轮冻结 Dify、Codex、决策产品等全部外部分发协议、全部通道或全部平台矩阵。
10. 不把上位项目验证型 handoff 直接写成平台实现真源。
11. 不在本轮正文承诺尚无统一运行时闭环的系统能力、通用能力或执行策略。

## 5. 页面与用户侧边界

本轮页面结构不再以“一个大而全的角色配置页”作为默认叙事，而固定为：

### 5.1 角色能力侧

面向角色创建者 / 角色维护者，负责：

1. `L1-L4` 角色定义
   - 其中新的 `L1` 已吸收原 `L2` 的判断方式字段
2. `使用前说明与调用预览`（消费契约层）维护

这里回答的是：

1. 这个角色是什么
2. 这个角色怎么判断
3. 这个角色基于什么知识
4. 这个角色是否被授权读取结构化业务数据
5. 这个角色默认是自由输出还是结构化输出，以及如何运行
6. 别人怎么正确地使用它

### 5.2 资产治理侧

面向资产运营方 / 发布责任人，负责：

1. 治理字段维护
2. 测试证据核对
3. 发布门禁执行
4. 外供生成
5. 使用记录与追溯

这里回答的是：

1. 这个角色由谁负责
2. 是否达到可发布资产标准
3. 是否已满足外供条件并生成稳定供给物
4. 外部使用后能否被持续追溯

### 5.3 全局一级导航优先级

1. 一级导航优先表达稳定任务域，而不是把“创建”这类动作和页面并列。
2. `资产市场` 放在首位，服务更大规模的消费 / 发现人群。
3. `角色资产` 作为第二入口，服务创建、维护和带消费目的的复合用户。
4. `运营看板 / 数据资产管理` 语义上偏向管理员与资产运营方，位于后段。
5. `新建角色` 固定为 `角色资产` 页内动作入口，不单列为一级导航项。

### 5.4 固定结构约束

1. `L1-L4` 是角色定义的唯一主骨架，其中新的 `L1` 已吸收原 `L2` 的判断方式字段。
2. `使用前说明与调用预览` 属于消费契约视图，不属于角色本体定义页主骨架。
3. `发布前检查`、`治理字段`、`外供生成` 属于资产治理侧，不属于角色定义页主骨架。
4. 治理页主路径固定为 `owner / business_domain / category`；`visibility / maintainer / tags / enterprise_role_mapping` 为补充治理项。
5. `owner / business_domain / category` 在“可供他人消费”和“正式发布 / 外供”阶段必须完整，不得降为纯展示字段。
6. formal 状态仍只保留 `draft / test / published / archived`；`02` 保存当前说明卡进入 `test`，`04` 承接 `publish / archive`，`05/06` 是发布后的复用面而不是状态。
7. `archived` 后角色退出活跃市场、正式消费和新外供，但历史版本、外供记录与使用记录继续可查。
8. 如某项字段不直接影响角色输出、角色选择或资产治理责任，应继续弱化或移出主路径。

## 6. 非目标与禁止动作

1. 不在需求分析和设计冻结前直接进入实现。
2. 不把“上位项目定义”误读为“必须新增定义包对象”。
3. 不让平台页面、数据库或接口反向定义角色资产本体。
4. 不为了“看起来管理更完整”而平白增加对象数量和维护负担。
5. 不把“负责 / 不负责”重新包装成单独字段组强行塞回本轮主设计。
6. 不把“发布门禁补充”偷换成“新建资产门禁体系”。
7. 不把“角色创建 / 编辑交互重设计”降级为纯视觉换肤或文字润色。
8. 不把“对外供给稳定载体”偷换成“做一个完整外部分发中心”。
9. 如设计继续显著走向全平台协议适配或动作执行平台，必须先回到范围评审。

## 7. 需求分析阶段退出标准

1. 已明确：平台当前核心对象仍是 `RoleAsset + RoleVersion`，上位项目输入首先作为设计依据。
2. 已明确：`main_duty_cluster` 是本轮角色本体核心 requirement，用户侧显示为 `核心职责`。
3. 已明确：`角色定位` 删除；`企业实际角色映射` 进入治理侧，并支持多角色输入。
4. 已明确：`负责什么 / 不负责什么` 不单列为本轮 platform requirement。
5. 已明确：本轮保留统一 requirement“角色资产最小说明能力”，用于解释“怎么用”和“靠什么成立”。
6. 已明确：角色创建 / 编辑交互重设计属于本轮 P0 requirement，目标是降低理解成本和操作门槛，而不是单纯视觉优化。
7. 已明确：发布门禁不新建体系，只在现有机制上补充本轮新增 requirement 的检查项。
8. 已明确：平台要支持把“适合外部复用的已发布角色版本”生成稳定供给载体。
9. 已明确：本轮对外供给形态先收口为 `Tool package` 和 `Skill package`。
10. 已明确：外部复用后的关键使用信号必须继续回写平台侧，不得切断运营闭环。
11. 已明确：当前低保真线框只用于方向评审，不能直接作为最终设计冻结依据。
12. 已明确：在 Design Freeze 前，关键页面必须补高保真原型并完成评审。
13. 已明确：代表性外部环境验证只要求两个代表环境，不冻结全部平台和协议矩阵。
14. 已明确：`起草角色 / 内部试用 / 可供他人消费 / 正式发布 / 外供` 是完成阶段，不新增状态枚举。
15. 已明确：AI 主入口继续保持“自然语言输入 -> 结构化草案 -> 人确认后保存”，治理项由人补齐。
16. 当前 Formal Status 已升级为 `Self-Tested`；`Design Freeze Status` 已于 `2026-06-10` 生效，当前允许进入最终用户测试与验收准备。
17. 已明确：知识绑定不是任何阶段的硬门槛；有绑定与暂不绑定真实知识都是合法状态，但消费侧与外供侧必须如实表达。
18. 已明确：`L3` 当前正文只保留版本级数据能力；角色页只选择绑定，管理员页维护可绑定数据资产项，且当前不做版本快照。
19. 已明确：外供当前冻结的是身份、说明卡当前保存版、输出契约与回写语义；数据能力按当前生效配置工作，不承诺版本冻结复现。
20. 已明确：`owner / business_domain / category` 在“可供他人消费”和“正式发布 / 外供”阶段均为硬要求。
21. 已明确：说明卡以“当前保存版 + 待确认更新”机制工作，来源变化后必须重新确认，未确认不得发布 / 外供。
22. 已明确：`Tool package / Skill package` 已冻结最小可交付契约与代表性验证标准，不再只是示意文件名。
23. 已明确：`L4` 重构为“输出方式 + 运行配置”；默认自由输出，只有结构化输出路径才需要模板与扩展。
24. 已明确：旧的 `capability_boundary / capability_level / collaboration_mode` 默认移出当前正文，不再默认保留。

## 8. 下一阶段约束

当前处于**Design Freeze 已生效、Formal Status = Self-Tested**阶段。接下来允许：

1. 基于当前实现与证据进入最终用户测试 / 验收阶段。
2. 若用户测试阶段发现字段边界、外供语义或页面结构需要调整，先登记偏差并回写真源，再继续修复。
3. 继续把已排除事项维持在 `Scope Out`，不得借实现名义回流。

## 9. 设计蓝图与实现批次

`v0.5` 的设计蓝图保持完整，不因实现排期被缩减。实现拆分只改变顺序，不改变最终验收目标。

主批次固定为：

1. **Batch 1：领域基础与门禁后端**
   - 承接 `L1-L4` 存储、消费契约生命周期、治理主路径门禁、legacy 兼容后端、数据资产管理底座
2. **Batch 2：统一工作区与治理界面**
   - 承接 AI / 手工同骨架工作区、`使用前说明与调用预览`、治理与发布页、数据资产管理页、legacy 补齐界面
3. **Batch 3：运行效果与外部复用闭环**
   - 承接知识 / 数据 / 输出契约真实生效、`Tool package / Skill package` 生成、代表环境验证、平台回写闭合
4. **Batch 4：全链路自测与验收材料**
   - 承接自动化、程序化 UI、运行效果型测试、外部环境验证、人工冒烟、交付材料与 `Self-Tested` 证据

并行治理线：

- **Parallel G1：仓库治理与发布元数据清理**
  - 清理 `iteration-guard` 当前受历史发布元数据影响的失败项；它不改变 `v0.5` 产品范围，并已在主张 `Self-Tested` 前闭合

详细拆分、批次进入条件和停止条件，以 `implementation-plan.md` 为准。
