## 一、集成可行性前置推演

在定义角色自身模型之前，先检查两个外部产品的现有能力是否足以支撑集成，避免设计出对方无法承接的方案。

### 1.1 角色产品对知识平台的接口需求

以下为角色产品需要知识平台提供的 4 项接口能力。**不指定知识平台的实现方案**（Dify / Open WebUI / 自建），只定义接口契约。

| 序号 | 接口需求 | 说明 | 调用时机 |
|------|---------|------|---------|
| **1** | 知识对象列表查询 | 按 status（reviewed/published）、type、tags 筛选，返回 title、summary、tags、knowledge_id | 角色创建/编辑时，浏览可绑定的知识 |
| **2** | 知识内容获取 | 按 knowledge_id 获取知识全文（Markdown 原文） | 角色绑定时记录内容快照；角色回答问题时检索 |
| **3** | 知识检索 | 基于角色已绑定的知识范围，按自然语言 query 返回最相关的内容片段（chunk + 来源 knowledge_id） | 角色对话运行时，检索相关知识注入 prompt |
| **4** | 知识版本标识 | 返回当前知识库的版本标识（如整体版本号或变更时间戳），用于角色侧记录 validated_knowledge_versions | 角色发布时，快照当前知识库版本 |

**原则**：角色产品只认这 4 个接口契约，不对知识平台的内部实现（Dify、Open WebUI、ChromaDB、BM25 等）做任何假设。知识平台自行决定如何满足。

#### 决策产品侧的潜在集成问题 

| 问题 | 评估 | 风险等级 |
|------|------|---------|
| 决策产品当前是设计阶段还是实现阶段？ | 集成草案写于 2026-05-13，结构完整但未见具体代码/工程目录。角色产品的设计需要**与决策产品并行推进，随时对齐** | 🟡 中 |
| 决策产品如何调用角色产品？ | 集成草案 §5.4 明确说：API 直连还是本地镜像、是否需要事件通知、是否需要深链跳转——**全部未写死** | 🟡 中 |
| 角色产品的 API 格式 | 集成草案 §8 给了候选 API 路径（`GET /role-assets` 等），但强调只是「消费侧建议范围，不是已冻结契约」 | 🟢 低 |

#### 结论：决策产品对角色产品的读取需求，角色产品均可满足，无需决策产品侧重构。

- 角色产品自主设计 API 格式，决策产品作为消费方对接
- **需要约定的是调用拓扑**（API 直连 / 本地镜像 / MCP？），这个由后续回 A 级裁决
- 角色产品先按 REST API 模式实现，后续切换调用拓扑不改变数据模型

## 二、角色资产数据模型

### 2.1 角色 5 层模型

```
┌─────────────────────────────────────────────────────────┐
│                  RoleAsset 数据模型                       │
├───────┬─────────────────────────────────────────────────┤
│  L1   │  身份 Identity                                  │
│       │  role_name, avatar_url, bio, tags                │
├───────┼─────────────────────────────────────────────────┤
│  L2   │  心智 Mind                                      │
│       │  identity_background（定位描述）                  │
│       │  point_of_view（立场/思维偏好）                   │
│       │  decision_style（决策风格）                       │
│       │  responsibility_boundary（职责边界）              │
│       │  speaking_style（表达风格）                       │
├───────┼─────────────────────────────────────────────────┤
│  L3   │  知识 Knowledge       ← 核心创新层                │
│       │  knowledge_refs[] （绑定的知识引用列表）           │
│       │  validated_knowledge_versions[] （版本快照）       │
│       │  knowledge_boundary（知识范围声明）               │
├───────┼─────────────────────────────────────────────────┤
│  L4   │  能力 Capability                                │
│       │  tools[]（可调用工具）                            │
│       │  collaboration_mode（独立/可委派/仅咨询）          │
│       │  capability_boundary（能力诚实声明）              │
├───────┼─────────────────────────────────────────────────┤
│  L5   │  配置 Config                                    │
│       │  model_binding（LLM 模型 + 参数）                 │
│       │  memory_strategy（记忆策略）                      │
│       │  api_expose_config（API 暴露配置）               │
└───────┴─────────────────────────────────────────────────┘
```

### 2.2 字段对照：角色 5 层 ↔ 决策产品 §5.2 公共字段

| 决策产品提议的公共字段 | 对应角色数据层 | 纳入公共契约？ | 备注 |
|----------------------|--------------|---------------|------|
| summary | L1 身份（计算字段：bio 截断） | ✅ 纳入 | 角色产品生成，决策产品读取 |
| identity_background | L2 心智 | ✅ 纳入 | 角色创建时填写 |
| point_of_view | L2 心智 | ✅ 纳入 | 角色创建时填写 |
| decision_style | L2 心智 | ✅ 纳入 | 角色创建时填写 |
| responsibility_boundary | L2 心智 | ✅ 纳入 | 角色创建时填写 |
| model_binding | L5 配置 | ✅ 纳入 | 角色创建时配置 |
| knowledge_refs | L3 知识 | ✅ 纳入 | 角色创建时绑定 |
| validated_knowledge_versions | L3 知识 | ✅ 纳入 | 发布时快照 |

**角色产品的反馈**：8 个字段均支持，建议全部进入公共契约。角色产品额外建议 `role_name` 和 `speaking_style` 也进入公共字段，因为决策产品的「信息流角色身份展示」和「结果追溯」会用到。

## 三、角色资产内部生命周期

### 3.1 状态机

```
draft ──→ test ──→ published ──→ archived
  │        │          │              │
  │        │          │              │
  │   测试不通过       │          角色被废弃
  │   回到 draft     │              │
  └────────┘          │              │
                      │              │
                  有新版本发布        │
                  旧版本自动 archived │
```

### 3.2 各状态说明

| 状态 | 含义 | 谁可见 | 触发动作 |
|------|------|--------|---------|
| **draft** | 创建/编辑中的草稿 | 仅角色产品内部 | 创建角色进入此状态 |
| **test** | 进入测试阶段 | 角色产品内部（测试页） | 人工点击「进入测试」 |
| **published** | 已发布，可被决策产品消费 | 决策产品可读取 | 人工点击「发布」，生成 version_id |
| **archived** | 已废弃/被新版本替代 | 仅内部追溯，决策产品不可读取 | 人工归档 或 新版本发布自动归档旧版本 |

### 3.3 与决策产品集成草案的对照

> 集成草案 §4.1 提问：draft/test/published/archived 是否足够？是否还需要 deprecated、superseded？

**角色产品回答**：
- draft/test/published/archived 四状态**足够**，不需要额外 deprecated/superseded
- superseded 逻辑由「新版本发布 → 旧版本自动 archived」替代，不引入额外状态
- 如果需要表达「不推荐使用但仍在」的语义，在 `RoleVersion` 上加一个 `deprecated: bool` 标记即可，不改状态机

## 四、知识引用方案

### 4.1 knowledge_ref 结构

```json
{
  "knowledge_ref_id": "kref-uuid",
  "knowledge_platform_id": "10-Areas/ai/rag-architecture",  // 知识平台文件路径或 Dify 条目 ID
  "knowledge_title": "RAG Architecture Comparison",
  "knowledge_status_snapshot": "published",  // 绑定时快照的状态
  "knowledge_tags": ["rag", "architecture"],
  "bound_at": "2026-05-14T10:00:00Z"
}
```

### 4.2 validated_knowledge_version 结构

```json
{
  "knowledge_version_id": "kver-uuid",
  "knowledge_ref_id": "kref-uuid",
  "git_commit_hash": "abc123def456",  // 绑定时知识平台的 Git commit
  "validated_at": "2026-05-14T10:00:00Z",
  "status": "valid"  // valid | expired
}
```

> 如果知识平台无法通过 API 提供 Git commit hash，降级方案：角色产品在绑定时执行 `git -C {vault_path} rev-parse HEAD` 获取当前 commit hash。此方案不需要知识平台侧任何改动。

### 4.3 知识平台集成风险结论

**无需知识平台重构**。Dify API 足以覆盖知识列表查询 + metadata 过滤。版本引用可走 Git commit hash（角色产品侧执行 `git rev-parse` 获取）。知识状态同步通过每次读取时查最新状态即可。

## 五、对外暴露接口（消费侧）

### 5.1 接口列表（反馈决策产品 §8 候选 API）

| 接口 | 方法 | 说明 | 对决策产品 §8 的反馈 |
|------|------|------|---------------------|
| `/role-assets?status=published` | GET | 已发布角色列表 | ✅ 同意 |
| `/role-assets/{role_id}` | GET | 角色详情（含所有公开字段） | 新增：决策产品 §8 只提了 published-version，建议增加角色详情接口 |

| `/role-assets/{role_id}/versions/{version_id}` | GET | 指定版本详情（冻结回放用） | ✅ 同意，对应 §8.3 |

## 六、UI 页面规划

### 6.1 页面清单

| 页面 | 用途 | 优先级 |
|------|------|--------|
| 角色列表页 | 查看所有角色（按状态筛选：全部/draft/test/published/archived） | P0 |
| 角色创建/编辑页 | 5 层模型的表单填写 + 知识绑定 | P0 |
| 角色详情页 | 只读展示角色完整信息 + 版本历史 | P0 |
| 角色测试页 | 选择角色 → 输入测试问题 → 查看回复（含知识溯源） | P1 |
| 发布与版本页 | 发布确认 + 版本历史列表 + 版本对比 | P1 |
| 知识浏览与绑定组件 | 嵌入在创建/编辑页中，连接知识平台 | P0 |

### 6.2 关键交互：知识绑定流程

```
角色创建/编辑页
   │
   ├── 点击「绑定知识」
   │     │
   │     ├── 知识浏览面板（弹窗或侧栏）
   │     │   ├── 按 status/type/tags 筛选（调用 Dify API）
   │     │   ├── 显示 title, summary, tags, status
   │     │   └── 选中若干知识条目
   │     │
   │     ├── 确认绑定
   │     │   ├── 记录 knowledge_refs
   │     │   └── 记录 validated_knowledge_versions（Git commit hash）
   │     │
   │     └── 关闭面板，回显已绑定知识列表
   │
   └── 继续填写其他字段
```
